# Dependencies, Node And Dockerfiles

Read this before bumping a dependency or Node, accepting a vulnerability (`osv-scanner.toml`, `pnpm.auditConfig`), or editing a Dockerfile. Part of the agent rules indexed in `AGENTS.md` § "Topic Rules".

## Two Scanners, One Acceptance

A vulnerability can be accepted in two places, and they read different files. `osv-scanner.toml` feeds CI's `vuln-scan` job; `pnpm.auditConfig.ignoreGhsas` in the root `package.json` feeds `pnpm audit --audit-level=high --prod`, the gate `scripts/release.mjs` runs before a tag is cut. **`pnpm audit` does not read `osv-scanner.toml`.** GHSA-mh99-v99m-4gvg was triaged and accepted in #914 and told only to osv-scanner, so v0.9.0 could not be cut over an advisory the repo had already accepted — the acceptance sat on record in a place the release path never consults (#993).

`scripts/lib/audit-ignore-parity.test.mjs` (pure logic in `audit-ignore-parity.mjs`, run by `pnpm test:scripts`) enforces the pairing. Every id in `ignoreGhsas` must have an `[[IgnoredVulns]]` entry with a `reason` and a **non-expired** `ignoreUntil`.

- **The expiry rule is the load-bearing one.** `ignoreGhsas` is a bare array of ids — no reason, no expiry, and pnpm offers no `ignoreUntil`. So on the expiry date osv-scanner re-opens the question and `pnpm audit` structurally cannot; the two configs diverge by construction, with the _release_ path the silent one. The guard is how the pnpm-side silence inherits the deadline written next to the rationale.
- **The check is one-directional on purpose** — `ignoreGhsas` ⊆ osv ids, never the reverse. Most entries here are things `pnpm audit --prod` at the root cannot see anyway (the braces one is a devDependency, the sprintf-js one is moderate; anything accepted in `docs/pnpm-lock.yaml` sits in a separate, non-workspace lockfile — the five astro advisories did, until #851 retired them). Mirroring those would silence a scanner about findings it never emits. An **empty** `ignoreGhsas` is therefore a legitimate state, and since GHSA-mh99 was retired (its brace-expansion lines are all past the fix) it is the current one: re-adding an id means adding both halves, never just one.
- **The `reason` is the machine-readable record; the TOML comment above it is not.** osv-scanner prints `reason` and nothing else, so a route named only in the comment is not named at all — an acceptance that does not name a path it accepts is not an acceptance of that path.
- **The routes are read from the lockfiles, not listed per advisory.** Every reason opens with the affected package and the versions it claims are affected — `braces <=3.0.3, …`, `katex <0.18.2 …` — and `findUnnamedRoutes` resolves that against the lockfiles `vuln-scan` hands osv-scanner (the `--lockfile=` args of that job in `ci.yml`). For every affected version it requires the reason to name each package that depends on it directly **and** each importer-declared dependency it is reached through. The second half is what catches a new consumer arriving through an intermediate the reason already names — a runtime package starting to use fast-glob, or js-yaml@3 pulling argparse@1 — which a one-hop check reads as green. The graph is versioned (argparse@2 is not a route to sprintf-js), resolves npm aliases to the real package, and drops peer edges (Starlight → astro is the consumer's own pick, not a second way in). Declaring a package directly is one route, not an exemption for its others.
- **The range is the only offline link from an advisory to a package.** A reason opening with some other package ("mammoth pulls sprintf-js in …") has no range and fails; a range no resolved version satisfies fails too. Nothing offline can prove the range is the advisory's own — it proves the reason is a claim about a package the lockfile really has in that version. A package in no scanned lockfile is reported as a stale acceptance, not as a misspelled reason.
- **An entry the parser cannot read is an error, not an absence.** `[[IgnoredVulns]] # comment` and `[[ IgnoredVulns ]]` are valid TOML that osv-scanner honours; the first parser split on the bare header and dropped both entries silently, and the test that counted headers used the same regex, so it agreed. Both spellings are read now, and so is a CRLF checkout. What is still unreadable — a quoted header, a case variant (osv-scanner's decoder matches keys case-insensitively), the inline `IgnoredVulns = [{ … }]` form, an entry without a readable `id` — throws. The repo-level count reads headers with a deliberately looser, case-insensitive pattern, so a parser miss shows up as a difference naming the skipped id, and the route test fails if any entry was not evaluated.
- **CI runs the release gate's own audit**, as the non-required, `changes`-gated `prod-audit` job. With `ignoreGhsas` empty the parity rule has nothing to compare, and an osv-only acceptance of a high/critical production advisory would otherwise surface only at `pnpm release`. The test reads the command out of `scripts/release.mjs` and requires a `ci.yml` job to run it byte-for-byte and to be able to fail on it: `--prod` without `--audit-level=high` is not the same gate, and a job carrying `continue-on-error`, `|| true`, `set +e`, `exit 0` or `if: false` is reported as defused. It is not required because a freshly published advisory turns it red with no commit behind it; that should inform a PR, not block every one.

## One Node Version, Stated In Four Kinds Of Place That Must Agree

Node is pinned in `.nvmrc` (`22`) and `engines.node` (`>=22 <23`); CI's `node-version:` and every Dockerfile's `FROM …node:<major>` must name the same major. `scripts/lib/node-version-pin.test.mjs` (pure logic in `node-version-pin.mjs`, run by `pnpm test:scripts`) fails if any of them drifts.

Until 2026-07 only CI said a version. A local Node could be anything, and nothing anywhere mentioned it — until a **native** module noticed, which is where this gets expensive. On Node v25.2.1 against a `better-sqlite3` built for Node 22, every `pinchy_read PDF integration` test failed like this:

```
AssertionError: expected 'The module …/better_sqlite3.node was compiled against a
different Node.js version using NODE_MODULE_VERSION 137. This version of Node.js
requires NODE_MODULE_VERSION 141.' to contain '<document>'
```

Read the shape, not just the text: `pinchy-files` returns the module loader's error as the tool's **result** rather than throwing, so an environment fault arrives as an ordinary assertion failure **on a product assertion**. Nothing says "rebuild your native modules". The honest reading is "the PDF path is broken", and the hours go into code that is fine (pinchy#947).

**The Dockerfiles are the place it is tempting to forget and the worst one to get wrong.** Through `better-sqlite3` 12 the module was compiled _inside_ those images against one Node ABI, so an image on a different major than the pin reproduced the mismatch above in production rather than on a laptop — and the laptop at least gets a stack trace. (`better-sqlite3` 13 is N-API and no longer has an ABI to mismatch, which removes this exact failure, not the reason to keep the majors in step.) Eleven Dockerfiles name a node image (runtime, dev, and every E2E mock), which is exactly the count that makes hand-checking them unreliable.

Four rules keep the pin honest:

- **`.nvmrc` holds a version, never an alias.** `lts/*` resolves to a different major as the calendar moves and per machine — that is the drift, not a way to express a pin. A patch wildcard (`22.x`) is fine: the major is fixed, and a moving minor never moves the ABI.
- **`engines.node` is bounded above.** A bare `>=22` admits Node 25, which is the version that caused the incident above. The guard requires the exact `>=<major> <<major+1>` shape and prints the line to paste.
- **A workflow may name the version or read the file.** `node-version-file: .nvmrc` is the better spelling — it cannot drift, because it _is_ the pin — and the guard accepts it. Pointing it at any _other_ file creates a second pin and is rejected.
- **Bumping Node means bumping all four in one change.** That is the whole point; a bump in some of them is what the guard exists to catch.
- **`docs/` states its own floor, inside the same major.** It is a standalone package with its own lockfile, and astro 7 needs `>=22.22.0` — a floor the root's `>=22 <23` does not say. So `docs/package.json` carries `>=22.22.0 <23`, and the guard reads it too: a higher floor within the pinned major passes, a different major or an unbounded range fails. The floor itself is not pinned anywhere a version manager reads — `.nvmrc` says `22`, so `nvm use` happily picks an installed 22.20, and CI's `node-version: 22` resolves to whatever 22.x the runner's tool cache holds (22.23.3 on 2026-10-17). Both fail loudly, not silently: astro refuses to start below 22.22 and names the version it needs. `nvm install 22` fixes the local case.

The guard reads `FROM` lines only, never prose. These Dockerfiles explain their base image in a comment right above it (`# Pull node:22-slim via …`), so a text search for `node:` would read a stale comment as drift and a sentence as a pin.

`engine-strict` is deliberately **not** set: a mismatch is a pnpm warning, not a refused install. The goal is to make drift visible at install time, not to lock a contributor out of the repo over a minor.

## A Documented Fallback That Cannot Run Is Not A Fallback

Through `better-sqlite3` 12 the install script was one line — `prebuild-install || node-gyp rebuild --release`: download a prebuilt binary, or compile one when that download is unusable. On 2026-08-05 the download timed out in CI and the whole dev-stack build died on `gyp ERR! find Python - "" could not be run` (CI run 30994369292 on PR #1110): `Dockerfile.pinchy.dev` and both install stages of `Dockerfile.pinchy` had no toolchain, so the compile half could not run **at all**. Read the shape rather than the timeout: a transient network failure met a fallback that structurally did not exist, and a rerun heals that only for as long as the next download succeeds. The fix then was `python3 build-essential` in every image that installed the module (306 MB; in `Dockerfile.pinchy`'s `base` stage so it never reached `runtime`), plus a guard, `scripts/lib/native-build-toolchain.mjs`, that demanded the toolchain wherever a manifest declared a dependency in `pnpm.onlyBuiltDependencies`.

**`better-sqlite3` 13 removed the premise.** It is N-API, ships its prebuilds inside the npm package (`prebuilds/` for darwin, linux glibc and musl, win32; x64 and arm64), sets `gypfile: false` and has no install script. Nothing downloads, nothing compiles, so there is no fallback to keep alive. In the same change:

- `python3 build-essential` left `Dockerfile.pinchy` (`base`), `Dockerfile.pinchy.dev` and `Dockerfile.openclaw` (`builder`), and `better-sqlite3` left `pnpm.onlyBuiltDependencies` (the key is gone). Nothing else needs a compiler: `@napi-rs/canvas` ships per-platform optional packages, the other plugin bundles are pure JS, `koffi` and `tree-sitter-bash` ship prebuilds (see `pnpm.ignoredBuiltDependencies`), and the `llama-server` stage in `Dockerfile.openclaw` installs its own `cmake g++ make` on arm64 only.
- The guard was retired with its test. Its own self-check said so: with an empty `onlyBuiltDependencies` it demanded apt packages nothing could justify. A guard whose premise is gone is a check nobody can explain, and its 400 lines are not free to keep.

**If a compile-at-install dependency ever comes back**, the signals are different now and the lesson is the same: do not accept a build that needs a compiler and has none.

- In `Dockerfile.openclaw`, `--config.strict-dep-builds=true` fails the image build on any dependency install script that is on neither `onlyBuiltDependencies` nor `ignoredBuiltDependencies`. That is where a new native dependency stops, loudly.
- In `Dockerfile.pinchy` and `.dev` pnpm only warns ("Ignored build scripts"), so a bump whose `pnpm install` prints that box needs reading: allow the script in `pnpm.onlyBuiltDependencies` **and** put the toolchain back in every stage that installs it, or record the skip in `ignoredBuiltDependencies`.
- Reproduce, do not read: `npm_config_build_from_source=true` in front of the install is what a dead download looks like to an install script that has a source fallback. Measured on 2026-08-05 (with v12), that failed on `find Python` before the toolchain and compiled after it.

Verify a change to any of this by building the images (`docker build -f Dockerfile.pinchy --target prod-deps .`, `-f Dockerfile.pinchy.dev`, `-f Dockerfile.openclaw`) and loading the module inside the openclaw image (`node -e "new (require('better-sqlite3'))(':memory:')"` from `/opt/pinchy-files-deps`).
