# Releases And Version Numbers

Read this before editing `docs/src/content/docs/guides/upgrading.mdx`, any declared version (`package.json`, `.env.example`, the README quick start, `marketplace/`), or the release scripts. Part of the agent rules indexed in `AGENTS.md` § "Topic Rules".

## A Released Upgrade Section Is Immutable

`docs/src/content/docs/guides/upgrading.mdx` is cumulative: one `## Upgrading from vA to vB` section per release, newest first. Once vB ships, that section describes vB and nothing else.

It kept not staying that way, and the reason was structural rather than careless. `pnpm release` **froze** the current `%%PINCHY_VERSION%%` section and opened nothing in its place, so the next commit to write an upgrade note appended it to the end of the file — which is the frozen section of the release that already shipped. The note then claims behaviour that release does not have, and re-renders on docs.heypinchy.com under the wrong version. Measured on `main` on 2026-08-01 against `git show <tag>:…`, **seven** released sections had drifted since their tag, four of them by gaining a whole `####` note (#1028).

Nothing saw any of it. The two existing guards cover the neighbouring questions only: `upgrading-mdx-freshness.test.mjs` catches a stale `%%PINCHY_VERSION%%` placeholder, and `upgrade-prune-step.test.ts` (#370) checks the newest section shows `docker image prune`. Neither reads a frozen section's content.

Both halves are now closed:

- **The cause.** `openNextUpgradeSection` (`scripts/lib/release-logic.mjs`) opens the next cycle's section in the release run itself, so the first note after a release always has somewhere correct to land. The skeleton carries `### Breaking changes`, `### Upgrade notes` and the standard-flow bash block — not just headings, because the #370 guard reads the newest section and an empty skeleton would turn the branch red on every release. That completeness costs something: the skeleton satisfies `assertUpgradingSectionExists` by construction, so a release where nobody wrote notes would no longer fail the way it used to (no section at all). `assertUpgradeNotesWritten` is the replacement — it refuses to release a section still byte-identical to the template. Both read `buildNextUpgradeSkeleton`, so the writer and the gate cannot drift apart.
- **The tripwire.** `scripts/lib/upgrading-released-sections.mjs` (+ its test, `pnpm test:scripts`) compares every section whose `to` is a real tag against that section at the tag, and prints which `####` notes were added or removed.

**The skeleton commit lands _after_ `git tag`, deliberately.** The tagged tree is what the docs deploy builds, and `inject-version.sh` resolves every `%%PINCHY_VERSION%%` to the build version — so a skeleton inside the `chore: release vX.Y.Z` commit would publish an empty "Upgrading from vX.Y.Z to vX.Y.Z" section at the top of the live upgrade guide. The branch gets the open section; the tag does not.

Three details worth knowing before editing the guard:

- **A missing tag warns; _every_ tag missing fails in CI.** A guard that hard-fails on one unreadable tag fails on infrastructure instead of on content, so a shallow clone gets a `::warning::`. But zero-of-N is not a soft verdict, it is the guard passing on an empty comparison — and `validateCiWiring` structurally cannot catch it, because it reads what the YAML _says_ rather than what `git show` _answers_. So `emptyCorpusError` fails the run when nothing resolved and `CI` is set, and stays quiet locally where a `--depth=1 --no-tags` clone is a legitimate way to work. `ci.yml`'s `quality` checkout sets `fetch-tags: true` (depth 1 is enough — a shallow-fetched tag still carries its own tree, which is all `git show <tag>:<path>` reads) and `validateCiWiring` fails if that, or the label passthrough, is removed. Verify a change to either by reproduction: `git clone --depth=1 --no-tags` the branch, run the guard with and without `CI=1`, and watch it warn in one and fail in the other.
- **Authorizing an edit is the same contract as a test deletion, with one merge-queue caveat.** A genuine correction to a released section — the v0.5.0 compose snippet that did not work as documented (#281) is the real example — needs an `Allow-upgrade-note-edit: #NNN` commit trailer or the `allow-upgrade-note-edit` PR label. A bare reason is not enough. Deleting a stale `KNOWN_PRE_GUARD_DRIFT` entry is **not** authorizable that way: a verdict must not outlive its evidence. **Prefer the trailer**: a `merge_group` run carries no PR labels (`github.event.pull_request.labels` is empty there), so a label-only authorization is green on the PR and then rejected by the merge queue. The test-deletion guard sidesteps this by running `if: github.event_name == 'pull_request'`; this one lives inside `pnpm test:scripts` and must keep guarding main in the queue, so the failure message names the caveat instead.
- **The baseline is a snapshot, so a rebase can re-open it.** The fingerprints pin `main` as of the moment they were taken. Any commit to `upgrading.mdx` that lands first — including a legitimate one — invalidates the entry it touches, and the guard says so with the new fingerprint. That is the correct behaviour and it is a one-time cost: once this guard is on `main`, such a commit needs its own authorization instead.
- **`KNOWN_PRE_GUARD_DRIFT` pins a body, not a section.** The pre-guard drifts are accepted by sha256 of the exact accepted text, so those sections are not left open — the next edit to one of them fails like any other, and the failure prints the new fingerprint. Entries are classified: `retro-correction` (a legitimate fix that predates the trailer, e.g. the `git checkout` → `docker compose pull` rewrite across v0.2.0–v0.4.0) or `misplaced-note` (the bug itself, still to be moved — those must cite a tracking issue). **No `misplaced-note` entries remain**: the last two were moved into their real release under #1028, so a new one means the cause is back, not that there is bookkeeping to do.
- **Which release a misplaced note belongs to is measured, not read off the note.** #1028 named a release for each note it listed; on both that survived to be moved, the number was a guess the tree contradicts. `Integration audit event names` was filed as v0.5.5 — `integration.created` first appears in the tree at **v0.5.7**, and v0.5.4 through v0.5.6 do not contain it. `Deleting a user keeps their invite history` sat in v0.8.0's section beside a migration `0044` bullet, and `0044` does not exist at v0.8.0 (that tree stops at `0043`). Before moving a note, find the symbol it describes and ask `git tag --contains <commit>` and `git show <tag>:<path>` which release first has it. A note moved into the wrong section is the same defect wearing a different number.
- **A `## ` inside a code fence is not a section boundary — for every reader, not just the guard.** Upgrade notes quote markdown at people (v0.9.1's knowledge-base note shows an agent's `## Document Access` block), and a line-anchored `^## ` reads that as a heading, silently ending the section there. `maskFencedBlocks` in `scripts/lib/mdx-fences.mjs` is the one reading; the boundary is searched in the mask and the body is cut from the original, which is safe because the mask is length-preserving. Every function that cuts this file goes through it — `parseUpgradeSections`/`noteHeadings` in the guard, and `extractUpgradeNotes`, `finalizeUpgradeSection`, `assertUpgradingSectionExists`, `assertUpgradeNotesWritten`, `assertNoStaleUpgradeSections`, `openNextUpgradeSection`, `deriveStagingChecklist` in `release-logic.mjs`. What each one loses is different and none of it is loud: the guard compares a truncated section against one truncated at the same place (symmetric blindness reads exactly like agreement); `finalizeUpgradeSection` leaves `%%PINCHY_VERSION%%` unfrozen past the fence and `assertNoStaleUpgradeSections` — the guard for exactly that miss — cannot see it, the v0.5.8 bug returning through its own guard; and `extractUpgradeNotes` writes the GitHub Release body, so **v0.9.1 published with its notes ending at a dangling ` ```markdown `**, the remediation the note exists to give missing. One fixture in `release-logic.test.mjs` runs all of them, so a new reader written without masking fails there rather than in a release. `maskFencedBlocks` deliberately leaves an **unclosed** fence unmasked: CommonMark would run it to EOF, which here would delete every later section from the caller's view — silently, which is the failure mode being removed. Test any change with a fenced sample, not only with prose.

## Two Version Numbers, And Which Question Each Answers

The repo declares a version in six places, and until #1044 they were one number that `pnpm release` wrote in one commit. That held while every release was cut from `main`. **Release branches ended it**: both 0.9.x releases were cut from `release/0.9`, so `main` never took the bump and sat at `0.8.0` for three months while v0.9.1 was current. Measured 2026-08-04 — and it was not one wrong label, it was five, in ascending order of who it reached:

- `assertNoStaleUpgradeSections` had been quietly taught `max(package.json, frozen tags)` to survive it. A guard working around a broken premise instead of failing on it.
- `/api/version` reads `package.json#version` through `NEXT_PUBLIC_PINCHY_VERSION`. **Staging tracks `:next`, so it announced 0.8.0 for a build 400+ commits past it** — the instance you check to see whether your fix landed.
- `.env.example` said `PINCHY_VERSION=v0.8.0`. That line is not a label, it is the image tag a new install pulls.
- The 1-Click deploy templates (`marketplace/digitalocean/template.json`, `marketplace/caprover/pinchy.yml`) said `v0.8.0` too, on a **public marketplace**.
- **`README.md`'s quick start curled `docker-compose.yml` from the `v0.8.0` tag** — the most-read install instruction the repo has, run off the GitHub front page. This one is worth its own note, because it was missed by the first pass of #1044 _while that pass was enumerating exactly this category_, and only surfaced when the guard was pointed at it. A hand-written enumeration of "all the places" is the thing this section exists to stop; the fix is that the guard reads each place, not that the next list is longer.

So the number was split by the question it answers, and the split is the rule:

- **"What should I pull?"** → `.env.example`, the README quick start's **two** pins (the curl'd `docker-compose.yml` URL and the `PINCHY_VERSION=` line it writes into `.env`), and both marketplace templates. Always the newest **released** tag. A tag that does not exist is not installable, so these must never carry a development version.
- **"What is this tree?"** → root and `packages/web` `package.json`. The newest release at a release commit, `<next>-dev` at every other moment. A build 400 commits past v0.9.1 is not v0.9.1 and must not say it is.

`scripts/lib/version-identity.mjs` enforces both, and `version-identity.test.mjs` runs it against the real repo in `pnpm test:scripts`. A second guard reads the same six files from the other end: `main-version-pins.mjs`, run by the weekly `docs-freshness.yml` cron, flags a pin a **full minor** behind the latest published release. The two must agree on what a healthy tree looks like, and #1079 and #1044 arrived at opposite answers before this section existed — so `DECLARED_VERSION_PINS` in that module names the two `package.json` pins as the ones a `-dev` suffix is correct for, and skips them. A declared pin **without** the suffix still goes through the ordinary check: a bare version claims to be a release, so it has to be the current one, which is exactly the state that guard was built for. Details worth knowing before touching it:

- **The offline source of truth for "newest released tag" is `upgrading.mdx`'s newest frozen section** — not `git tag`. It is in the repo, needs no tags fetched (CI checkouts are shallow), and it is already what a release must update, so a release that forgets it fails here too.
- **`git describe` is the same mistake wearing a different name, and the release path made it.** `scripts/release.mjs` derived the previous release with `git describe --tags --abbrev=0` — the newest tag _reachable from HEAD_. That was right while every release was cut from `main`, and the release-branch model ended it: v0.9.0 and v0.9.1 were cut from `release/0.9`, which never merges back, so `main` answers **v0.8.0**. The upgrade-notes gate then looks for a `from v0.8.0` section, finds the frozen one, and aborts — `pnpm release 0.10.0` could not run from `main` at all. Worse than the abort is the near miss: had the section existed, `finalizeUpgradeSection` would have frozen a released section instead of the open one. Both `release.mjs` and `release-preflight.mjs` now read `newestFrozenRelease`, and `scripts/lib/release-prev-version.mjs` (+ its test, `pnpm test:scripts`) fails either file that goes back to a reachability-based derivation, or that stops reading the frozen section at all — both directions, because checking only the first would pass a file that derives nothing. It keeps string literals and strips comments, deliberately: the banned call **is** a string literal, so a stripper that blanked strings would report nothing and read exactly like a clean pass. Verify a change to it by canary — put `git describe --tags` back in either file and watch the guard name that file and line.
- **`-dev` is the only accepted suffix.** Not `-rc.1`, not `-alpha`, not `+dev`. Otherwise "is this a development tree?" becomes a semver-precedence question in every consumer; it is meant to be a string check.
- **`compareVersions` was hardened in the same change and this is load-bearing.** It used to `.split(".").map(Number)`, so `"0.10.0-dev"` became `[0, 10, NaN]` and every NaN comparison is false — it fell through and returned **0**. Introducing a suffixed version against a comparator with a silent "equal" in it would have made the new guard answer "consistent" for the exact state it exists to catch. It throws now.
- **A development tree must fail the release build gate.** `assert-package-version.mjs` compares `package.json` against the tag before any image is pushed, and a `-dev` tree can never match. That is correct, not a limitation — it is why that script grew a `--root` flag so its passing case can be tested against a fixture.
- **`docs/scripts/inject-version.sh` stopped reading `package.json` for its fallback**, and reads `upgrading.mdx`'s newest frozen release instead (`docs/scripts/newest-released-version.mjs`). `%%PINCHY_VERSION%%` goes into `docker pull` lines and `raw.githubusercontent` URLs, so it needs the _other_ question's answer — a tag that exists. The first shape of this **refused** a `-dev` version instead, on the reasoning that both real callers pass the version explicitly (`release.yml` from the tag, `docs.yml` as a required input) and anything else is a hand-built run. That enumeration was one short, in exactly the way this section is about: **CI's `quality` job runs `cd docs && pnpm build` on every PR** and passes no version, so the refusal turned a required check red on every PR — caught by reproduction, not by reading. A fallback on a path that publishes nothing must resolve; the `-dev` number is what must not reach a reader.
- **The marketplace templates are checked one hop away, on purpose.** `marketplace-version.test.mjs` already pins both to `.env.example` against the real files, so `version-identity` checks `.env.example` and inherits them. Re-checking them here would create a second place to keep in sync — the failure this whole section is about. The README is read **directly, and both its pins are**, because the hop that exists there does not carry the same claim: `readme-quickstart-gate.mjs` checks the two pins agree with _each other_, not that either agrees with the newest release. Reading only the URL and leaning on that agreement would pass a README installing one release's compose topology with another's images — silent by construction, since the reader's install succeeds.

**After cutting a release from a release branch, set `main` to `<next>-dev` and pull `.env.example`, both README quick-start pins and both marketplace templates up to the tag you just shipped.** That is the step whose absence caused all of this; the guard now fails a PR instead of letting it run for three months.

**`pnpm release` opens the next `-dev` version itself.** Its post-tag commit — the one that opens the next upgrade-notes section — also sets both `package.json` files to `nextDevVersion` (`scripts/lib/release-logic.mjs`): `X.Y.(Z+1)-dev` on `release/X.Y`, `X.(Y+1).0-dev` on `main`, because a release branch hosts only patches of its minor and trunk becomes the next minor. Until #1372 it left both at the release, so the branch it ran on stayed non-dev and every backport after it went red; that was fixed by hand after v0.10.0, v0.10.1 and v0.10.2. The install pins stay on the tag in that commit — a `-dev` version is not pullable. `nextDevVersion` also refuses a version that does not belong on the branch (0.11.0 from `release/0.10`), and both `release.mjs` and the preflight call it before anything is written. The tripwire for a tree that still declares a bare release after its release commit is `assert-package-version.test.mjs`'s "CLI exits 1 on a development tree" — it fails on any branch, so `version-identity`'s `order === 0` silence no longer hides a main cut.
