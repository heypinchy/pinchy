The [Audit Trail](/concepts/audit-trail/) reference explains **what** Pinchy logs. This page explains **how** that log defends itself against tampering — and, just as importantly, how you can check that defense yourself instead of taking our word for it.

We wrote this page because "trust us, it's signed" is not a security property. A tamper-evident log is only worth something if the people relying on it can independently confirm it hasn't been touched. So everything below is verifiable by you, from the admin UI or the API, against the same cryptographic evidence stored in your own database.

A note on wording we hold ourselves to: the audit trail is **tamper-evident**, not tamper-proof. Nothing here prevents a sufficiently privileged attacker from changing rows. What it does is make any change — an edited field, a deleted row, a reordered history — **detectable**. The difference between prevention and detection matters, and we cover exactly where that line sits in [The threat model, honestly](#the-threat-model-honestly) below.

## Two layers, two jobs

Pinchy protects the audit log with two independent mechanisms that catch different attacks:

1. **A per-row HMAC signature** catches a change to the _contents_ of a row — someone edits a field in an existing entry.
2. **A hash chain linking each row to its predecessor** catches a change to the _shape_ of the log — someone deletes a row from the middle, truncates the tail, or reorders history.

Neither alone is enough. A per-row signature says "this row is unchanged" but says nothing about whether the row _next to it_ was quietly deleted. The chain closes that gap. Together they make the whole log tamper-evident, not just each row in isolation.

Underneath both sits a third layer that isn't cryptographic at all: the database itself refuses to modify or delete audit rows. That's the append-only guard, and we cover it in [The append-only guard](#the-append-only-guard).

## Per-row HMAC signatures

When an audit event occurs, Pinchy builds a **canonical serialization** of the row's meaningful fields — timestamp, event type, actor type and id, resource, the structured `detail` payload, outcome, and error — and signs it with **HMAC-SHA256** using a server-side secret. The result is stored in the row's `row_hmac` column.

Canonical means deterministic: the same logical row always serializes to the exact same bytes, so the signature is reproducible. Anyone holding the HMAC secret can re-derive the expected signature for a row and compare it against the stored one. If a single character of any signed field was changed after the fact, the recomputed signature won't match — and the row is flagged as invalid.

The HMAC secret is auto-generated on first start if you don't set one. For multi-instance deployments you should set `AUDIT_HMAC_SECRET` explicitly so every instance signs and verifies against the same key — see [Multi-instance deployments](/concepts/audit-trail/#multi-instance-deployments) in the reference.

## The hash chain

A per-row signature has a blind spot: it proves each surviving row is intact, but it can't see a row that's no longer there. Delete entry #5000 entirely and every remaining row still verifies perfectly on its own. That's the gap the chain closes.

Each row's signature also folds in the **previous row's signature**. Concretely, before Pinchy signs a row it includes the predecessor's `row_hmac` in the canonical payload, and it stores that predecessor value in the row's `prev_hmac` column. Every row is therefore cryptographically bound to the one before it, forming a chain back to the very first row — the genesis row, which has no predecessor.

Because each link depends on the row before it, changing the _sequence_ breaks the chain even when every individual row is untouched:

- **Deleting a row from the middle** leaves a gap — the next row's `prev_hmac` no longer matches the signature of the row that now precedes it.
- **Truncating the tail** removes the most recent links; verification of a known range detects the missing continuation.
- **Reordering rows** puts a `prev_hmac` next to the wrong predecessor.

Verification reports these two failure modes **separately**, because they mean different things:

- `invalidIds` — rows whose own signature doesn't recompute. A field inside the row was changed.
- `chainBreakIds` — rows whose own signature is fine, but whose chain link no longer points at the correct predecessor. A neighbouring row was deleted, or rows were reordered.

Keeping them distinct tells you not just _that_ something is wrong but _what kind_ of tampering happened, which is exactly what an investigation needs first.

### Rows signed with an earlier secret

There's a third bucket, and it is deliberately not a failure:

- `previousKeyIds` — rows whose signature recomputes under the secret this instance **used to** sign with, rather than the current one.

This is what a changed `AUDIT_HMAC_SECRET` looks like. Change the variable, or pin it on an install that had been running on the key Pinchy generated, and every entry written earlier carries the old signature. Recomputing those under the new key alone would mismatch on all of them — and reporting a key change as "the entire history was tampered with" is worse than useless during an investigation.

So Pinchy keeps looking at the key it superseded. That key stays in the key file in the `pinchy-secrets` volume; rows that verify against it are authentic and unmodified, and they're listed on their own instead of being folded into the healthy rows, so a rotation stays visible to whoever reads the report. `valid` stays true, because nothing was tampered with.

The earlier key is only accepted for the **opening stretch** of the log, the rows that pre-date the key change. Pinchy keeps no record of when that change happened, so verification infers it: the first row that verifies under the current key marks the change, and every row after it has to verify under the current key too. A later row that only verifies under the earlier key goes into `invalidIds`, not `previousKeyIds`, and `valid` turns false. The background check carries the rule across its runs: its checkpoint tells it the change has already happened. Without the rule, anyone holding the earlier key could rewrite rows written after the change and still get a clean report.

The rule rests on one precondition: once a row is signed with the current key, no row is ever signed with the earlier one again. A single instance meets that on its own, as long as the key only moves forward. Switching back to the earlier key and later forward again breaks it on a single instance too, see [Switching back to the earlier key](#switching-back-to-the-earlier-key). Several instances sharing one database meet it only if they switch together, see [Switching the key on several instances](#switching-the-key-on-several-instances).

The hash chain is untouched by any of this. Each row stores its predecessor's signature verbatim, whichever key produced that signature, so the links still match straight across the point where the key changed.

What the rule doesn't do is make a leaked earlier key harmless. Someone holding it can still forge rows in the opening stretch. And because the change point is inferred, they could get a clean full verification by re-signing every row from that point to the newest one, so that no current-key row is left to mark the change. The background check catches that as a break against the checkpoint it stored, as long as the checkpoint, which lives in the same database, wasn't rewritten as well. What actually closes the door is removing the earlier key.

The background check can only do that for rows it has already seen under the current key. Right after the key change, its checkpoint is still the last row signed with the earlier key, so for the next run the change hasn't happened yet. Rows written after the change but before the first background run that covers them aren't protected against the earlier key: someone holding it, with write access to the database, could re-sign all of them up to the newest one, and both the background check and a full verification would report them as signed with an earlier secret. The first run starts about 60 seconds after Pinchy starts and the next ones every 6 hours (`AUDIT_VERIFY_INTERVAL_MS`). A run that finds no new rows leaves the checkpoint where it is, so on a quiet instance the window stays open until a run finds rows written after the change. Removing the earlier key file closes it too.

So once nothing signed with the earlier key still needs verifying, or as soon as you can after a **leak**, remove the earlier key file. When you remove it matters, see [Retiring the earlier key](#retiring-the-earlier-key).

Two limits worth stating plainly. Pinchy checks against one earlier key, and that's always the key file, never an earlier value of the variable. Change the variable a second time without retiring the earlier key first, and the value you replaced is gone: the rows signed with it, between the first change and the second, verify under no key, and the background check records a failure for the ones it hadn't reached yet (see [Retiring the earlier key](#retiring-the-earlier-key)). And if you overwrite the key file yourself, the key it held is gone and the rows it signed can no longer be verified by anyone. [Switching the key](#switching-the-key) avoids both.

#### Switching the key

This is the procedure for changing `AUDIT_HMAC_SECRET`, whether you just want to hold the key yourself or the old one leaked. The other pages that mention a key switch link here.

**Before you switch, make sure the current key is in the key file.** After the switch, the earlier key Pinchy checks against is the file `.audit_hmac_secret` in the `pinchy-secrets` volume (`/app/secrets/.audit_hmac_secret` inside the container). Pinchy keeps that file filled on its own: when `AUDIT_HMAC_SECRET` is set and there's no key file yet, it writes the variable's value there at start and logs `Wrote the AUDIT_HMAC_SECRET value to .audit_hmac_secret`. It never overwrites a file that's already there. So the current key is in the file if you never set the variable (the file is the key Pinchy generated), or if Pinchy has started on the current value at least once since the file was last removed.

All of this holds only as long as `/app/secrets` is persistent storage you back up. The stock `docker-compose.yml` mounts the `pinchy-secrets` volume there. If you run Pinchy another way, mount a persistent, backed-up volume at `/app/secrets` yourself: a directory that disappears when the container is recreated takes the key file with it, and with it the earlier key your older entries verify against.

Four cases need a step first:

- **The variable is set, and the instance hasn't started on a Pinchy version that writes the file yet.** Upgrade and start it once on the current value before you switch. If it logs `Could not write the AUDIT_HMAC_SECRET value` instead, fix what the code in brackets names and start it again: `EACCES` is the volume's permissions (Pinchy runs as uid 999), `ENOSPC` a full disk, `EROFS` a read-only mount. A volume without hard links, such as exFAT or some network shares, isn't one of them: Pinchy then creates the file directly.
- **Pinchy logs `.audit_hmac_secret in the secrets volume is not a valid key`.** The file is there but doesn't hold a key (it's empty, or not 64 hex characters), and Pinchy never overwrites it, so the current value isn't saved anywhere. Move the file out of the volume, keeping it in case it's what's left of a key you still need, and restart Pinchy. It writes the current value into a new file and logs `Wrote the AUDIT_HMAC_SECRET value`.
- **Pinchy logs `Could not read .audit_hmac_secret in the secrets volume`.** The file is there, but Pinchy can't open it, and the code in brackets says why. Don't move this one aside: it may be the earlier key, for example one restored from a backup as root. With `EACCES`, check the file's owner and permissions: Pinchy runs as uid 999 and has to be able to read it, so give it to that user with `docker compose exec -u root pinchy chown 999:999 /app/secrets/.audit_hmac_secret`. With `EISDIR`, there's a directory where the file should be. Then restart Pinchy. Once it can read the file, it either holds the current value and there's nothing more to do, or it holds an earlier key, the next case.
- **The key file holds an even older key from an earlier switch.** Pinchy says so on every start (`AUDIT_HMAC_SECRET is set and differs from the audit signing key`). It keeps one earlier key, so the value you're about to replace would have nowhere to go. [Retire the older key](#retiring-the-earlier-key) first; on the start after that, Pinchy writes the current value into the file.

Then switch:

1. Back up the `pinchy-secrets` volume.
2. Generate the new key with `openssl rand -hex 32`, set it as `AUDIT_HMAC_SECRET` in `.env`, and keep a copy somewhere safe.
3. Restart Pinchy (`docker compose up -d`). From now on it logs a notice on every start saying the variable differs from the key file. That's expected: the file is now the earlier key. If it logs `AUDIT_HMAC_SECRET is set but is not a valid key` instead, the new value isn't 64 hex characters, so Pinchy ignores it and keeps signing with the key file. Fix the value and restart again.

Several instances against one database have to switch together, see [Switching the key on several instances](#switching-the-key-on-several-instances). If the old key leaked, retire it afterwards, below.

#### Retiring the earlier key

Once the key file is gone, Pinchy has no earlier key to check against, so every row signed with it reports in `invalidIds` and `valid` stays false. That is the price of closing the door: those rows can't be told apart from tampered ones any more. Keep the file in an offline backup first if you want to be able to re-verify the old history later.

When you remove it matters. Each background run verifies the rows written since the run before it. Until the first run under the new key has gone through, some of those were signed with the earlier key: everything written between the last run and the restart, up to 6 hours of entries. If the file is gone by the time the run reaches them, they verify under no key and the run records a failure. So retire the key in this order:

1. [Switch to the new key](#switching-the-key) with the key file still in place.
2. Right after the restart, do something that writes an audit entry, for example sign out and back in, and note its id: the sign-in is the first entry in `GET /api/audit?eventType=auth.login&limit=1`. Then wait until `GET /api/audit/verify/status` (see [Checking the job's own health](#checking-the-jobs-own-health)) shows a `lastVerifiedId` at least that id, with `lastStatus` `"ok"`. That's the background check saying it has verified everything up to your entry. The first background run starts about 60 seconds after the start and usually covers it. It doesn't if your entry lands while that run is still working: the run then stops short of everything written in the meantime, and your entry waits for the next run, up to 6 hours later. Go by the id, not by `lastRunAt`. A run that stops short like that still moves `lastRunAt` past your entry, a run that finds no new rows leaves it where it is, and a run that failed leaves it unchanged too. If Pinchy's logs show `[audit-verify-job] sweep failed`, stop here and keep the key file until a run goes through.
3. Make sure the variable is the key Pinchy signs with. In Pinchy's log from its latest start (`docker compose logs pinchy`), look for the notice `AUDIT_HMAC_SECRET is set and differs from the audit signing key`, and make sure there's no warning `AUDIT_HMAC_SECRET is set but is not a valid key`. The notice is Pinchy saying the variable is in effect and the file holds the earlier key. If it's missing, don't remove the file. Either the variable isn't in effect, and then the file is the key Pinchy signs with: remove it and the next audit entry makes Pinchy generate a new random key in its place. Or the file already holds the current value, and there's no earlier key to retire. If the warning is there, fix the value, restart, and check again.
4. Back up the key file, remove it from the volume, and restart Pinchy (`docker compose restart pinchy`). On that start Pinchy writes the current `AUDIT_HMAC_SECRET` value into a new key file and logs `Wrote the AUDIT_HMAC_SECRET value to .audit_hmac_secret`, so it's in place as the earlier key for the next switch.

On several instances, do steps 3 and 4 on each of them. They all sign with the new key by then, so one after another is fine.

Lose a key while the background check still has rows signed with it ahead of it, and the failure entry it records can't be cleared. That happens in two ways:

- The key file is removed before the first background run under the new key.
- `AUDIT_HMAC_SECRET` changes a second time while the key file still holds the key from before the first change. The value you replaced is gone at once, and the rows it signed since the last background run verify under no key.

As with a rolling restart (below), there's no reset, on purpose. Write down what happened, with timestamps, wherever you keep records for auditors: when the key was lost (the file removed or the restart on the new value) and when the background run before that finished (the `audit.integrity_check` entry before the failure). Every flagged row should fall between those two points. One outside them deserves a proper look.

**After a leak, the order is a trade-off.** Until a background run has gone through rows written after the switch, the leaked key is still accepted for them: someone holding it, with write access to your database, could re-sign those rows and get them past both the background check and a full verification. So write the audit entry from step 2 right after the restart, within the first minute: the first run starts about 60 seconds after Pinchy starts, and an entry written before then is usually covered by it, which closes the window. Usually, not always, so don't assume it. Only step 2's check tells you the window is closed: until `lastVerifiedId` reaches your entry with `lastStatus` `"ok"`, it's still open. An entry written after the first run has started, or one the run stopped short of, waits for the next run, and so does the window: the leaked key stays accepted for rows written after the switch until a run finds them, up to one interval later (6 hours by default, `AUDIT_VERIFY_INTERVAL_MS`). Retiring the key in the same stop as the switch leaves no window at all: stop Pinchy, back up and remove the key file, set the new value, start. Then check that start's log for `Wrote the AUDIT_HMAC_SECRET value to .audit_hmac_secret`. If it shows `AUDIT_HMAC_SECRET is set but is not a valid key` instead, the new value isn't in effect and Pinchy is signing with a key it just generated: fix the value before anything else. That costs you the failure entry above for the rows signed with the leaked key since the last background run. The key alone does nothing without write access to the database, so for most leaks the short window is the smaller risk. If you have reason to think someone holds both right now, retire it in the same stop and document why.

#### Switching back to the earlier key

If the key changed by accident, for example because an `AUDIT_HMAC_SECRET` line left in `.env` took effect on an upgrade, switching back isn't a free undo. The earlier key Pinchy checks against is always the key file, so once the file key is active again, the rows signed with the variable's value in the meantime verify under no key. A full verification reports them in `invalidIds`, and if the background check hadn't reached them yet, it records a failure as described above.

Switching forward again later makes it worse. Pin the same value again and the log reads: earlier key, new key, earlier key, new key. The rows in the third stretch are earlier-key rows after a new-key row, which is exactly what a forgery looks like, so a full verification reports them as invalid on every run, on a single instance too.

So keeping the new key is usually the safer choice: back it up and treat it as yours from then on. If you do switch back, remove the line from `.env` and stay on the key in the file for good. The clean moment is before the restart that would switch the key, when nothing has been signed with the new value yet. Removing the line only switches anything while the file holds a different key: once Pinchy has written the variable's value into the file, the key stays the same without the variable.

#### Switching the key on several instances

If several Pinchy instances share one database, switch the key on all of them at once. Each instance checks against the key file it sees, usually the one in its own `pinchy-secrets` volume, so [the check before a switch](#switching-the-key) applies to every one of them.

1. Make sure every instance has the current key in its key file.
2. Back up every instance's `pinchy-secrets` volume.
3. Stop every instance.
4. Set the new `AUDIT_HMAC_SECRET` on each.
5. Start them again.

Skip step 1 on an instance and the rows it signed with the current value become unverifiable. A full verification reports them in `invalidIds`, and the first background run records a failure entry for the ones it hadn't reached yet, which can't be cleared. [Retiring the earlier key](#retiring-the-earlier-key) says what to write down for your auditors if that happens.

A rolling restart breaks the precondition above. For as long as some instances sign with the new key and others still with the old one, their rows interleave: old, new, old. Pinchy can't tell an old-key row written after the change by an instance that hadn't restarted yet from one forged with a leaked key, so it treats both the same way.

If that has already happened, this is what you'll see:

- Verification lists the old-key rows written after the first new-key row in `invalidIds`, and `valid` is false. A full verification reports them on every run, because the rows never change.
- The background check writes an `audit.integrity_check` entry with `outcome: "failure"` that names those rows, and emits `audit_integrity_violation` on stderr. From then on `GET /api/audit/verify/status` shows a `lastViolationAt`.

There's no reset for this, on purpose: the failure entry is part of the append-only log, and a way to clear it would clear a real alarm just as easily. What you can do is explain it. Check that every flagged row was written during the restart, between the first instance starting on the new key and the last one stopping on the old, and write that down with your deployment's timestamps wherever you keep records for auditors. The log shows the violation; your record shows why it's benign. A flagged row outside that window is a different story and deserves a proper look.

:::note[Rows written before the chain existed]
Entries created before the hash chain was introduced keep their original per-row signatures and stay verifiable under them. The chain binds forward from the point it was introduced — older rows are checked for content integrity but aren't chain-checked against a predecessor they never recorded. This is expected, not an integrity failure.
:::

## The append-only guard

The HMAC chain makes tampering _detectable_. The database makes the most common tampering _fail outright_.

The `audit_log` table carries PostgreSQL triggers that reject every attempt to change it:

- A `BEFORE UPDATE` trigger raises an exception — no row can be edited.
- A `BEFORE DELETE` trigger raises an exception — no row can be removed.
- A `BEFORE TRUNCATE` statement-level trigger raises an exception — the whole table can't be wiped in one shot. (`TRUNCATE` is a statement-level operation in Postgres, so the row-level `UPDATE`/`DELETE` triggers don't fire for it — it needs its own guard.)

This is enforced by the database, not by application code, so it holds even against direct SQL. The application role Pinchy connects with cannot disable these triggers; only a database **superuser** can. That's the boundary: append-only is guaranteed against anyone operating with Pinchy's own credentials, and against ordinary database access. It is not a guarantee against someone who already holds superuser on your Postgres — see the threat model below.

We describe this as **append-only, database-enforced**. We deliberately don't call the log "immutable" without that qualifier, because the honest scope is "the application and normal database access cannot change it," not "no one in any circumstance can."

## Verify it yourself

You don't have to trust that any of the above is working. You can run the exact same verification Pinchy runs internally, on demand, and read the result.

### On demand, via the API

`GET /api/audit/verify` (admin only) walks the log, recomputes every row signature and every chain link, and returns a structured result:

```bash
curl -b session_cookie https://your-pinchy-instance/api/audit/verify
```

```json
{
  "valid": true,
  "totalChecked": 14203,
  "invalidIds": [],
  "chainBreakIds": [],
  "previousKeyIds": []
}
```

`valid` is `true` only when both `invalidIds` and `chainBreakIds` are empty. If tampering is present, `valid` is `false` and the two arrays tell you which rows failed and how — `invalidIds` for changed content, `chainBreakIds` for deletion or reordering, as described above. `previousKeyIds` lists the rows signed with an earlier secret (see [Rows signed with an earlier secret](#rows-signed-with-an-earlier-secret)) and doesn't affect `valid`.

Optional `fromId` and `toId` query parameters restrict verification to a range of row ids, which is useful for spot-checking a window without scanning the entire table. The scan is memory-bounded, so verifying a large log won't strain the process.

The same check is available in the admin UI: open the **Audit** page and click **Verify Integrity**.

### Continuously, via the verify cron

On-demand verification is only run when someone remembers to run it. So Pinchy also runs the _same_ check continuously in the background.

A periodic verify job re-verifies newly written rows against the chain and raises an alarm the moment it finds a break — you don't have to be watching for it. The alarm is itself an audit event: `audit.integrity_check`.

- On a clean sweep it writes `audit.integrity_check` with `outcome: "success"`.
- On a detected break it writes `audit.integrity_check` with `outcome: "failure"`, and the `detail` carries structured findings — `invalidCount`, `chainBreakCount`, and the offending `invalidIds` / `chainBreakIds` (capped so the row stays within the audit-detail size budget).

Because the alarm is a first-class audit event, you can wire your normal audit monitoring to it: filter the log for `eventType=audit.integrity_check` with a failure outcome, or route those rows to your SIEM, and you have a standing tamper alarm without any extra plumbing. The actor is the system job (`audit-verify-job`), and each sweep records the id range it covered so you can confirm coverage.

### Checking the job's own health

If you'd rather ask than watch, `GET /api/audit/verify/status` (admin only) answers directly — how far the job has verified, when it last got there, whether the last sweep was clean, and whether a violation was ever recorded:

```bash
curl -b session_cookie https://your-pinchy-instance/api/audit/verify/status
```

```json
{
  "lastStatus": "ok",
  "lastVerifiedId": 4821,
  "lastRunAt": "2026-07-28T09:14:02.417Z",
  "lastViolationAt": null
}
```

Every field is read back out of the database, so a restart can't quietly reset the answer. Read both status fields: `lastStatus` covers the most recent sweep only — the job deliberately moves past a tampered range instead of re-alarming on it every cycle, so a later sweep over intact rows reports `ok` again — while `lastViolationAt` comes from the append-only failure entries and is never cleared.

One thing `lastRunAt` is not: a heartbeat. When a sweep finds nothing new to verify it leaves the checkpoint alone, so a quiet instance shows a timestamp hours old while the job runs exactly on schedule.

We keep this behind admin authentication on purpose. It is not part of the public `/api/health` endpoint your container runtime polls, because telling an anonymous caller that tampering was detected also tells the attacker they were noticed.

## Personal data is redacted at write time

Verifiability and privacy pull in opposite directions: a tamper-evident log is one you _can't_ go back and scrub, but privacy law expects personal data to be erasable. Pinchy resolves this by keeping the identifying data out of the signed row in the first place, so there's never anything to scrub.

Two things happen **before** a row is signed:

- **Email addresses** are never stored as plaintext. Where an event needs to identify an address, Pinchy stores a keyed HMAC of it (so an admin holding a known address can match it, but a leaked log doesn't yield addresses back) plus a short masked preview for human recognition. See [Email addresses](/concepts/audit-trail/#email-addresses-gdpr-art-17) in the reference.
- **User identity** is recorded as a per-user pseudonym rather than the raw user id, again folded into the row before signing so the chain covers it consistently.

Because the pseudonym-to-person mapping lives on the user's own (mutable) record, **deleting a user removes that mapping** while every audit row they generated stays exactly where it is, still signed, still chained. What happened and when remains intact and verifiable; who did it becomes an opaque token that nothing in the database can resolve back to a person. This is the standard **crypto-erasure** (crypto-shredding) pattern for append-only logs — you erase the key to the data rather than the data itself.

The design consequence is deliberate: the audit trail survives a right-to-erasure request structurally intact and still passes verification. Erasure changes _who a row can be linked to_, not _whether the row is authentic_.

:::caution[Not legal advice]
This describes a design stance, not a legal opinion. Whether crypto-erasure satisfies a specific obligation for your organization is a question for your Data Protection Officer or counsel. We're documenting the mechanism so your DPO can assess it — not asserting a compliance outcome on your behalf.
:::

## The threat model, honestly

It's worth being precise about what this system does and does not promise, because a security control you misunderstand is worse than one you don't have.

**What the chain detects.** Any tampering that touches the signed data or the sequence:

- editing a field in an existing row (`invalidIds`),
- deleting a row from the middle (`chainBreakIds`),
- reordering rows (`chainBreakIds`),
- truncating the tail — the missing continuation shows up when you verify a range whose end you know.

**What it gives you: detection, not prevention.** The cryptography can't stop a write; it can only make the write conspicuous when you check. The append-only database triggers _do_ prevent the common cases (edits and deletes through Pinchy's own role, or ordinary SQL), but they too can be disabled by a database superuser.

**The root-of-trust caveat.** The signatures are only as trustworthy as the secret that produces them. An attacker who holds **both** database superuser (to disable the triggers and rewrite rows) **and** the HMAC secret (to re-sign the rewritten rows and rebuild a consistent chain) could, in principle, forge a clean-looking history. Detection assumes the attacker doesn't control the signing key. This isn't a Pinchy-specific limitation — it's inherent to any log that signs itself with a key held in the same trust domain it's protecting.

**Where we're headed.** The roadmap answer to that caveat is **external anchoring**: periodically publishing the chain head (the latest row signature) into a second, independent trust domain — an append-only store the Pinchy host can't rewrite. Once the chain head is anchored externally, an attacker who forges local history still can't match the externally recorded head, so even a superuser-plus-key compromise becomes detectable. Until that ships, treat the guarantee as: strong detection against everything short of a full compromise of both the database and the signing key.
