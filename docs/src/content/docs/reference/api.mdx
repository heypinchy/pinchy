All API endpoints require authentication unless noted otherwise. Unauthenticated requests receive a `401 Unauthorized` response. Authenticate by including a valid session cookie (set during login via the web UI).

Some endpoints are **admin only** — non-admin users receive a `403 Forbidden` response.

## WebSocket (Chat)

Agent chat is handled over WebSocket at `/api/ws`, not via REST. The browser sends JSON messages and receives streaming responses. For details on the WebSocket protocol, message types, and session management, see the [Architecture](/architecture/#request-flow) page.

## Health

### `GET /api/health`

Service health check. **Public — no authentication required.** Suitable for load-balancer probes and uptime monitoring.

**Response:** `200 OK` whenever the Pinchy web process is running.

```json
{
  "status": "ok",
  "secrets": {
    "encryption_key": "envvar",
    "auth_secret": "envvar",
    "audit_hmac_secret": "envvar",
    "db_password": "default"
  },
  "openclaw": { "connected": true },
  "configRegeneration": { "ok": true },
  "disk": {
    "status": "ok",
    "volumes": [
      {
        "name": "system",
        "status": "ok",
        "freeGb": 61,
        "totalGb": 100,
        "freePercent": 61
      },
      {
        "name": "workspaces",
        "status": "ok",
        "freeGb": 61,
        "totalGb": 100,
        "freePercent": 61
      },
      {
        "name": "knowledgeBaseArtifacts",
        "status": "ok",
        "freeGb": 61,
        "totalGb": 100,
        "freePercent": 61
      },
      {
        "name": "data",
        "status": "ok",
        "freeGb": 61,
        "totalGb": 100,
        "freePercent": 61
      }
    ]
  }
}
```

`openclaw.connected` reflects whether the web process currently has a live WebSocket connection to the OpenClaw gateway — the dependency chat relies on. Top-level `status` deliberately stays `"ok"` even when `openclaw.connected` is `false`: brief disconnects during OpenClaw restarts (for example while applying a config change) are expected and self-heal, and flipping `status` would make the Docker healthcheck restart-loop the container during normal operation. Monitor `openclaw.connected` directly (or poll `/api/health/openclaw`) if you need alerting on gateway reachability specifically.

`configRegeneration` reports the outcome of the most recent boot-time OpenClaw config regeneration. It is `{ "ok": true }` in normal operation. When a startup regeneration fails — most commonly because an image-only upgrade dropped the `openclaw-secrets` volume (see [Upgrading Pinchy](/guides/upgrading/)) — it becomes `{ "ok": false, "error": "<actionable message>", "at": "<ISO timestamp>" }`. This is the one signal that catches a **frozen config**: Pinchy still marks itself healthy so the OpenClaw container can start and hot-reload a fixed config later, so `status` stays `"ok"` and `openclaw.connected` can be `true` while new providers, agents, and model changes silently never take effect. `error` carries operator guidance only — never secret material. Alert on `configRegeneration.ok == false`. A later successful regeneration (for example after you fix the compose file and restart) clears it back to `{ "ok": true }`.

`disk` reports the free space where Pinchy writes, by role rather than by path: `system` is the container's own filesystem, which sits on Docker's storage (where pulled images land and temporary files are written); `workspaces` holds agent files and chat uploads; `knowledgeBaseArtifacts` holds the PDFs the knowledge base converts Office documents into; `data` is the `/data` mount agents read from. On a default install they all share one disk, so the numbers repeat. A volume is `"warning"` below 15 GB free, and `disk.status` is `"warning"` if any volume is. Numbers are whole gigabytes (10⁹ bytes), rounded down for `freeGb` and `freePercent`, so a reported value never sits above the line it is compared to. A location that can't be measured — missing on this machine, or not answering within a second — is left out, and if none can be measured `disk` is `{ "status": "unknown", "volumes": [] }`. The database volume isn't mounted in the Pinchy container and isn't measured. Like `openclaw.connected`, a disk warning leaves top-level `status` at `"ok"` and the response at `200`, so the Docker healthcheck never restarts a container over it. Alert on `disk.status == "warning"`; [Disk space](/guides/hardening/#disk-space) explains the threshold and what to free up.

### `GET /api/version`

Which build is running. **Public — no authentication required**, and exempt from Domain Lock, so upgrade verification and monitoring work from any host.

```json
{
  "pinchyVersion": "v0.9.0",
  "openclawVersion": "2026.6.1",
  "build": "086161f92bc1",
  "nodeEnv": "production"
}
```

This is the endpoint to check after an upgrade: it answers what the container actually is, not what the compose file asked for.

### `GET /api/diagnostics`

Database and OpenClaw reachability, plus the running version. **Public**, but the session is inspected: authenticated **admins** additionally get a `logs` field with recent server logs (redacted of email addresses and known secret patterns). Nobody else gets that field — the log buffer is process-global and can carry detail from other users' sessions.

A signed-in non-admin also gets `"logsWithheld": "admin-only"`. It lets a client tell "your role may not read these" apart from "there are none": the in-app bug reporter uses it to ask the reporter to forward their report to an administrator, rather than pointing them at a host shell they have no account on. Anonymous callers never get the field: with no session there is no role to withhold for, and that caller may be the setup wizard's pre-flight check — run by whoever is installing Pinchy, who does hold the host shell. Nothing in the request separates that person from a signed-out member, so the bug reporter's fallback names the host command and the administrator both.

### `GET /api/health/openclaw`

OpenClaw gateway reachability check. **Public — no authentication required**, except the `?channelHealth=1` mode described below, which requires an admin session.

Useful for monitoring the WebSocket gateway separately from the web process.

**Response:**

```json
{
  "status": "ok",
  "connected": true,
  "configPushesPending": 0
}
```

`configPushesPending` is the number of configuration updates Pinchy has accepted but not yet confirmed inside the OpenClaw runtime (for example while OpenClaw's config-apply rate limit defers an update). A value of `0` means the runtime reflects every change you've made — useful for automation that needs to act right after a settings or permission change. While the gateway restarts, the response is `{ "status": "restarting", "connected": false, "since": <timestamp> }` instead.

With `?agentId=<uuid>`, the response additionally includes `agentDispatchable` — `true` when the OpenClaw runtime currently carries that agent, i.e. a chat sent to it right now would not be rejected as unknown. This is how a client waits out the gap between a route that changed an agent answering and the runtime having the change; the setup wizard polls it after saving the first provider. It reveals no agent metadata, so it stays public, and every failure on the OpenClaw side reports `false` rather than an error status.

With `?channelHealth=1`, the response additionally includes a `channelHealth` array — the channel-health watchdog's per-account snapshot (used by the admin Telegram settings UI to show a "degraded" badge). **This mode requires an admin session** and returns `401`/`403` otherwise: entries carry `accountId` (a Pinchy agent id) and `lastError` (worker error text, passed through the same scrubbing used for the audit trail). The rest of this endpoint — the default `{ status, connected }` check and `?agentId=` — stays public.

## Setup (public)

Setup endpoints handle the initial installation and first-admin account. They are accessible **only before setup has completed** — once an admin exists, they return `409 Conflict`.

### `GET /api/setup/status`

Check whether setup is required.

**Response:**

```json
{
  "setupComplete": false,
  "providerConfigured": false
}
```

### `POST /api/setup`

Create the first admin account.

**Request body:**

| Field      | Type   | Required | Description                  |
| ---------- | ------ | -------- | ---------------------------- |
| `name`     | string | Yes      | Admin display name           |
| `email`    | string | Yes      | Admin email address          |
| `password` | string | Yes      | Admin password (min 8 chars) |

**Response:** `201 Created`. A session cookie is set — the admin is logged in immediately.

### `POST /api/setup/provider`

Add or update a built-in LLM provider. Despite the path, this is not setup-only:
the setup wizard and **Settings → AI Provider** both post here, so it is the one
endpoint that configures a built-in provider's credentials. Admin only.

**Request body:**

| Field      | Type   | Required | Description                                                     |
| ---------- | ------ | -------- | --------------------------------------------------------------- |
| `provider` | string | Yes      | `anthropic`, `openai`, `google`, `ollama-cloud`, `ollama-local` |
| `apiKey`   | string | Cond.    | Required for cloud providers                                    |
| `url`      | string | Cond.    | Required for `ollama-local`                                     |

Pinchy validates the credential against the provider before persisting it, and
API keys are encrypted at rest with AES-256-GCM. Only the **first** provider
configured on an instance becomes the default automatically; afterwards the
default is an explicit action ([`PATCH /api/settings/providers/default`](#patch-apisettingsprovidersdefault)).

**Response:** `{ "success": true }`, plus:

| Field     | Type   | When                                                                                                                                                                                                                               |
| --------- | ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `warning` | string | The credential was saved but applying it to the agent runtime failed. Not an error — the runtime picks it up on its next restart.                                                                                                  |
| `agentId` | string | This was the instance's **first** provider and the config regenerated. The id of the Smithers agent it was configured for — poll [`GET /api/health/openclaw?agentId=…`](#get-apihealthopenclaw) until `agentDispatchable` is true. |

The route does not wait for the runtime itself. Pinchy hands OpenClaw the new
config in the background, so an agent becomes dispatchable shortly after this
call answers — and on a fresh install "shortly" can be most of a minute, because
the first saved key also provisions the runtime's secrets store and restarts it.
`agentId` is what lets a caller render that wait instead of holding a request
open through it; the setup wizard uses it to gate **Continue to Pinchy**.

Later provider saves send no `agentId`: they change no agent, so there is no
particular one to wait for. To know when such a change has reached the runtime,
poll `configPushesPending` on the same health endpoint until it is `0`.

## Agents

### `GET /api/agents`

List agents visible to the current user. Admins see every shared agent, of any visibility; non-admin users see shared agents their visibility setting admits them to. Everyone additionally sees their own personal Smithers, and nobody sees anyone else's — admins included.

The list is sent with `Cache-Control: no-store`: it differs per user, so the browser never keeps a copy the next person signing in on the same browser could be shown.

**Response:**

```json
[
  {
    "id": "uuid",
    "name": "HR Policy Assistant",
    "model": "anthropic/claude-haiku-4-5-20251001",
    "templateId": "knowledge-base",
    "allowedTools": ["knowledge_search"],
    "pluginConfig": {
      "pinchy-files": { "allowed_paths": ["/data/hr-policies"] }
    },
    "isPersonal": false,
    "ownerId": "user-uuid",
    "createdAt": "2025-01-15T10:00:00.000Z",
    "updatedAt": "2025-01-15T10:00:00.000Z"
  }
]
```

### `POST /api/agents`

Create a new agent. **Admin only.** The agent inherits default tool permissions from its template. Use `PATCH /api/agents/:id` to configure permissions after creation.

**Request body:**

| Field                 | Type     | Required | Description                                                                                                                              |
| --------------------- | -------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `name`                | string   | Yes      | Display name for the agent                                                                                                               |
| `templateId`          | string   | Yes      | Template to use. Call `GET /api/templates` for the full live list (Knowledge Base, custom, document-analysis, Odoo, and email families). |
| `tagline`             | string   | No       | Short subtitle shown under the agent name. Falls back to the template's default tagline.                                                 |
| `pluginConfig`        | object   | No       | Plugin configuration, e.g. `{ "pinchy-files": { "allowed_paths": ["/data/hr"] } }`. Required for file-access templates.                  |
| `connectionId`        | string   | No       | Integration connection to attach. Required for Odoo and email templates.                                                                 |
| `defaultAllowedTools` | string[] | No       | Extra tool IDs to allow on creation, merged with the template's defaults.                                                                |

**Example — Knowledge Base agent:**

```json
{
  "name": "HR Policy Assistant",
  "templateId": "knowledge-base"
}
```

**Example — Custom agent:**

```json
{
  "name": "General Assistant",
  "templateId": "custom"
}
```

**Response:** `201 Created` with the created agent object.

**Errors:**

- `400` — missing or invalid `name` or `templateId`, or a template requirement is unmet (for example, a file template without a selected directory, or an Odoo/email template without a `connectionId`)
- `401` — not authenticated
- `403` — not an admin
- `422` — `template_capability_unavailable`: the default provider has no model with the capabilities the template requires. The body lists what's missing:

```json
{
  "error": "template_capability_unavailable",
  "message": "Template requires vision but provider ollama-local has no matching model.",
  "missingCapabilities": ["vision"],
  "docsUrl": "https://docs.heypinchy.com/guides/ollama-setup#models-for-agent-templates"
}
```

### `GET /api/agents/:id`

Get a single agent by ID.

**Response:** The agent object, or `404` if not found.

An agent you may not see answers `404` as well, with the same body — someone else's personal agent, or a restricted agent outside your groups, is deliberately indistinguishable from an ID that was never issued. This holds for admins too: nobody can list another user's personal agents, so nobody gets to confirm one exists.

Every endpoint that gates on **your access to the agent** answers the same way, over the WebSocket chat bridge as well as over HTTP, and including the `agentId`-keyed [Automations endpoints](#automations). That now covers the admin-only management endpoints too — `knowledge/*`, `integrations`, and connecting a Telegram bot: being an admin is not a visibility rule, so those answer `404` for another user's personal agent as well. They are the surfaces that reindex an agent's documents, grant it an integration, or give it a Telegram bot, and none of that is reachable for an agent Pinchy will not show you.

No endpoint under this prefix is exempt, and a test asserts it rather than this page claiming it: `agent-route-access-gate.test.ts` fails on a handler that does not run the gate, so a new one cannot quietly skip it.

### `PATCH /api/agents/:id`

Update an agent's settings. Any combination of fields can be included.

**Request body:**

| Field          | Type     | Required | Description                                                                     |
| -------------- | -------- | -------- | ------------------------------------------------------------------------------- |
| `name`         | string   | No       | New display name                                                                |
| `model`        | string   | No       | New model identifier                                                            |
| `allowedTools` | string[] | No       | List of tool IDs the agent can use (**admin only**)                             |
| `pluginConfig` | object   | No       | Plugin configuration, e.g. `{ "allowed_paths": ["/data/hr"] }` (**admin only**) |

**Example — update permissions:**

```json
{
  "allowedTools": ["pinchy_ls", "pinchy_read"],
  "pluginConfig": {
    "allowed_paths": ["/data/hr-policies"]
  }
}
```

**Response:** The updated agent object.

**Errors:**

- `400` — cannot change permissions for personal agents
- `401` — not authenticated
- `403` — only admins can change `allowedTools` or `pluginConfig`
- `404` — agent not found, or you have no access to it (the two are indistinguishable)
- `500` — the update failed, either before or after it was stored

The `500` is worth handling deliberately, because it covers two outcomes that
call for different responses. Pinchy stores the agent row first and then
regenerates the runtime configuration, and the message tells you which step
gave out:

```json
{ "error": "Could not update the agent: <cause>" }
```

Nothing was stored. The agent is unchanged and the request can simply be
repeated.

```json
{
  "error": "Settings were saved, but the agent runtime was not updated: <cause>"
}
```

The change **is** stored; only the runtime has not caught up. That includes a
`groupIds` change sent in the same request: the group assignment is written
before Pinchy answers. If writing it fails too, the message says so with a
second sentence, `The group assignment was not saved: <cause>`, and only the
group change needs to be sent again. Any other step that fails after the
group assignment is written adds `A follow-up step also failed: <cause>`
instead; the group change is then stored. A later save or a restart brings the
runtime up to date. Retrying is safe — the update is idempotent — but treating
the change as discarded is not. Pinchy records this case in the audit trail as
an `agent.updated` entry with outcome `failure`, so a change that reached the
database but not the runtime still leaves a trace — including the
`allowedGroups` diff when the request changed the agent's groups.

### `DELETE /api/agents/:id`

Delete an agent. **Admin only.** Personal agents (auto-created Smithers) cannot be deleted.

**Response:** `200 OK`

```json
{
  "success": true
}
```

**Errors:**

- `400` — attempting to delete a personal agent
- `401` — not authenticated
- `403` — not an admin
- `404` — agent not found, or it is another user's personal agent (admins cannot reach those either)

### `GET /api/agents/admin-only`

List the shared agents only admins can use under a license: visibility **Restricted** with no group assigned. **Admin only.** Answers in every license state — on a community instance it is the list of agents members would lose the moment a key is activated. Personal and deleted agents never appear.

**Response:** `200 OK`

```json
{
  "agents": [{ "id": "a1b2c3", "name": "Sales Assistant" }]
}
```

**Errors:**

- `401` — not authenticated
- `403` — not an admin

### `POST /api/agents/admin-only/open-to-all`

Make the named admin-only agents visible to every user. **Admin only, enterprise.** This widens access, so it only ever happens as an explicit request for the agents you name — activating a license never does it on its own.

**Request body:**

| Field      | Type     | Required | Description                         |
| ---------- | -------- | -------- | ----------------------------------- |
| `agentIds` | string[] | Yes      | 1–200 agent IDs to set to All users |

Only agents that are still Restricted with no group are changed. An agent that got a group (or was deleted) after you loaded the list is left alone, so this can never widen a group-scoped agent. Each changed agent writes an `agent.updated` audit entry with `changes.visibility` from `restricted` to `all`, the same entry the Access tab writes.

**Response:** `200 OK` — the agents that were actually changed (an empty list if none still qualified):

```json
{
  "agents": [{ "id": "a1b2c3", "name": "Sales Assistant" }]
}
```

**Errors:**

- `400` — `agentIds` is missing, empty, or longer than 200
- `401` — not authenticated
- `403` — not an admin, or no active license

### `POST /api/agents/:agentId/uploads`

Stage a file for an upcoming chat message. The file is held in the agent's staging area; the chat sends the returned `id` as one of its `attachmentIds` rather than inlining the file. Anyone with access to the agent can upload.

**Headers:**

| Header              | Required | Description                                          |
| ------------------- | -------- | ---------------------------------------------------- |
| `x-pinchy-draft-id` | Yes      | UUID grouping uploads for the message being composed |

**Request body:** `multipart/form-data` with a single `file` field.

**Accepted types:** images (`image/jpeg`, `image/png`, `image/webp`, `image/gif`, `image/heic`, `image/heif`), `application/pdf`, and text formats (`text/plain`, `text/csv`, `text/markdown`, `application/json`, `text/yaml`). The detected content type must match the declared one. Maximum file size is **15 MB**.

**Response:** `201 Created`

```json
{
  "id": "upload-uuid",
  "filename": "report.pdf",
  "mimeType": "application/pdf",
  "sizeBytes": 51234
}
```

Send `id` in the chat message's `attachmentIds` (up to **10** attachments per message). Staged files expire after **24 hours** and are removed by an hourly garbage-collection sweep if never attached.

**Errors:**

- `400` — missing or invalid `x-pinchy-draft-id`, malformed form data, missing `file` field, or invalid filename
- `401` — not authenticated
- `404` — no such agent, or no access to it (the two answer alike)
- `413` — file exceeds the 15 MB limit
- `415` — unsupported or mismatched file type

### `GET /api/agents/:agentId/chats`

List the caller's conversations with this agent, newest first — the data behind the chat switcher. A chat with no explicit label is titled from its first user message; if that message can't be read, the chat falls back to its date rather than failing the list.

### `POST /api/agents/:agentId/sessions/reset`

Clear the caller's conversation context with this agent — the `/reset` slash command. The OpenClaw session key stays the same but starts empty on the next turn; the old transcript remains on disk, just unreachable from that key. Audited as `chat.session_reset`.

**Response:** `{ "ok": true }`

### `POST /api/agents/:agentId/sessions/compact`

Summarize the caller's conversation with this agent so a long context stops degrading model quality — the `/compact` slash command. Takes effect on the next turn, and the visible messages stay where they are.

**Response:** `{ "ok": true }`

**Errors:**

- `429` — a compaction for this session is already in flight
- `502` — OpenClaw could not compact the session

### `GET /api/agents/:agentId/active-error`

The agent's current "paused" banner for the caller: the latest error from the last 24 hours that has not been superseded (a later message in the conversation went through) or dismissed, or `null`. Pass `?chatId=` to address one specific chat; omit it for the default per-user session. The session key embeds the caller's own id, so a user can only ever read their own errors.

### `DELETE /api/agents/:agentId/active-error?id=<errorId>`

Dismiss the error the banner is showing. Scoped to the owning user, so one user can never clear another's banner.

**Errors:**

- `404` — no un-dismissed error with that id belongs to the caller

### `GET /api/agents/:agentId/retry-gate`

Whether retrying the caller's last failed run in this conversation could duplicate actions the agent already performed. Pass `?chatId=` to address one specific chat; omit it for the default per-user session.

**Response:**

| Field         | Type      | Description                                                            |
| ------------- | --------- | ---------------------------------------------------------------------- |
| `sideEffects` | `boolean` | `true` when the failed run had already executed at least one tool call |

The chat asks this when you press Retry, not when the run failed — see [Retrying after the agent already acted](/guides/retry-messages/#retrying-after-the-agent-already-acted). The time window comes from the stored run, never from the request, and only tool calls made on the caller's behalf count — on a shared agent, another member's activity in the same window never turns the answer to `true`. So this cannot be used to query an agent's tool history.

### `GET /api/agents/:agentId/uploads/:filename`

Download a file the caller uploaded to this agent. Cached like `workspace-file` below: kept, but checked again on every reuse (`304` when unchanged), and only for the same session. Unlike `workspace-file`, downloads here are not written to the audit trail, a `304` included.

### `GET /api/agents/:agentId/artifacts/:filename`

Download a file the agent produced and delivered in chat — see [Generating files](/guides/file-uploads/#generating-files). Cached like `workspace-file` below: kept, but checked again on every reuse (`304` when unchanged), and only for the same session. Unlike `workspace-file`, downloads here are not written to the audit trail, a `304` included.

Serves a file the caller was actually handed, not whatever currently carries that name. Each delivery records where the file was and a checksum of its contents, and the download is refused with `404` unless the file on disk still matches one of the caller's own deliveries of that name. On a shared agent that matters: everyone's chats write into the same workspace, so without it a later file of the same name — from a conversation you cannot see — would be served under your download link.

### `GET /api/agents/:agentId/files/:filename`

Read a file in the agent's own workspace.

### `PUT /api/agents/:agentId/files/:filename`

Write a file into the agent's own workspace.

### `GET /api/agents/:agentId/workspace-file?path=<path>`

Serve a file from a directory this agent is granted under `allowed_paths` — the path behind a knowledge-base citation you click. Supports byte ranges, so a PDF viewer can jump straight to the cited page.

The bytes are sent with `Cache-Control: private, no-cache`, `Vary: Cookie` and a weak `ETag`. The browser keeps its copy but asks the server before every reuse, and the server answers only after the access check: if the agent's grant was removed, or you lost access to the agent, every new request for the document is answered `403` or `404` instead of letting the browser reuse its copy. A page the browser restores from its own history (the Back button) can still show what it displayed before; that is not a new request and no cache header prevents it short of not storing the document at all. An unchanged document you may still see is answered `304 Not Modified` without its bytes, so a large PDF is not sent again; that reuse is logged like any other read (`knowledge.source_viewed`, or `knowledge.source_downloaded` with `download=1`), marked `revalidated: true`. `Vary: Cookie` keeps a copy from crossing sessions, such as another person signing in on the same browser.

A `Range` request is honoured on its own. Sent with `If-Range`, it is answered with the whole file instead: `If-Range` needs a strong validator, and splicing a range of a newer edition onto a cached copy of an older one would corrupt the document.

**Query parameters:**

| Field      | Required | Description                                                                                                            |
| ---------- | -------- | ---------------------------------------------------------------------------------------------------------------------- |
| `path`     | Yes      | The file, which must resolve inside one of the agent's granted directories                                             |
| `download` | No       | `1` marks this as taking a copy rather than reading it                                                                 |
| `variant`  | No       | `original`, `converted` or `rows` — the converted PDF is what previews an Office source. Anything else 400s            |
| `sheet`    | No       | `variant=rows` only: the worksheet the cited rows live on. Pass it together with `from` and `to`, or none of the three |
| `from`     | No       | `variant=rows` only: first cited row, 1-based inclusive                                                                |
| `to`       | No       | `variant=rows` only: last cited row, inclusive; clamped to at most 200 returned rows                                   |

`variant=rows` is what a spreadsheet citation's preview asks for. It answers JSON instead of bytes — `{ sheet, columns, rows }`, each row carrying its sheet row number and its cell texts index-aligned to `columns` — read through the same traversal the index used, so hidden rows and hidden sheets stay excluded. With none of `sheet`/`from`/`to` it opens the top of the first visible sheet; naming a sheet the workbook does not have answers `200` with an empty range (the document was found); a workbook that will not open answers `422`, and one that is too large to read safely answers `413` — refused without being opened when it is over 100 MB, unpacks to far more than it weighs, has a sheet (or another part the reader reads as text) over 16 MB or a picture over 32 MB, and refused after the attempt when reading it needs more memory than the separate process the rows are read in may use (384 MB). That process is why a heavy workbook never costs Pinchy's own memory. `503` is about the reader, never the workbook: there was no room on the artifact volume for the private copy the rows are read from, the process could not be started, ran past its two-minute limit or was stopped by the system — or two reads are already waiting for it, in which case the answer carries `Retry-After`. An `.xls` is previewed from the `.xlsx` the index converted it to, so the sheet and rows are the ones the citation was made from and the size limits apply to that converted file; before a run has converted it, or when the converter refused it, `variant=rows` answers `404` and the original stays downloadable. Workbooks are read one at a time, the index's reads included, so a request that is abandoned while it waits or reads (a reload, a closed preview) has its read dropped; its audit row says `cancelled`.

`download` decides which audit row is written: `knowledge.source_viewed` without it, `knowledge.source_downloaded` with it. Reading a cited document and carrying it out of the building are different acts, so they are different rows — and the caller has to say which, because the response cannot: a `.docx` is served as an attachment either way. A successful read also records which representation was served — or, on a `304`, which one was checked (`original`, `converted` or `rows`).

### `GET /api/agents/:agentId/workspace-file/:name?path=<path>`

The same file, under a URL whose last segment is its name — the URL the citation viewer opens, so the browser's PDF viewer shows the document's name instead of `workspace-file`. Takes the same query parameters as the route above and behaves exactly like it: `path` alone decides which file is read, against the same grant, with the same audit rows. `:name` must be the name of the file actually served — for a Word or PowerPoint source that's its converted PDF (`Angebot.pdf` for `Angebot.docx`), unless `variant=original` asks for the original. When the requested path is a link, the link's name counts as well as the target's. Any other name answers `404`, and the audit row records `name_mismatch`. `variant=rows` answers JSON rather than a file, so it doesn't check the name.

### `GET /api/agents/:agentId/telegram-chat`

The mirrored transcript of this agent's Telegram conversations, for reading them in the web UI.

## Agent Provisioning API

Machine clients (CI, scripts) provision agents with a scoped API key instead of a session. Admins mint and revoke keys under **Settings → API Keys**; the key then authenticates the versioned `/api/v1/*` surface. The [Agent Provisioning API reference](/reference/agent-provisioning-api/) carries the authentication model, scopes, `curl` examples, and full request/response shapes — the entries below are the index.

### `GET /api/settings/api-keys`

List every API key (masked `start`, scopes, expiry, last-used, enabled state, and `createdBy` with the creator's snapshotted name and an `active` flag that turns `false` once the creator is banned, deleted or no longer an admin). **Admin only.** The plaintext secret is never returned — it is shown once at creation and never again.

### `POST /api/settings/api-keys`

Mint a new API key. **Admin only.** Body: `name` (32 characters max), `scopes` (one or more of `agents:read`, `agents:write`, `agents:delete`), and an optional `expiresInDays` (1–365; omit it for a key that never expires). The response carries the plaintext key exactly once; store it then, because no endpoint can return it later. Audited as `api_key.created`.

### `DELETE /api/settings/api-keys/:keyId`

Revoke (hard-delete) a key by id. **Admin only.** Returns `404` when no key has that id; the revocation touches no other key. Audited as `api_key.deleted` with the key's snapshotted name.

### `GET /api/v1/agents`

Key-authenticated (`agents:read`). Lists every **shared** agent org-wide — unlike the session `GET /api/agents`, it is not filtered by the caller's group membership. Personal agents are always excluded. See the [Agent Provisioning API reference](/reference/agent-provisioning-api/).

### `POST /api/v1/agents`

Key-authenticated (`agents:write`). Creates a shared agent from a template, identically to `POST /api/agents` but with the key as the audit actor (`actorType: "api_key"`). The created agent is unowned (`ownerId: null`). See the [Agent Provisioning API reference](/reference/agent-provisioning-api/).

### `GET /api/v1/agents/:agentId`

Key-authenticated (`agents:read`). Fetches one shared agent by id; a personal agent's id answers `404` indistinguishably. See the [Agent Provisioning API reference](/reference/agent-provisioning-api/).

### `DELETE /api/v1/agents/:agentId`

Key-authenticated (`agents:delete`) — its own scope, separate from `agents:write`, because deletion is irreversible. Soft-deletes a shared agent, audited with the key as actor. See the [Agent Provisioning API reference](/reference/agent-provisioning-api/).

## Knowledge Base

See [Create a Knowledge Base Agent](/guides/create-knowledge-base-agent/) for the end-to-end setup flow.

### `POST /api/agents/:agentId/knowledge/reindex`

Queue a (re)index of the agent's granted knowledge-base folders. **Admin only.** Reads the agent's `pinchy-files` `allowed_paths`, extracts text from each PDF, chunks and embeds it with the bundled in-process `embeddinggemma` model (no Ollama endpoint required), and stores the result in Pinchy's Postgres knowledge-base index. Idempotent: unchanged files are skipped, changed files are replaced, and files removed from disk are dropped from the index.

The request returns as soon as the job is queued — indexing runs in the background, because a real corpus takes hours to embed. Poll [`GET`](#get-apiagentsagentidknowledgereindex) on the same path for progress and results.

**Request body:**

| Field   | Type     | Required | Description                                                                                                                                                        |
| ------- | -------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `paths` | string[] | No       | Subset of the agent's granted folders to reindex. Can only narrow the granted set — any path not already granted is ignored. Omit to reindex every granted folder. |

**Response — `202 Accepted`:**

```json
{
  "jobId": "6f1c2b64-6c3e-4a2f-9c19-5c1d3a1f2e77",
  "status": "pending",
  "pathCount": 2
}
```

| Field       | Description                                                                                            |
| ----------- | ------------------------------------------------------------------------------------------------------ |
| `jobId`     | The queued job. Pass nothing — `GET` on the same path reports this agent's most recent job.            |
| `status`    | `pending` (queued) — or `noop` when the agent has no granted folders, in which case `jobId` is `null`. |
| `pathCount` | Number of granted folders the job will reindex.                                                        |

**Errors:**

- `401` — not authenticated
- `403` — not an admin
- `404` — agent not found, or it is another user's personal agent (admins cannot reach those either)
- `409` — a reindex is already running. One index job runs at a time across the whole instance, so the run in your way may belong to a **different** agent. The response carries the running job's `jobId`, `status`, and `agent` — `GET` that agent's reindex endpoint to watch it, rather than retrying.
- `503` — the bundled embedding model file is missing from the image (a broken build or mount, not a configuration step)

| `counts`                        | The run's findings **so far**, updated as it goes. `null` before the first document.                                                                                                                                                                                                                                                                                                                                                                                                                         |

| `counts.removed`                | Source file no longer on disk; the document and its chunks were deleted. | `counts.unsearchable`           | Parsed without error but yielded no text, so the document exists in the index yet can never be retrieved — a workbook whose sheets are all hidden, or a scan that no vision model was available to read.                                                                                                                                                                                                                                                                                                     |
| `counts.failed`                 | The file could not be read or parsed, or was refused because it had been [swapped for a symbolic link](/guides/mount-data-directories/#links-inside-a-mounted-folder) during the run. The run continues — one bad file never aborts the reindex — and a previously indexed version of the file stays searchable.                                                                                                                                                                                             |
| `counts.archived`               | Documents in this run that sit under an archive folder (`OLD`, `Archiv` and the like) and are therefore left out of everyday search. Not a separate outcome: an archived document is also `indexed` or `skipped`.                                                                                                                                                                                                                                                                                            |
| `counts.unsupported`            | Files in the granted folders whose type the index can't read — an `.rtf` note, a binary `.xlsb` workbook. | `error`                         | Why the run failed. `null` unless `status` is `failed`. The matching audit entry gives the same failure without folder paths.                                                                                    |

`schedule` answers "do I still have to press the button?" for this agent. It is `null` if the schedule could not be read; the job is reported either way.

| Field               | Description                                                                                                                                                                                                                                                                                                                                                                            |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schedule.enabled`  | Whether the instance reindexes knowledge-base agents on its own every night. Set with [`PUT /api/settings/knowledge-index-schedule`](#put-apisettingsknowledge-index-schedule).                                                                                                                                                                                                        |
| `schedule.time`     | The time of day it runs, in the organization timezone.                                                                                                                                                                                                                                                                                                                                 |
| `schedule.timezone` | The organization timezone `time` is read in.                                                                                                                                                                                                                                                                                                                                           |
| `schedule.nextRun`  | The next run as `date`, `time` and `day` (`today` or `tomorrow`), all in the organization timezone, and as `at`, the same moment as a UTC timestamp — the one to convert for a reader elsewhere. On the night the clocks go forward, a `time` that doesn't happen that night is reached at the first minute after the jump, and `at` says so. `null` while the nightly reindex is off. |
| `schedule.included` | Whether the nightly run covers **this** agent. Only agents that have the `knowledge_search` permission and at least one granted folder are swept; an agent that only reads files is reindexed on demand.                                                                                                                                                                               |

`unsearchable` and `failed` can be non-zero on a `succeeded` run: the reindex itself worked, and these are its findings about the corpus.

`status: "failed"` means something systemic stopped the run — the embedding endpoint or the database, or none of the agent's folders could be read — not that a file was broken. A broken file is a `counts.failed`, and the run keeps going. Failed runs keep the counts they reached before dying.

A run interrupted by a restart is picked up again automatically: indexing is idempotent, so the resumed run skips everything already done.

Every run writes two `knowledge.reindex` audit entries, correlated by `jobId`: the request — the admin's, the nightly scheduler's, Pinchy's own after an update, or a first index's (the admin whose grant started it, or the background worker when it had to wait) — and the outcome (recorded by the background worker, with the counts). Both carry `trigger`.

**Errors:**

- `401` — not authenticated
- `403` — not an admin
- `404` — agent not found, or it is another user's personal agent (admins cannot reach those either)

### `GET /api/agents/:agentId/knowledge/first-index`

Whether the agent's first index is still to come, and how far it has got. This is what the agent's chat shows above the message box, so a new Knowledge Base agent doesn't quietly answer "nothing found" while its documents are still being read. Open to **anyone who can see the agent**, not only admins: the answer is a state and two counts, never folders or run details.

Pinchy queues the first index on its own when an agent that has the `knowledge_search` permission is granted a folder no run has gone through yet: on [`POST /api/agents`](#post-apiagents), on [`PATCH /api/agents/:id`](#patch-apiagentsid) when the permissions change, and through its background worker for every other grant — one that found another run in the way (as soon as that run finishes), or an agent created with an API key. Those runs are requested by `kb-index-worker`. Only those folders are indexed, not the agent's others. The run is an ordinary reindex with `trigger: "initial"`, behind the same [one-run-at-a-time rule](#post-apiagentsagentidknowledgereindex).

**Response:**

```json
{ "state": "indexing", "processed": 120, "total": 505, "partial": false }
```

| Field       | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `state`     | `none` once every granted folder has had a run that finished (or for an agent that doesn't search the index), `queued` while the first index is about to start, `waiting` while another run holds the one job slot and the first index starts after it, and `indexing` while a run goes through a folder still waiting for its first index — whichever agent's run it is. Later runs (nightly, **Reindex now**) report `none`, and so does an instance whose bundled embedding model is missing, since no run can start there. |
| `processed` | Documents done so far. `indexing` only.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `total`     | Documents found. `null` until discovery has walked every folder. `indexing` only.                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `partial`   | `true` when some of the agent's folders are indexed already, so it answers from them while only the newly granted ones wait. Every state but `none`.                                                                                                                                                                                                                                                                                                                                                                           |

**Errors:**

- `401` — not authenticated
- `403` with `code: "personal_agent_disabled"` — an admin has turned members' personal agents off, and this is yours
- `404` — agent not found, or not visible to you

### `GET /api/settings/knowledge-index-schedule`

The nightly reindex: whether it's on, when it runs, and what the last nights did. **Admin only.**

```json
    "agentCount": 2
  }
}
```

| Field          | Description                                                                                                                                                                                 |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `enabled`      | Whether the nightly reindex runs. On by default.                                                                                                                                            |
| `time`         | 24-hour `HH:MM`, in the organization timezone. Defaults to `02:00`.                                                                                                                         |
| `timezone`     | The organization timezone `time` is read in.                                                                                                                                                |
| `nextRun`      | `date`, `time` and `day` (`today` or `tomorrow`) of the next run, in the organization timezone, and `at`, the same moment as a UTC timestamp. `null` while `enabled` is `false`.            |

### `PUT /api/settings/knowledge-index-schedule`

Turn the nightly reindex on or off, or move it. **Admin only.** Send the whole schedule; the response is the same as `GET`.

**Request body:**

| Field     | Type    | Required | Description                                                 |
| --------- | ------- | -------- | ----------------------------------------------------------- |
| `enabled` | boolean | Yes      | Whether Pinchy reindexes knowledge-base agents on its own.  |
| `time`    | string  | Yes      | 24-hour `HH:MM` in the organization timezone, e.g. `02:00`. |

A new setting applies from its next occurrence. Switching the reindex back on at 14:00, or moving it from 23:00 to 09:00 in the afternoon, never starts a run on the spot; the next run is the next time the clock reaches `time`.

A change is recorded as a `settings.updated` audit entry with the old and new schedule. Saving the same values again records nothing.

**Errors:** `400` invalid body (for example `time` not in `HH:MM`), `401` not authenticated, `403` not an admin.

### `POST /api/internal/knowledge/search`

**Internal** — authenticated with the shared OpenClaw gateway token, not a user session. Called by the `pinchy-knowledge` plugin's `knowledge_search` tool, never by the browser.

Runs a hybrid (vector + full-text) search over the requesting agent's indexed, granted documents and returns numbered, citable passages. The raw query is never persisted — only a one-way hash, since a knowledge-base question can itself carry PII.

### `POST /api/agents/:agentId/knowledge/passage`

Which indexed passage of a cited page, slide or Word section an answer drew on — what the citation viewer asks before it highlights one. Read-only: it isn't audited itself, because it accompanies a document view that `workspace-file` already records as `knowledge.source_viewed`.

It returns text from a document, so it applies the same two gates as `workspace-file`, in the same order, before the index is read: the agent check (`404` for an agent you can't use, `403` for a paused one), then the agent's granted folders (`403` for a path outside them, `404` for a file that isn't there).

**Request body:**

| Field     | Type   | Required     | Description                                                                                                                                                      |
| --------- | ------ | ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `path`    | string | Yes          | The document's full path — the `path` a citation link carries.                                                                                                   |
| `page`    | number | One of three | A PDF's cited page, from 1.                                                                                                                                      |
| `slide`   | number | One of three | A slide deck's cited slide, from 1.                                                                                                                              |
| `heading` | string | One of three | A Word document's cited heading path, levels joined by a space, `>` and a space, as the citation shows it — `Quality > Incoming goods`. At most 2000 characters. |
| `claim`   | string | No           | The answer's sentences that cite the source, at most 2000 characters. Used only to choose between the passages of the page, slide or section, and never stored.  |

Send exactly one of `page`, `slide` and `heading`; a body with none or more than one is a `400`. A heading matches only the whole path: `Quality` does not match a passage filed under `Quality > Incoming goods`.

**Response:**

```json
{
  "passage": {
    "text": "§ 4 Reaktionszeiten\nDer Auftragnehmer reagiert auf Störungen innerhalb von vier Stunden."
  }
}
```

`passage` is the indexed text of the passage, or `null` when there is none to show: the page, slide or section holds no indexed text, or it holds several passages and nothing says which — no `claim`, or the embedding model isn't available. The response names no page: for a Word section, the viewer finds the passage's page in the converted PDF itself. With several, the one nearest to `claim` in meaning wins, which also works when the answer is in a different language than the document.

**Errors:** `400` invalid body, `401` not authenticated, `403` path outside the agent's granted folders or agent paused, `404` agent not found or not accessible, or file not found, `502` the lookup failed.

### `GET /api/agents/:agentId/knowledge/unsearchable`

**Which** documents the index holds but search can't reach. Two kinds: documents that produced no searchable text — the ones the `unsearchable` counter in the reindex status counts — and Word or PowerPoint files search leaves out until they have been converted again after an update, which that counter never counts. **Admin only.**

The counter answers for the last run; `totals.no_text` answers for everything currently in the agent's granted folders, so it is usually the larger of the two. That is the two numbers agreeing, not disagreeing: a file unchanged since an earlier run is `skipped` by the next one and never counted again.

Scoped to the folders that agent is granted, exactly like search itself, so the list never names a document the agent isn't allowed to know about.

A corpus can hold thousands of these documents, so the route answers in two steps. Without a query it returns the counts — per reason, per cause and per folder — and no document names. With `root` (and optionally `folder`) it returns one folder's documents. [`GET …/knowledge/unsearchable/csv`](#get-apiagentsagentidknowledgeunsearchablecsv) has all of them in one file.

**Query parameters:**

| Parameter | Description                                                                                                                                                                                                      |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `root`    | One of the agent's granted folders, as `groups[].root` names it. Lists that group's documents. A folder the agent isn't granted lists nothing.                                                                   |
| `folder`  | A folder directly inside `root`, as `groups[].folder` names it: one name, no `/`. Lists the documents anywhere under it. Leave it out to list the documents directly in `root`. Only valid together with `root`. |

**Response without a query:**

```json
{
  "total": 21,
  "totals": { "no_text": 20, "awaiting_conversion": 1 },
  "causes": {
    "ocr_off": 19,
    "no_vision_model": 0,
    "read_next_run": 0,
    "read_refused": 0,
    "vision_failed": 0,
    "read_blank": 1
  },
  "groups": [
    { "root": "/data/certs", "folder": "Food", "count": 19 },
    { "root": "/data/offers", "folder": null, "count": 2 }
  ],
  "searchesIndex": true
}
```

| Field           | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `total`         | How many documents there are, never capped.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `totals`        | `total` per reason. `no_text` — indexed, but it produced no searchable text (a scan nothing has read, a file refused for its size or content). `awaiting_conversion` — a Word or PowerPoint file search leaves out until it has been converted again after an update changed how such files are converted.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `causes`        | The `no_text` documents by why they have no text, as this server stands now. `ocr_off` — reading scans is switched off (`PINCHY_KB_OCR=off`); switching it on lets the next run read them. `no_vision_model` — it's on, but no vision model is available. `read_next_run` — the next run reads them again: a vision model is available that hasn't read them, an older version of Pinchy read them, or their last read didn't finish. `vision_failed` — every vision read failed, five runs in a row; a different vision model or a replaced file gets them read again. `read_refused` — the converter, the workbook reader or the mail reader refused the file (too large, damaged, not what its name says), or it's a workbook with nothing visible in it; the server log names each refused file and the reason, and a file that's replaced is read again. `read_blank` — read in full, and nothing found. Sums to `totals.no_text`. |
| `groups`        | The documents per folder: a granted folder (`root`) and one folder directly inside it (`folder`), or `folder: null` for the files directly in `root`. Largest first; the counts sum to `total`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `searchesIndex` | Whether the agent has `knowledge_search`. Pinchy converts the `awaiting_conversion` files again on its own only for an agent that searches the index; for any other agent, a reindex converts them.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |

**Response with `root`:**

```json
{
  "documents": [
    {
      "sourcePath": "/data/certs/Food/2024/AFNOR validation.pdf",
      "name": "AFNOR validation.pdf",
      "root": "/data/certs",
      "folder": "Food/2024",
      "status": "active",
      "reason": "no_text",
      "cause": "ocr_off"
    }
  ],
  "total": 19
}
```

| Field                    | Description                                                                                                                          |

## Automations

Standing email workflows an agent runs on its own — see [the Automations tab](/concepts/agent-settings/#automations-tab). You can manage automations on a personal agent you own; admins can manage them on any agent they can see, which is every shared agent. Someone else's **personal** agent is not one of them: personal agents stay private to their owner, admins included, and that rule wins here as it does everywhere else in Pinchy.

The endpoints keyed by **`agentId`** ask two questions in order, and answer differently depending on which one you fail. Can you **see** the agent at all? If not — someone else's personal agent, or a restricted one outside your groups — you get a plain `404`, identical to an ID that was never issued, because any other answer would confirm the agent exists. If you can see it but may not **manage** its automations — the everyday case of a shared agent you chat with daily — you get `403`, which tells you nothing you did not already know and points you at an admin instead of at a typo.

`PATCH` and `DELETE` are keyed by **workflow** id instead, and there a scope refusal is `404` too. The middle case has no equivalent: `GET /api/automations` asks this same scope question _and_ the visibility one in front of it, so anyone refused here could never have listed the workflow in the first place. `403` would be the only way to learn that a workflow id is real.

Being keyed by workflow id also gives these two a reach the `agentId` endpoints deliberately lack: an admin who already holds a workflow's id — from the [audit trail](/concepts/audit-trail/), which is where a runaway automation surfaces — can disable or delete it even on someone's personal agent. Standing autonomous authority has to stay stoppable. It grants no way to **find** such a workflow, only to act on one already known.

### `GET /api/automations?agentId=<agentId>`

List the agent's email workflows.

Each item carries `pausedByBudget: true` while a used-up blocking [cost budget](/guides/cost-governance/) pauses the agent's automations for this month. The sweep skips them without changing `status`, so read `pausedByBudget` rather than `status` to tell whether one is actually running.

**Errors:**

- `400` — `agentId` is missing from the query string
- `401` — not authenticated
- `403` — you can see the agent, but its automations are outside your scope: a shared agent is admin-only, and a personal agent's automations belong to its owner. Also answered with `code: "personal_agent_disabled"` when an admin has turned members' personal agents off
- `404` — no agent has that id, **or** you may not see the one that does

### `POST /api/automations`

Create a workflow. It is always created **disabled** and `pending`, whatever the payload says — Pinchy proposes an automation, it never activates one on its own. Enabling is the separate, human-gated step below.

**Request body:**

| Field             | Type     | Required | Description                                                                       |
| ----------------- | -------- | -------- | --------------------------------------------------------------------------------- |
| `agentId`         | string   | Yes      | The agent that will run the workflow                                              |
| `name`            | string   | Yes      | Label for the workflow, up to 200 characters                                      |
| `action`          | string   | Yes      | The instruction the agent follows for each matching mail                          |
| `connectionIds`   | string[] | Yes      | One to 50 email connections to watch. A workflow with no mailbox would never fire |
| `filter`          | object   | No       | Trigger filters, AND-combined. Omit for the whole mailbox                         |
| `sweepWindowDays` | number   | No       | How far back the reconciliation sweep re-lists, 1–365 (default `14`)              |

`filter` accepts `from` (string[]), `toDomain` (string[]), `subjectContains` (string[]), `hasAttachment` (boolean), `attachmentType` (string), and `folder` (string).

**Response:** `201 Created`

**Errors:**

- `400` — the body fails validation, or a requested connection is one the agent has no email **read** access to. The response names those connection ids; an id that doesn't exist lands here too, since it has no permission row either
- `401` — not authenticated
- `403` — you can see the agent but may not create a workflow on it (same scope rule as the list). Also answered with `code: "member_automations_disabled"` when an admin has turned off automations on members' personal agents (see [Cost governance](/guides/cost-governance/)), and with `code: "personal_agent_disabled"` when they have turned off members' personal agents altogether
- `404` — no agent has that id, **or** you may not see the one that does

### `PATCH /api/automations/:id`

Enable or disable a workflow — the human-gated step that turns a proposal into a live automation, and the way to pause one without deleting it.

**Request body:** `{ "enabled": true }`

**Response:** `{ "id": "...", "enabled": true }`

Toggling to the state it already has is a no-op: still `200`, no audit entry — an unchanged state is not an event.

**Errors:**

- `400` — the body has no boolean `enabled`
- `401` — not authenticated
- `403` — `code: "member_automations_disabled"`: you asked to **enable** a workflow on a member's personal agent while automations there are turned off. Admins get this too, because the workflow would read "enabled" and never run. Disabling is always allowed
- `403` — `code: "budget_exhausted"`: you asked to **enable** a workflow on an agent that a used-up blocking [cost budget](/guides/cost-governance/) has paused for this month. Same reason, same rule: disabling is always allowed
- `404` — no workflow has that id, **or** its agent is outside your scope. This endpoint addresses a workflow, not an agent, so a malformed id lands here as well: it definitionally matches nothing

### `DELETE /api/automations/:id`

Delete a workflow for good.

**Response:** `{ "id": "..." }`

**Errors:**

- `401` — not authenticated
- `404` — no workflow has that id, **or** its agent is outside your scope (as with `PATCH`, a malformed id matches nothing)

### `GET /api/automations/connections?agentId=<agentId>`

The email connections this agent can watch — what the create form offers in its mailbox picker.

**Errors:**

- `400` — `agentId` is missing from the query string
- `401` — not authenticated
- `403` — you can see the agent, but its automations are outside your scope
- `404` — no agent has that id, **or** you may not see the one that does

### `GET /api/data-directories`

List directories available under `/data/` for agent configuration.

**Response:**

**Query parameters:**

| Parameter | Description                                                                                |

| Field         | Description                                                                                                                                                                          |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

- `401` — not authenticated
- `403` — not an admin
- `404` — the folder doesn't exist, isn't a folder, can't be read, or is reached through a symbolic link

### `GET /api/agents/:agentId/granted-folders`

Whether each folder the agent is granted still exists. The directory picker uses it to mark a grant whose folder was renamed, moved or deleted, instead of showing it as an ordinary ticked box. **Admin only.**

It checks the agent's **saved** grants under `/data/` and nothing else: it takes no path from the request, so it can't be used to ask about an arbitrary folder. Nothing outside `/data/` is touched, and a symbolic link is reported as one rather than followed.

**Response:**

```json
{
  "folders": [
    { "path": "/data/suppliers", "status": "available" },
    { "path": "/data/old-suppliers", "status": "missing" }
  ]
}
```

| `status`       | Meaning                                                                                                                                  |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `available`    | The folder is there and Pinchy can open it.                                                                                              |
| `missing`      | Nothing is there any more, or a file is. Remove the grant with [`PATCH /api/agents/:id`](#patch-apiagentsid), or mount the folder again. |
| `unreadable`   | Something is there, but Pinchy isn't allowed to open it. A permissions problem on the server — removing the grant is not the fix.        |
| `link`         | The path runs through a symbolic link. Agents can't read through one.                                                                    |
| `outside_data` | Not a path under `/data/`. Never checked.                                                                                                |

**Errors:**

- `401` — not authenticated
- `403` — not an admin
- `404` — agent not found, or it is another user's personal agent

### `GET /api/budgets`

Every budget with this month's spend, in the organization timezone.

**Response:**

### `PUT /api/budgets`

Create or replace a budget. Requires an Enterprise license. There is at most one instance budget and one per agent, so saving again for the same scope updates it. | `onExceeded`      | string         | Yes      | `notify` or `block`                                      |

### `DELETE /api/budgets/:id`

Remove a budget. Works without a license, so an expired one never leaves an instance with chats paused and no way to lift it. Writes `budget.deleted`.

**Response:** `{ "id": "…" }`

**Errors:** `401`, `403` (not an admin), `404` (no budget has that id, or it is on another user's personal agent).

### `POST /api/internal/budgets/check`

**Internal** — authenticated with the shared OpenClaw gateway token, not a user session. Called by the `pinchy-audit` plugin's `before_agent_run` hook before every agent run, on every channel (web, Telegram, automations), never by the browser.

Answers whether a used-up blocking budget — the agent's own or the instance's — stops this run. When it does, the plugin refuses the run before the model reads the prompt, and the sender gets `message` as the reply.

**Request body:**

| Field        | Type   | Required | Description                                                                   |
| ------------ | ------ | -------- | ----------------------------------------------------------------------------- |
| `agentId`    | string | Yes      | The agent about to run                                                        |
| `sessionKey` | string | No       | The OpenClaw session; a web-chat session names the Pinchy user                |
| `channel`    | string | No       | Where the run came from, e.g. `telegram`; recorded on a refusal               |
| `senderId`   | string | No       | The sender's account on that channel, mapped to the Pinchy user who linked it |
| `trigger`    | string | No       | What started the run, as OpenClaw names it (`user`, `cron`, `heartbeat`, …)   |

The plugin never sends the prompt, the conversation or the system prompt — only who is asking and where.

**Response:**

```json
{
  "blocked": true,
  "message": "Knowledge Base has used its monthly budget. It's available again next month, or sooner if your admin raises the budget."
}
```

`{ "blocked": false }` when nothing stops the run; that answer writes nothing. A refusal writes `chat.policy_refused` with `reason: "budget_exhausted"` and the `channel`, attributed to the Pinchy user when the session or a linked channel account names one, otherwise to the agent.

The plugin reuses a `blocked: false` answer for the same agent for 15 seconds and never reuses a block, so raising a budget reopens the agent on the next message. When this endpoint can't be reached or answers with an error, the plugin lets the run through — unless its last answer for that agent was a block, which then stands — and waits 10 seconds before asking again. It logs one warning per outage in the agent runtime's log, and says so when the endpoint answers again.

`sessionKey`, `channel`, `senderId` and `trigger` only shape the audit row. One that isn't a string or is too long (500, 100, 200 and 100 characters) is dropped, not rejected: an error answer lets the run through, so rejecting an audit detail would switch the budget off.

**Errors:**

- `400` — `agentId` missing, empty, or longer than 200 characters
- `401` — gateway token missing or wrong. The plugin lets every run through until the token matches again and says in its log that blocking budgets are not enforced.

### `POST /api/settings/providers/openai-compatible`

Add or update an OpenAI-compatible provider. See [OpenAI-compatible providers](/guides/llm-providers/#openai-compatible-providers).

**Request body:**

| Field            | Type     | Required | Description                                                                                                                                                                                                                                                                                                        |
| ---------------- | -------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `id`             | uuid     | No       | Omit to create, pass to update                                                                                                                                                                                                                                                                                     |
| `displayName`    | string   | Yes      | Name on the provider tile, up to 120 characters                                                                                                                                                                                                                                                                    |
| `baseUrl`        | string   | Yes      | Endpoint that speaks the OpenAI API, up to 2048 characters. Rejected if it resolves to a loopback, link-local/metadata or reserved address; a private-network address only when `PINCHY_PROVIDER_BLOCK_PRIVATE_NETWORKS=1` (see [Which base URLs are allowed](/guides/llm-providers/#which-base-urls-are-allowed)) |
| `apiKey`         | string   | No       | Omit on update to keep the stored key. Required when the update changes `baseUrl`                                                                                                                                                                                                                                  |
| `manualModelIds` | string[] | No       | Model ids to fall back on when the endpoint's live discovery returns none                                                                                                                                                                                                                                          |

The stored key is bound to the base URL it was entered for — scheme, host, port **and path**, because a shared gateway host routes by path. Only a trailing slash and the letter case of the host are ignored. An update that changes `baseUrl` without a fresh `apiKey` is rejected with `422` and an `apiKey` field error before any request is made, and the refusal is written to the audit trail as a failed `config.changed` row — the stored key is never sent to a new address.

An update is saved only if the provider still has the base URL and key it was checked against when the request arrived. Live model discovery runs in between, against the address you submitted, and can take a few seconds; if another save changed the base URL or the key in that time, nothing is written and the request answers `409`.

**Errors:**

- `400` — invalid body, e.g. a `baseUrl` that is not an http(s) URL or longer than 2048 characters
- `404` — no provider with that `id`, or it was deleted while this update was being saved
- `409` — the provider changed while this update was being saved; reload and try again
- `422` — the base URL is not allowed, the update changes `baseUrl` without a fresh `apiKey`, or a new provider's endpoint lists no models and no `manualModelIds` were given

The key is encrypted at rest and never written into the OpenClaw configuration in plaintext — see [Secret handling](/security/secrets/).

## Domain Lock (admin only)

### `GET /api/settings/domain`

Get the current domain lock status, together with the hostname and scheme this request arrived on — which is what the UI compares against to tell you whether locking is safe right now.

**Response:**

```json
{
  "domain": "pinchy.example.com",
  "currentHost": "pinchy.example.com",
  "isHttps": true
}
```

`domain` is `null` when no domain is locked.

### `POST /api/settings/domain`

Lock Pinchy to a domain. **Takes no request body.** The domain is the hostname the request itself arrived on (the outermost hop of `X-Forwarded-Host`, falling back to `Host`), and that is deliberate: you can only lock Pinchy to an address you have just proven reachable, so a typo can't lock you out of your own instance. See [Lock Pinchy to a Domain](/guides/domain-lock/) for the full flow and safety guarantees.

The request must arrive over HTTPS (`X-Forwarded-Proto: https`).

What gets stored is the canonical form of that hostname — lower-cased, with a default `:443` dropped — because that is the same folding the host check applies when it later matches an incoming request. A proxy sending `Host: EXAMPLE.COM` or `example.com:443` therefore locks to `example.com`, and the response echoes the value that was actually stored. A port that is not the default is kept (`pinchy.example.com:8443`), since it is part of the name a browser sends.

**Response:** `{ "domain": "pinchy.example.com", "restart": true }`

`restart: true` is not advisory. The process exits half a second later so the secure-cookie settings take effect, and your container runtime restarts it — expect a few seconds of downtime and one dropped WebSocket.

**Errors:**

- `400` — the request did not arrive over HTTPS, no hostname could be determined, or the hostname is not a value a browser can send as `Host` (rejected before it is stored)
- `401` — not authenticated
- `403` — not an admin

### `DELETE /api/settings/domain`

Unlock the domain. Same restart behaviour as `POST`.

**Response:** `{ "removed": true, "restart": true }`

**Errors:**

- `400` — no domain is currently locked
- `401` — not authenticated
- `403` — not an admin

```json
{

}
```

**Errors:**

- `400` — the body is not `{}`
- `401` — not authenticated
- `403` — not an admin

### `DELETE /api/users/:id`

Deactivate a user (soft delete — sets banned status). Their sessions are deleted, and any chat WebSocket they have open is closed with code `4403` after an error frame (`code: "policy_account_deactivated"`) saying the account was deactivated; a frame that tab still sends is refused — so is a message the server accepted just before and had not yet dispatched — and the chat UI sends the tab to the login page instead of reconnecting. A tab that had no connection open at that moment (hidden, or reconnecting) gets no `4403`; its reconnects fail the handshake, and after the second failed one in a row it asks Better Auth's session lookup (`/api/auth/get-session`) and goes to the login page when there is no session. Every chat run Pinchy has in flight for the user is aborted on OpenClaw before the response, each recorded as `chat.run_aborted` with `reason: "account_deactivated"` and the admin as the actor. A run that was still waiting to be dispatched is not dispatched again. When an abort stops nothing or fails (`outcome: "failure"`) — OpenClaw may still be preparing the run, and can start it afterwards — Pinchy keeps aborting it by its runId after the response, with a growing pause up to two seconds and for at most a minute, until OpenClaw confirms an abort, reports the run over (`agent.wait`), or turns the dispatch away (`ok: false` on the `agent` request; nothing ran, and no further row is written). A run Pinchy dispatched again after OpenClaw failed the first attempt resolving its model is aborted under the new attempt's runId. A stop that took effect this way gets a second `chat.run_aborted` row with `outcome: "success"` and `followUp: "aborted_by_run_id"` (or `"stopped_before_dispatch"` for a run not dispatched again); a run OpenClaw reports finished is recorded as `chat.run_completed_after_disconnect`. A run whose abort OpenClaw confirmed never is. A run that is no longer in flight — its reply already ended, or a stop OpenClaw confirmed already stopped it — is left alone: no abort, no row. When OpenClaw's confirmation of a stop is still on its way as deactivation lands, the run is aborted again and that abort stops nothing; Pinchy waits briefly for the confirmation, and once it arrives, writes no row for deactivation's abort. Telegram replies already running and automations are not aborted — see [what deactivation doesn't stop](/guides/user-management/#what-deactivation-doesnt-stop). Their personal agents are removed from the shared view but the account record is retained and can be reactivated via `POST /api/users/:id/reactivate`.

**Response:** `200 OK`

```json
{
  "success": true
}
```

**Errors:**

- `400` — attempting to delete yourself
- `401` — not authenticated
- `403` — not an admin
- `404` — user not found

```json

```

**Errors:**

## Integrations (admin only)

External system integrations — **Odoo**, **email** (Gmail and Microsoft 365 via OAuth), and **Web Search**. See [Integrations](/concepts/integrations/) for the conceptual overview, [Connect Odoo](/guides/connect-odoo/) for the Odoo setup guide, and [Connect Email](/guides/connect-email/) for the email setup guide.

Every route below that accepts an Odoo URL — create, update, sync, `test-credentials`, `list-databases` and `sync-preview` — runs the same SSRF guard. An address literal is classified as it stands; a hostname is resolved first and **every** address it answers with is classified, so a name pointing at an internal address is refused exactly like the address itself. A name that does not resolve is allowed through — it is far more likely a typo, and the request fails on its own. `list-databases` is the exception: it sends its request to the address the guard just checked rather than looking the name up again, so a name with no answer is answered with `400` and `"Could not resolve the server's host name. Check the URL for a typo."`, and nothing is contacted. `ALLOW_PRIVATE_URLS=1` additionally allows the [private ranges](/reference/network-address-checks/#private-ranges) — RFC 1918, Tailscale's `100.64.0.0/10`, IPv6 unique-local and the rest — for an on-premise Odoo; loopback, link-local, cloud-metadata and reserved addresses stay refused either way. See [Odoo on your own network](/guides/connect-odoo/#odoo-on-your-own-network). An Odoo URL longer than 2048 characters is rejected with `400`.

Update a connection's name, description, or credentials. Credential fields you leave out keep their stored values, and the merged credentials are tested against the service before they are saved.

A stored secret never follows the connection to a new destination. If the update changes where the secret would be sent, the secret has to come in the same request:

| Type | Destination fields                                              | Secret to re-send |
| ---- | --------------------------------------------------------------- | ----------------- |
| Odoo | `url` (trailing slash ignored), `db` (exact, whitespace counts) | `apiKey`          |
| IMAP | `imapHost`, `imapPort`, `smtpHost`, `smtpPort`, `security`      | `password`        |

A credential update that the service rejects (`400`) or that loses a race against another save (`409`) changes nothing, and is written to the audit trail as a failed `integration.credentials_updated` row too.

- `404` — connection not found
- `409` — the credentials were changed concurrently; retry

### `POST /api/integrations/imap/test`

Try the settings without saving them. Both halves are exercised: an IMAP login and an SMTP handshake.

**Request body:**

| Field                  | Type   | Required | Description                                 |
| ---------------------- | ------ | -------- | ------------------------------------------- |
| `imapHost`, `imapPort` |        | Yes      | IMAP server (up to 253 characters) and port |
| `smtpHost`, `smtpPort` |        | Yes      | SMTP server (up to 253 characters) and port |
| `username`, `password` | string | Yes      | Mailbox credentials                         |
| `security`             | string | Yes      | `tls`, `starttls`, or `none`                |

**Response:** `200 OK` whether the probe passed or failed — a rejected login is a result, not a request error. Read `ok`, not the status code.

```json
{
  "ok": false,
  "imap": { "ok": true },
  "smtp": {
    "ok": false,
    "code": "refused",
    "message": "Connection refused — check the host and port"
  },
  "smtpPortProbe": [
    { "port": 465, "reachable": false },
    { "port": 587, "reachable": true },
    { "port": 25, "reachable": false }
  ],
  "suggestion": {
    "kind": "switch_smtp_port",
    "port": 587,
    "security": "starttls"
  },
  "error": "Connection refused — check the host and port"
}
```

Both legs always run, so a failing IMAP login never hides a firewalled SMTP port. A failing leg carries a `code` — one of `timeout`, `refused`, `dns`, `auth`, `tls`, `unknown`, or `blocked` when the host resolves to an address we refuse to probe (see [Mail servers on your own network](/guides/connect-email-imap/#mail-servers-on-your-own-network)) — plus a message that is safe to show a user. Those same codes land in the audit trail as `imapCode` / `smtpCode`, so what you see in the form is what an auditor can filter on later. See [Audit Trail](/concepts/audit-trail/).

`smtpPortProbe` and `suggestion` appear only when SMTP failed at the connection level (`timeout` or `refused`). Pinchy then checks 465, 587 and 25 for raw reachability. Port 25 is reported but never suggested — it is there to tell an outbound-firewall story, not to be switched to. So a suggestion is always 587 (STARTTLS) or 465 (implicit TLS), whichever answers and isn't the port that just failed. `{ "kind": "all_smtp_blocked" }` means neither 465 nor 587 answered, which usually points at an outbound firewall rather than at your settings. `"suggestion": null` means there's nothing better to offer: the port you're on answers a raw TCP probe and the other of the two doesn't, so the problem is above the connection layer. `error` is the banner text for the leg that failed, IMAP first — a broken login blocks reading mail entirely, which matters more than a send-side problem.

### `GET /api/internal/integrations/:connectionId/credentials`

**Internal** — authenticated with the shared OpenClaw gateway token (Pattern C in `agent-rules/secrets.md`), not a user session. Called by Pinchy plugins at runtime, never by the browser.

Returns the decrypted credentials for a connection, auto-refreshing an expired OAuth access token first (Google and Microsoft rotate refresh tokens differently — see the plugin cache/refetch behavior in the Secret Handling section of `AGENTS.md`). Called by `pinchy-email`, `pinchy-odoo` and `pinchy-web` with the gateway token as Bearer auth; the plugin caches the response, typically with a 5-minute TTL, and invalidates that cache when the third-party service answers `401`. A `401` from this route itself is retried for a few seconds instead: it means Pinchy briefly could not read the gateway token during a configuration change.

**The calling plugin must name its agent**: `?agentId=<id>` is required, and the request is refused unless that agent was actually granted the connection. The gateway token is one shared secret written into every plugin's config block, so on its own it identifies the container, not the caller — without this check any plugin could name any `connectionId` and receive a decrypted password. Odoo and mailbox connections are checked against the agent's integration grants; the instance-wide web-search connection is checked against the agent's `pinchy_web_search` tool grant, because it is deliberately shared by every agent and has no per-agent grant rows. `pinchy_web_fetch` alone does not grant it: fetching a page needs no key, so a fetch-only agent is refused the Brave Search key like any other agent without a grant.

| Query parameter | Required | Description                                |
| --------------- | -------- | ------------------------------------------ |
| `agentId`       | yes      | The agent the calling plugin is acting for |

| Status | Meaning                                                                                                                                        |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `200`  | Credentials returned                                                                                                                           |
| `400`  | `agentId` missing, longer than 128 characters, or containing anything but letters, digits, `-` and `_` (no audit row: malformed, not denied)   |
| `401`  | Gateway token missing or wrong; the plugins retry it for about 3.75 s before giving up                                                         |
| `403`  | The agent is not granted this connection, the connection is still `pending`, or its stored Odoo URL / IMAP / SMTP host fails the address check |
| `404`  | The connection no longer exists — the body says so in words an admin can act on, because plugins surface it into the tool error                |
| `500`  | The stored credentials could not be decrypted under the current encryption key                                                                 |
| `503`  | An OAuth access token expired and the app's OAuth settings are gone, so it cannot be refreshed. Deliberately not a `200` carrying stale tokens |

**The stored destination is checked before credentials leave.** An Odoo connection's URL and an IMAP connection's IMAP and SMTP hosts are run through the same address check as when the connection was saved ([Odoo on your own network](/guides/connect-odoo/#odoo-on-your-own-network), [Mail servers on your own network](/guides/connect-email-imap/#mail-servers-on-your-own-network)), under the rules and switches as they are now. A refusal is a `403` whose `error` names the field and the fix — deliberately not a `401`, which the plugins would retry for several seconds before surfacing this final refusal.

A refusal for a missing grant or a refused destination writes an `integration.credentials_denied` audit row naming the agent and the connection — see [Audit Trail](/concepts/audit-trail/). A successful fetch is not audited: plugins re-fetch on every cache miss, so a row per success would be volume without signal.

### `POST /api/internal/integrations/:connectionId/report-auth-failure`

**Internal** — authenticated with the shared OpenClaw gateway token, not a user session. Called by Pinchy plugins at runtime, never by the browser.

Reports a permanent authentication failure (expired API key, revoked OAuth grant) detected by a plugin at call time. ## Enterprise License

### `GET /api/enterprise/status`

Get the current enterprise license status and seat usage. Any authenticated user can call this endpoint (non-admins see it too, so the UI can show licence-gated features correctly).

**Response:**

```json
{
  "enterprise": true,
  "type": "paid",
  "org": "Acme Corp",
  "expiresAt": "2027-01-15T00:00:00.000Z",
  "daysRemaining": 263,
  "managedByEnv": false,
  "seatsUsed": 7,
  "maxUsers": 10
}
```

| Field           | Type           | Description                                                                                                                                                |
| --------------- | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `enterprise`    | boolean        | Whether an active enterprise license is present                                                                                                            |
| `type`          | string \| null | `"trial"` or `"paid"`. `null` when no license is active.                                                                                                   |
| `org`           | string \| null | Organisation name encoded in the license token. `null` when no license is active.                                                                          |
| `expiresAt`     | string \| null | ISO 8601 expiry timestamp. `null` for non-expiring tokens or when no license is active.                                                                    |
| `daysRemaining` | number \| null | Days until the key expires, rounded up: a key with hours left counts as `1`, `0` means expired. `null` when the key has no expiry or no license is active. |
| `managedByEnv`  | boolean        | `true` when the key comes from the `PINCHY_ENTERPRISE_KEY` environment variable (read-only in the Settings UI)                                             |
| `seatsUsed`     | number         | Number of seats currently in use: active users + valid pending invitations                                                                                 |
| `maxUsers`      | number         | Maximum seats allowed by the license. `0` means unlimited.                                                                                                 |

**Seat cap behaviour:** the seat cap is a **soft cap with a 20% grace window**. When `maxUsers > 0`, invites keep working up to `floor(1.2 * maxUsers)` seats (for example 12 on a 10-seat license); in the 100–120% grace band admins see a notice but invites still succeed and nothing is blocked. Only when `seatsUsed >= floor(1.2 * maxUsers)` is the **Invite User** button disabled and the API rejects new invitations with `403` (the response includes `graceCap`). Existing users are never affected. See [Enterprise Setup — Seat cap enforcement](/guides/enterprise-setup/#seat-cap-enforcement) for the full explanation.

**Errors:**

- `401` — not authenticated

### `PUT /api/enterprise/key`

Save or update the enterprise license key. **Admin only.** Not available when the key is managed via the `PINCHY_ENTERPRISE_KEY` environment variable (`managedByEnv: true`).

**Request body:**

| Field | Type   | Required | Description           |
| ----- | ------ | -------- | --------------------- |
| `key` | string | Yes      | The JWT license token |

The key is verified **before** it is stored. A key Pinchy refuses is never written, so a rejected attempt — a typo, an expired token, a key from another install — leaves the license you already had in place and active. There is nothing to restore and no window in which the instance drops to community.

**Response:** the status of the key that was just accepted, which takes effect immediately without a restart. These five fields carry the same meaning as in `GET /api/enterprise/status`, which returns the fuller picture (`state`, `seatsUsed`, `managedByEnv`, …):

```json
{
  "enterprise": true,
  "type": "paid",
  "org": "acme-gmbh",
  "expiresAt": "2027-06-01T00:00:00.000Z",
  "daysRemaining": 300
}
```

`daysRemaining` counts from the moment of the request and rounds up, so a 7-day key issued today reads `7`. It moves while `expiresAt` stays put.

**Errors:**

- `400` — the key is missing, or Pinchy does not accept it: a bad signature, an issuer that is not ours, an expired token, or a valid token that does not carry the `enterprise` feature (nothing is stored; the previous key stays active)
- `401` — not authenticated
- `403` — not an admin
- `409` — the key is managed by the `PINCHY_ENTERPRISE_KEY` environment variable and cannot be changed here

## Tool Confirmations

The human-in-the-loop checkpoint an admin can put in front of a tool — see [Require Confirmation Before a Tool Runs](/guides/tool-confirmation/). Which tools are gated is per-agent configuration, stored under `pinchy-approvals.confirmTools` in the agent's `pluginConfig` and written through `PATCH /api/agents/:agentId`.

### `GET /api/approvals`

Your own pending confirmations, newest first — the source for the in-app confirmation cards. Returns only requests where you are the requester and that have not expired; a confirmation is personal and never appears in a teammate's list, even on a shared agent. A confirmation that is settled while the list is being read is left out rather than listed without its arguments, so every listed confirmation that is not in `known` carries its `argsSummary`.

**Query parameters:**

| Parameter | Description                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `known`   | Optional. Comma-separated ids of confirmations you already hold. They are listed as usual but **without** `argsSummary`, which never changes once stored and can be large (0.5–1.5 MB of JSON in the worst case, the upper end for non-Latin text), so a client that polls this list receives each summary only once. Anything that is not an id is ignored, and at most 200 ids are read; a confirmation past that is listed with its summary again. |

**Response:**

```json
{
  "approvals": [
    {
      "id": "b1f4…",
      "agentId": "agt_…",
      "agentName": "Smithers",
      "toolName": "email_send",
      "argsSummary": { "to": "ada@example.com", "subject": "Q3 numbers" },
      "sessionKey": "agent:agt_…:direct:usr_…",
      "createdAt": "2026-08-01T09:12:44.000Z",
      "expiresAt": "2026-08-01T09:22:44.000Z"
    }
  ]
}
```

`argsSummary` is a faithful, redacted rendering of the tool's arguments so you can decide in context — always of the whole call. Arrays and objects keep their real contents and every value keeps its JSON type. A call that does not fit — more than 100 keys in an object, 200 items in a list or addresses in a recipient field, nesting deeper than ten levels, a string longer than 200,000 characters (code points, as sent), a key longer than 100 characters, more than 512,000 characters in all (counted as rendered: every string with its markers, every key label, every number, boolean or `null` by its JSON length, and 2 per array or object), or a collapsed card that would cost more than 16,384 to draw (one for every key, value and note the card draws, plus one for each of their characters and 128 for a character outside the Basic Multilingual Plane, such as an emoji — except the Mathematical Alphanumeric Symbols, U+1D400–U+1D7FF, which browsers lay out like letters and which count one; a previewed string counts by its preview — what a character costs the browser to lay out varies by orders of magnitude, and an emoji's font lookup is the costliest) — gets no pending confirmation at all: the gate refuses it, tells the agent which limit was crossed and at which path (such as `values.comment`), suggests splitting the call only where that can help (too many keys, items or recipients, too much in all, or too costly to draw), and writes an `approval.refused` audit entry. So no listed confirmation has anything left out. Strings are kept as sent — never trimmed or whitespace-collapsed — except that a CR LF pair becomes a line feed, and that a run of four or more spaces, line breaks or tabs becomes `⟨N spaces⟩` / `⟨N line breaks⟩` / `⟨N tabs⟩`, and every invisible or blank-rendering character (controls other than tab and line feed, a lone UTF-16 surrogate, format characters such as bidi overrides and Unicode tag characters, every space separator other than U+0020, variation selectors and the other default-ignorables such as the Hangul fillers, and the braille blank U+2800) is shown as a `⟨U+XXXX⟩` marker, with a run of more than three of one character shown as one `⟨N × U+XXXX⟩` marker; a run of different characters names each one, so no two strings share a rendering. A literal `⟨` or `⟩` is always shown as `⟨U+27E8⟩` / `⟨U+27E9⟩`, so every `⟨` in a summary string opens a marker and no marker contains a bracket. U+200C, U+200D, U+FE0E and U+FE0F are marked like the rest, everywhere — in Arabic-script and Indic text (`گزارش⟨U+200C⟩ها`, `க்⟨U+200C⟩ம`) and inside emoji (`👨⟨U+200D⟩👩⟨U+200D⟩👧`, `❤⟨U+FE0F⟩`), since whether one draws anything depends on the script and on the approver's fonts, not on the server's Unicode data. The file tools accept all four anywhere in a path; the email tools accept all four in a display name, never in an address. A combining mark (`\p{M}`) is kept only on a letter it is written with — a letter of one of its scripts (the Unicode property `Script_Extensions`), or any letter for a mark of every script (`Zinh`, such as U+0336) — directly or through marks that are; every other one, at the start, after a space, digit, `/`, punctuation or marker, or on another script's letter, is shown as a `⟨U+XXXX⟩` marker (`⟨U+05BC⟩בא`), because a mark with no base of its own is drawn onto its neighbour and `ּבא` renders like `באּ`. The file tools accept such a mark in a path, and the email tools in a display name: the card marks it. The stored strings carry no direction controls: Pinchy's card draws each one in stored order (each line in `<bdo dir="ltr">`, each run of right-to-left words in a `<bdi dir="ltr">`, where a word is letters, their marks and the non-letters whose bidi class is R or AL, plus a `"` or `'` between two such characters), because left to itself the bidi algorithm draws `/data/חוזים/2024.md` and `/data/2024/חוזים.md` alike — a client that renders `argsSummary` itself should do the same. A string under a recipient or target key, and an email- or URL-shaped string at any key, is drawn whole up to 8,192 characters as drawn; every other string longer than 200 characters (and a longer one of those) is stored as a `previewed` node (below) and shown as a preview, with the rest on demand a part at a time, only one part drawn at once: Chromium lays out a long mixed-direction text in time that grows faster than its length, and drawn whole, one 200,000-character value froze the tab for 13 seconds, and again on every relayout. Under a target key, and anywhere inside one, a space, tab or line feed at the start or end of a string is marked too (`/data/out/report.md⟨U+0020⟩`; a run of four or more still reads `⟨N spaces⟩`). Keys are never merged: a key that is not a plain identifier (`[A-Za-z0-9_.-]`) appears quoted and escaped, such as `"to "`, and keys are unique. `to`, `cc` and `bcc` are split into one entry per address (a single address stays a single entry, not a list). Recipient keys and target keys (`model`, `ids`, `id`, `path`, `filename`, `url`, `target`, …) are summarized before any other key.

What Pinchy says **about** a value is never written into its text: a string in `argsSummary` is always the value's own text, and every annotation is a separate **node** — an object with the key `@`, which no summarized object can have, because a key is shown bare only when it is a plain identifier and quoted (`"@"`) otherwise. Written into the text, `(record reference: res.partner #7 "Acme GmbH")` would read exactly like a string an agent could send instead, which pinchy-odoo resolves as a record **name**. There are four nodes:

| Node                                                       | Replaces                                                                                                           | Fields                                                                                                                                                                                                                                                                                                                                                                              |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `{"@": "ref", "model", "id", "label", "labelCut"}`         | An opaque Odoo reference that decodes — only when the string is exactly the reference, nothing before or after it. | The record it names. `label` is the record's display name, rendered like any string and cut at 200 characters; `labelCut` says how many more there were (`0` if none), and a cut label does not make the call too large, because the reference acts on `<model> #<id>`, which is always whole.                                                                                      |
| `{"@": "secret", "length"}`                                | A string under a secret-looking key, or anywhere inside an array or object under one.                              | The value's length in characters; the value itself is never stored.                                                                                                                                                                                                                                                                                                                 |
| `{"@": "noted", "text", "notes"}`                          | A string Pinchy has something to say about.                                                                        | `text` is the value, rendered like any string — a string, or a `previewed` node where the value is previewed; `notes` is a non-empty list of `{"kind": "host", "host"}`, `{"kind": "not-a-domain", "host"}` or `{"kind": "name", "name"}`, where `name` is a string or a `previewed` node too, and a `not-a-domain` note's `host` is the host as written, rendered like any string. |
| `{"@": "previewed", "text", "preview", "parts", "inside"}` | A string the card shows as a preview.                                                                              | `text` is the value, rendered like any string. `preview` is where the preview ends and `parts` where each part **Show full text** reveals ends — UTF-16 offsets into `text`, the last part ending at its length; `inside` lists the offsets among them that fall inside one grapheme cluster.                                                                                       |

A recipient entry with a display name is a `noted` node with a `name` note (`{"@": "noted", "text": "ada@example.com", "notes": [{"kind": "name", "name": "Ada Lovelace"}]}`); a non-ASCII domain adds a `host` note with its punycode form, in a recipient field and in any other string that is one mailbox, at any key and depth — read the way the mail tools read one: trimmed, and taken out of `Name <address>`, so `Boss <boss@fіrma.at>` and ` boss@fіrma.at` are noted too. Any string the WHATWG URL parser (`new URL`, what the web tools use) accepts with a scheme that has a host (`http`, `https`, `ws`, `wss`, `ftp`, `file`) is a URL, whatever its shape — `https:fіrma.at`, `https:\\fіrma.at\x` and a leading control character included — and gets a `host` note with the host the parser resolves whenever its text does not show exactly that host right after `scheme://` (ASCII case aside), or carries userinfo: `https://fіrma.at` → `xn--frma-l9d.at`, `https://fіrma.at\@evil.com/x` → `xn--frma-l9d.at`, `https://fir%6Da.at/` → `firma.at`, `https://firma.at@evil.com` → `evil.com`. A string the parser refuses is not a URL and gets no note — unless it has such a scheme and a host that Node's parser refuses but Chromium and WebKit open: an all-ASCII host with a label such as `xn--a` that does not decode. That host is read the way the WHATWG parser reads it, tabs and line breaks deleted and percent-encoding decoded, and whatever follows it — a space or a tab in the path, words after it — does not matter: `https://xn--a.evil.com/x y`, `ht\ttps://xn--a.evil.com/` and `https://u@xn--a.evil.com/ see above` all reach `xn--a.evil.com`. Such a string gets a `not-a-domain` note, like a mailbox whose domain Node's `domainToASCII` rejects. The note names that host as written (ASCII case aside, every hidden character marked) — there is no resolved form to name — and Pinchy's card draws it beside the value, quoted and escaped, and counts it in the draw cost, so two previewed values that differ only in that host draw two different cards; the approval request text names it too. A host a browser refuses too — `https://xn--a.evil.com see above`, where the space sits in the host — gets none. A URL or mailbox string (a recipient entry included) that is previewed always gets a `host` note, even when its host is plain ASCII and reads as it resolves, because the host at its end would be hidden behind the preview. A string is previewed, counted in characters as drawn (a string that would read as a JSON literal is drawn quoted and escaped), when it is longer than 200 characters, unless it sits under a recipient or target key or is email- or URL-shaped as a whole (the parser accepts it with nothing after it, or it is one mailbox) and is at most 8,192 characters long. So a URL with words after it, or one whose stored text holds a count marker such as `⟨4 × U+200B⟩` (which has spaces in it), is previewed past 200 characters and noted.

Every decision about how a string is shown is made by Pinchy's server when it builds the summary, and stored: whether it is previewed, where the preview ends — at most 200 characters as drawn, cut back to a grapheme-cluster boundary and never inside a `⟨…⟩` marker or an escape — and where each part ends: after a space where one fits, else between two grapheme clusters, where its characters would cost more than 8,192 by the draw count above. The draw count charges exactly that preview. Whether a string is a URL is answered by Node's URL parser, the one the web tools fetch with, and where a character ends by Node's `Intl.Segmenter`; browsers answer both differently — Chromium and WebKit accept hosts such as `xn--a` that Node refuses, and Firefox before version 125 has no `Intl.Segmenter` — so Pinchy's card answers neither and draws exactly the stored cuts, the same in every browser. A plain string is drawn whole, and the summary stores none longer than 8,192 characters as drawn. A string that does not decode as a reference, or that carries anything past one (padding, a line break, more text), is kept as the text it is, and counted against the limits like any other; pinchy-odoo refuses such a string as a reference too. Numbers, booleans and `null` under a secret-looking key are shown, and a key ending in `_id` or `_ids` is never treated as secret-looking, since it holds record ids.

A client that renders `argsSummary` itself must draw a node apart from any text — Pinchy's card draws each annotation as a label of its own beside the value, outside any preview of a long text — and keep them apart for assistive technology too: Pinchy's card exposes each string value as its `"`-quoted, escaped text (the drawn copy is `aria-hidden`) and each annotation as a `role="note"` element whose text starts with "Pinchy note:", and quotes and escapes a ref's `label`. It should treat an object with an `@` key it does not recognize, or a node missing a field, as a value it cannot show, never as fields; Pinchy's card does the same for a plain string longer than 8,192 characters as drawn, rather than guess where to cut it, and for a `previewed` node whose cuts draw more than the server's own would — a preview longer than 200 characters as drawn, a part costing more than 8,192 by the draw count, or a cut inside a `⟨…⟩` marker. Confirmations stored before nodes existed carry no nodes; they expire within ten minutes.

### `POST /api/approvals/:id/decision`

Approve or deny one of your own pending confirmations. The agent's tool call is held open while the confirmation is pending, so the decision is handed straight to it: on approve the agent resumes the same turn and runs the tool, on deny it is told no. Nobody has to prompt the agent again.

**Request body:**

| Field      | Type   | Required | Description                                                                                                  |
| ---------- | ------ | -------- | ------------------------------------------------------------------------------------------------------------ |
| `decision` | string | Yes      | `approve` or `deny`                                                                                          |
| `reason`   | string | No       | Why, up to 500 characters — recorded in the audit row, with any email address replaced by `<email-redacted>` |

**Response:**

```json
{
  "ok": true,
  "status": "approved",
  "resumed": true
}
```

| Field         | Type    | Description                                                                                                                                                               |
| ------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `status`      | string  | The confirmation's new state — `approved` or `denied`                                                                                                                     |
| `resumed`     | boolean | Whether the decision reached the waiting tool call. `false` means the decision is recorded but the agent never heard it, so the tool did **not** run                      |
| `resumeError` | string  | Present only when `resumed` is `false` — why, in words you can show the user (the agent had already stopped waiting, or the agent runtime was unreachable at that moment) |

A failed delivery is still a `200`: the decision itself is persisted, and retrying would only return `409`. Clients must read `resumed` rather than treat `ok` as "the action ran".

**Errors:**

- `403` — you are not the requester. Only the person who triggered the action can confirm it (four-eyes approval by a different admin is a planned extension, [#124](https://github.com/heypinchy/pinchy/issues/124))
- `403` — `code: "personal_agent_disabled"`: you asked to **approve** a confirmation on your own personal agent while an admin has turned members' personal agents off. Approving would resume the run. Denying is always allowed
- `404` — no such request
- `409` — the request is no longer pending: already decided, already consumed, or expired

### `POST /api/internal/approvals/gate-check`

**Internal** — authenticated with the shared OpenClaw gateway token (Pattern C in `agent-rules/secrets.md`), not a user session. Called by the `pinchy-approvals` plugin's `before_tool_call` hook, never by the browser.

This is the server-side security boundary for the whole feature. The plugin asks it about every tool call; the route loads the agent's policy, allows anything ungated without recording a thing, and otherwise either spends an approved single-use grant (`allow`) or records a pending confirmation and blocks (`block`). Keeping the policy here rather than in plugin config is what makes a permission change take effect on the next call instead of after a cache expires.

**Request body:**

| Field        | Type   | Required | Description                                                                                   |
| ------------ | ------ | -------- | --------------------------------------------------------------------------------------------- |
| `agentId`    | string | Yes      | The agent making the call                                                                     |
| `sessionKey` | string | No       | The OpenClaw session, which identifies the acting person; a gated call without one is blocked |
| `toolName`   | string | Yes      | The tool the agent wants to run                                                               |
| `params`     | object | No       | The tool's arguments; hashed into the grant's digest, never stored                            |
| `senderId`   | string | No       | The channel-side sender, when one is known                                                    |

**Response:**

```json
{
  "decision": "block",
  "requestId": "b1f4…",
  "reason": "This action needs the user's confirmation before it can run. A confirmation card is waiting for them in Pinchy. …"
}
```

The `reason` is written for the model, which relays it to the person in the chat — so it names the action, says where to act, and tells the model to stop rather than retry. It deliberately carries no request id: `/approve <id>` is a real OpenClaw command for OpenClaw's own approvals, and given an id a model will invent it, handing the user an instruction that fails. The id travels in `requestId`, where the plugin reads it.

A grant is bound to the agent, the person, the session, the tool **and** a sha256 of the exact arguments, and is spent on first use — so a changed recipient or a different tool asks again. The route fails closed: if the acting person cannot be resolved to a Pinchy user — or the call arrives from a run with no session at all, which a grant could not be bound to — it is blocked rather than allowed, because only a real user can confirm it. The plugin applies the same rule to this endpoint being unreachable.

A blocking answer that opens a confirmation also carries `approval: {title, description}` — the request text every approval surface shows, at most 80 and 256 characters. When the description has to be cut, it names every server and mail domain the call reaches before the arguments, each by its last 100 characters. A call whose servers don't all fit gets no confirmation: it is refused like a call too large for the card, with `exceeded: "too-many-hosts"` in its `approval.refused` entry and a reason telling the agent to split it. A call too large for the card is refused before that, and carries no `approval` either.

One person can have at most **20 confirmations open on one agent** at a time. Past that the route blocks with a reason saying so and opens nothing: a changed argument otherwise mints a new confirmation per attempt, and an agent that retries in a loop would bury the requester's inbox. Consuming a grant the user already approved is never subject to the cap.

**Errors:**

- `401` — gateway token missing or wrong

### `POST /api/internal/approvals/resolution`

**Internal** — same gateway-token authentication as `gate-check`, called by the same plugin, never by the browser.

Reports what the agent runtime finally did with a call it had held open. This is not a second decision endpoint: it is the runtime's account of the outcome, and it is the only channel for two things the decision route cannot carry — the resolutions nobody clicks (the run stopped waiting, or was cancelled), and the moment an approved grant is actually spent. An approved call resumes inside the runtime's own hook and never reaches `gate-check` again, so nothing else would record it.

**Request body:**

| Field        | Type   | Required | Description                                                                                                                                                                                         |
| ------------ | ------ | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `toolCallId` | string | Yes      | The call the confirmation was holding up                                                                                                                                                            |
| `sessionKey` | string | No       | The conversation that call belongs to. A tool call id is only unique per response on some model backends, so this is what keeps a report from closing a confirmation in someone else's conversation |
| `decision`   | string | Yes      | `allow-once`, `allow-always`, `deny`, `timeout` or `cancelled`                                                                                                                                      |

**Response:**

```json
{
  "ok": true,
  "settled": true,
  "status": "consumed"
}
```

`settled: false` means the report changed nothing, which is the ordinary case rather than an error: the user's own decision had already closed the confirmation, or the call was never Pinchy's — the same approval machinery carries the agent runtime's own requests. Nothing is written to the audit trail in that case, because a second row for the same act would double-count it.

**Errors:**

- `401` — gateway token missing or wrong

## Audit Trail (admin only)

### `GET /api/audit`

Retrieve a paginated, filterable audit log. **Admin only.**

**Query parameters:**

| Parameter   | Type   | Default | Description                                                   |
| ----------- | ------ | ------- | ------------------------------------------------------------- |
| `page`      | number | 1       | Page number                                                   |
| `limit`     | number | 50      | Entries per page                                              |
| `eventType` | string | —       | Filter by event type (e.g., `auth.login`, `tool.pinchy_read`) |
| `actorId`   | string | —       | Filter by user ID                                             |
| `status`    | string | —       | `success` or `failure`; an unrecognized value is ignored      |
| `from`      | string | —       | Start date (ISO 8601)                                         |
| `to`        | string | —       | End date (ISO 8601)                                           |

**Response:**

```json
{
  "entries": [
    {
      "id": 1,
      "timestamp": "2026-02-21T10:00:00.000Z",
      "actorType": "user",
      "actorId": "user-uuid",
      "actorName": "Alice",
      "actorDeleted": false,
      "eventType": "auth.login",
      "resource": "user:user-uuid",
      "resourceName": "Alice",
      "resourceDeleted": false,
      "outcome": "success",
      "error": null,
      "detail": {},
      "rowHmac": "sha256-hex-string"
    }
  ],
  "total": 142,
  "page": 1,
  "limit": 50
}
```

`actorName` is resolved when the log is read: a user's current name, an agent's current name for `actorType: "agent"` rows, the key's name for `api_key` rows (snapshotted into `detail` when the row was written), and a readable label for `system` rows (for example `"Scheduled reindex"` for `kb-index-scheduler`). It is `null` when nothing resolves — an erased user, or an agent that no longer exists. `actorDeleted` is `true` for a deactivated user or a deleted agent. `actorId` is always the raw value the row was written with.

`outcome` is one of `"success"` or `"failure"`. `error` is `null` for successes and a short error message for failures (e.g. `"seat_cap"` on a blocked invite). Both fields are part of the HMAC-signed v2 row shape.

`total` is only present in the response for `page=1`. A request for `page > 1` omits the field entirely rather than recomputing it — the audit log is append-only and can grow unbounded, so counting it on every page view is wasteful once a client already has the number from its page-1 fetch. Callers that page through results should keep the `total` from their first response and not expect it on later pages.

On an unfiltered `page=1` request, `total` is an **estimate** read from Postgres's own planner statistics (`pg_class.reltuples`) rather than an exact `count(*)`, so it may lag slightly behind the true row count (bounded below by the number of entries the same response returns). Any filtered request (`eventType`, `actorId`, `from`, `to`, or `status`) still gets an exact count.

**Errors:**

- `401` — not authenticated
- `403` — not an admin

### `GET /api/audit/verify`

Verify the integrity of audit log entries by recomputing HMAC signatures. **Admin only.**

**Query parameters:**

| Parameter | Type   | Default | Description                                      |
| --------- | ------ | ------- | ------------------------------------------------ |
| `fromId`  | string | —       | Start verification from this entry ID (optional) |
| `toId`    | string | —       | End verification at this entry ID (optional)     |

**Response:**

```json
{
  "valid": true,
  "totalChecked": 142,
  "invalidIds": [],
  "chainBreakIds": [],
  "previousKeyIds": []
}
```

| Field            | Description                                                                                                                                                                                                                                     |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `valid`          | `true` when `invalidIds` and `chainBreakIds` are both empty                                                                                                                                                                                     |
| `totalChecked`   | Number of entries verified                                                                                                                                                                                                                      |
| `invalidIds`     | IDs of entries whose signature doesn't match their content, or that only verify under an earlier key although they come after the key change                                                                                                    |
| `chainBreakIds`  | IDs of entries whose own signature matches but whose link to the previous entry doesn't: an entry before them was deleted, or entries were reordered                                                                                            |
| `previousKeyIds` | IDs of entries signed with an earlier `AUDIT_HMAC_SECRET`, before the key changed. They're authentic and don't affect `valid`; see [Rows signed with an earlier secret](/concepts/audit-trail-verification/#rows-signed-with-an-earlier-secret) |

If tampered entries are found, `valid` is `false`, and `invalidIds` and `chainBreakIds` say which entries and how.

A range that starts at `fromId` takes its key context from the entry immediately before it. If that entry verifies under the current signing key, the key changed before the range starts, and an entry in the range that only verifies under an earlier key is reported in `invalidIds` rather than as signed with an earlier secret. The same goes for an entry that verifies under no key at all or carries a signature version Pinchy doesn't know: the range treats the key change as already behind it. That's why a spot check can list entries in `invalidIds` that a full verification lists in `previousKeyIds`. Only a verification without `fromId` establishes where the key actually changed. See [Rows signed with an earlier secret](/concepts/audit-trail-verification/#rows-signed-with-an-earlier-secret).

**Errors:**

- `401` — not authenticated
- `403` — not an admin

### `GET /api/audit/verify/status`

Report the health of the periodic verify job without re-scanning the log. **Admin only.**

**Response:**

```json
{
  "lastStatus": "ok",
  "lastVerifiedId": 4821,
  "lastRunAt": "2026-07-28T09:14:02.417Z",
  "lastViolationAt": null
}
```

| Field             | Description                                                                                                  |
| ----------------- | ------------------------------------------------------------------------------------------------------------ |
| `lastStatus`      | Outcome of the most recent sweep: `ok`, `violation`, or `never_run` if no sweep result has been recorded yet |
| `lastVerifiedId`  | Highest audit entry ID the job has verified so far                                                           |
| `lastRunAt`       | When a sweep last advanced the checkpoint, or `null` if none ever has                                        |
| `lastViolationAt` | When an integrity violation was last recorded, or `null` if none ever was                                    |

Read both status fields. `lastStatus` describes the most recent sweep only — the job advances past a tampered range on purpose, so a later sweep over intact rows reports `ok` again. `lastViolationAt` is derived from the append-only `audit.integrity_check` failure entries and is never cleared, so it answers whether the log was ever found tampered with. Both survive a restart; nothing here is held in process memory.

`lastRunAt` is not a liveness check. A sweep that finds nothing new to verify returns without touching the checkpoint, so on a quiet instance this timestamp legitimately sits hours behind the job's last run. It answers "verified up to here, at this time", not "the job is still ticking".

This is intentionally not part of the unauthenticated `/api/health` endpoint: telling an anonymous caller that tampering was detected also tells an attacker that they were noticed.

**Errors:**

- `401` — not authenticated
- `403` — not an admin

### `POST /api/audit/background-run`

Report that a chat run finished while the user was away from the chat page. Called by the chat UI, not by agents — it writes one `chat.background_run_completed` audit entry for the named agent.

**Request body:**

| Field        | Type   | Required | Description                                                     |
| ------------ | ------ | -------- | --------------------------------------------------------------- |
| `agentId`    | string | Yes      | Agent the run belongs to. The caller must have access to it.    |
| `durationMs` | number | Yes      | Wall-clock run duration, in milliseconds. Capped at 10 minutes. |

**Response:** `204 No Content`. Returns `400` if `durationMs` is negative or above the cap, and `404` if the agent doesn't exist **or** the caller has no access to it — one answer for both, so this endpoint cannot be used to probe which agent IDs are real.

### `GET /api/audit/export`

Export the audit log as a CSV or PDF file. Supports the same filters as `GET /api/audit`, plus `resource`. Unlike the list route, an unrecognized `status` here is a `400` rather than being ignored — the export URL is meant to be scripted, so a typo should be reported instead of silently returning everything. **Admin only.**

**Query parameters:**

| Parameter   | Type   | Default | Description                                  |
| ----------- | ------ | ------- | -------------------------------------------- |
| `format`    | string | `csv`   | `csv` or `pdf`                               |
| `eventType` | string | —       | Filter by event type                         |
| `actorId`   | string | —       | Filter by user ID                            |
| `resource`  | string | —       | Filter by resource (e.g. `agent:agent-uuid`) |
| `status`    | string | —       | `success` or `failure`                       |
| `from`      | string | —       | Start date (ISO 8601)                        |
| `to`        | string | —       | End date (ISO 8601)                          |

**Response:** `200 OK` with `Content-Type: text/csv` or `application/pdf` and `Content-Disposition: attachment; filename="audit-log-<timestamp>.<ext>"`.

The export is capped at 100,000 rows — `audit_log` grows without bound, and an unbounded export risks exhausting the container's memory. When more rows match the filters than the cap, the response carries an `X-Audit-Export-Truncated: true` header, the CSV gets one trailing note line describing the cap, and the PDF prints a truncation notice below its header. Narrow the filters (date range, event type, actor) and export again to see the rest.

**Errors:**

- `400` — unsupported `format` or `status` value, or an invalid `from`/`to` date
- `401` — not authenticated
- `403` — not an admin

### `POST /api/users/me/password`

Change your own password.

**Request body:**

| Field             | Type   | Required | Description                      |
| ----------------- | ------ | -------- | -------------------------------- |
| `currentPassword` | string | Yes      | Current password                 |
| `newPassword`     | string | Yes      | New password (min 12 characters) |

**Response:** `{ "success": true }`

A successful change **revokes every session the user holds** and issues a replacement for the caller, returned as a `Set-Cookie` on this response. A client that discards it will be unauthenticated on its next request.

**Errors:**

- `400` — missing fields or new password too short
- `401` — not authenticated
- `403` — current password incorrect
- `429` — too many attempts (5 per 10 minutes per user); `Retry-After` carries the seconds to wait
