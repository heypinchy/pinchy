Pinchy agents can only access files inside the `/data/` directory. To make your documents available, you mount host directories into subdirectories of `/data/` — in a `docker-compose.override.yml`, so upgrades never touch them.

## The `/data/` convention

![Agent permissions with directory picker — select which directories each agent can access](/screenshots/agent-settings-permissions.png)

All agent-accessible files live under `/data/`. The `pinchy-data` named volume is mounted there in **both** the `openclaw` and the `pinchy` container, at the same path, so a directory you grant an agent resolves identically wherever Pinchy reads it. You can bind-mount additional host directories as subdirectories.

This convention provides a clear boundary: anything under `/data/` is potentially accessible to agents (depending on their permissions), and nothing outside `/data/` is.

## Put your mounts in `docker-compose.override.yml`

`docker-compose.yml` belongs to the Pinchy project and gets replaced whenever you upgrade — mounts you add there are gone after the next `curl -o docker-compose.yml ...`. `docker-compose.override.yml` is yours: Docker Compose merges it on top of the base file on every `docker compose up`, and upgrades leave it alone. See [Customizing your deployment](/guides/customizing-deployment/) for the full picture.

Create the file next to `docker-compose.yml`:

```yaml
# docker-compose.override.yml
services:
  openclaw:
    volumes:
      - /path/on/host/hr-policies:/data/hr-policies:ro
      - /path/on/host/engineering-docs:/data/engineering-docs:ro

  pinchy:
    volumes:
      # Required — see the note below.
      - pinchy-data:/data
      - /path/on/host/hr-policies:/data/hr-policies:ro
      - /path/on/host/engineering-docs:/data/engineering-docs:ro
```

Compose merges volumes by mount path, so you only list what you're adding — the mounts already in `docker-compose.yml` stay as they are.

The `:ro` suffix mounts the directory as read-only, which is recommended since agents only need to read files.

Then apply the change:

```bash
docker compose up -d
```

<Aside type="caution">
  **The `- pinchy-data:/data` line on `pinchy` is required**, not decoration.
  The base file mounts `/data` read-only in that container, and Docker can't
  create a `/data/hr-policies` mount point inside a read-only mount — the
  container refuses to start with `error mounting ... read-only file system`.
  Re-declaring the same mount without `:ro` makes `/data` writable and the
  nested mounts work. Your own directories stay read-only either way, because
  each one carries its own `:ro`.

What you trade away is one layer of defence in depth: the `pinchy-data` volume
itself is no longer read-only from the web container. Nothing in Pinchy writes
to it — the agent runtime already mounts it writable, and user uploads go to a
different store — but a compromised web tier could. If that trade isn't one
you want to make, mount your directories on `openclaw` only; agents can still
read them, you just can't index them into a knowledge base or open them in the
picker to grant a subfolder.

</Aside>

## Why both services

Two containers read `/data`, for different jobs:

| Service    | Reads `/data` for                                                        | Needed when                                     |
| ---------- | ------------------------------------------------------------------------ | ----------------------------------------------- |
| `openclaw` | Agent file access                                                        | Always                                          |
| `pinchy`   | Knowledge Base indexing, and the subfolders the permissions picker lists | You index those documents, or grant a subfolder |

Mounting in both is the simple path, and it's what we recommend: the paths stay identical, and a directory you later point a [Knowledge Base agent](/guides/create-knowledge-base-agent/) at is already there. A directory mounted only on `openclaw` shows up in the picker and agents can read it, but indexing it finds nothing, and it opens with no subfolders.

## Examples

Each example shows the mount line to add. Add the same line to **both** services in your override file.

### Local folder

Mount a folder from your host machine:

```yaml
- /home/admin/company-docs:/data/company-docs:ro
```

### NAS or network drive

If your NAS is mounted on the host at `/mnt/nas/shared`, mount a subdirectory:

```yaml
- /mnt/nas/shared/legal:/data/legal:ro
- /mnt/nas/shared/finance:/data/finance:ro
```

**Mount the share for the container user.** The `pinchy` container runs as uid 999. A network share mounted without an owner mapping belongs to `root`, so Pinchy can't read it — and indexing then fails with a permission error that never mentions the mount. For an SMB/CIFS share, pass `uid=999,gid=999`:

```
//fileserver/share/suppliers /mnt/suppliers cifs ro,_netdev,credentials=/etc/smb.cred,uid=999,gid=999,iocharset=utf8,vers=3.0 0 0
```

`_netdev` matters just as much: it holds the mount back until the network is up, so a reboot doesn't leave the containers pointing at an empty directory.

Mount the share read-only — `ro` on both the host mount and the Compose volume. Pinchy never writes to `/data/`, and a read-only mount makes that structural rather than a promise.

### Multiple directories

You can mount as many directories as you need:

```yaml
- /srv/docs/hr:/data/hr:ro
- /srv/docs/engineering:/data/engineering:ro
- /srv/docs/compliance:/data/compliance:ro
```

Each mounted directory appears as a separate selectable option in the Permissions tab when configuring an agent.

## How directories appear in the UI

When you configure an agent's permissions in the **Permissions tab** of Agent Settings, Pinchy lists the directories under `/data/` as selectable options, and you can open each one to grant a folder inside it. Each mounted directory shows up by name — for example, `/data/hr-policies` appears as "hr-policies".

The list is read each time you open the tab, so it always shows what is mounted right now: a new mount appears once `docker compose up -d` has picked it up, and a mount you removed or renamed is gone from the list.

### Granting a subfolder

You don't need a mount per department. Mount the share once — say at `/data/suppliers` — and give each agent only its own folder inside it: open `suppliers` in the picker with the arrow beside it, then tick `food` for one agent and `vet` for another. Folders open one level at a time, so a large share costs nothing until you look inside it.

Granting a folder grants everything inside it. So when a folder is ticked, the folders inside it show as included and can't be ticked on their own, and ticking a folder replaces any grants you had already made inside it.

A few things worth knowing:

- **Subfolders are read in the `pinchy` container.** A share mounted only on `openclaw` still shows up as a mount, but opens with no subfolders. Mount it on both services, as described [above](#why-both-services).
- **Symbolic links are not offered**, and a folder reached through one can't be opened. A link inside a share can point anywhere, so the picker only ever shows the folder a grant actually names. An older grant that names a link is marked as one. See [Links inside a mounted folder](#links-inside-a-mounted-folder).
- **Hidden folders and operating-system folders** (`.snapshot`, `$RECYCLE.BIN` and the like) are left out. The index skips them anyway.
- **A folder with more than 500 subfolders** shows the first 500 and says so.
- **A grant the picker can't show** — a folder beyond the first 500, or one that no longer exists — is listed below the folders, so you can take it away.
- **A granted folder that is gone is marked "Folder not found"**, with a **Remove** button instead of a tick box. That is what a renamed or deleted mount leaves behind: the agent still holds a grant for `/data/old-name`, and nothing can be read through it. Remove it and save; the change is recorded in the [audit trail](/concepts/audit-trail/) like any other permission change. If the folder was only unmounted for a while, mount it again instead and the mark goes away.
- **A granted folder Pinchy can't open is marked too**, and keeps its tick box: the folder is there, but its permissions on the server don't let Pinchy in. Removing the grant is the wrong fix for that one — see [NAS or network drive](#nas-or-network-drive) for mounting a share so Pinchy can read it.
- **For a Knowledge Base agent, archive folders count inside the granted folder only.** Documents under a folder named `OLD`, `Archive`, `Archived` or `Archiv` _inside_ the folder you grant are left out of everyday search. The granted folder's own name and the folders above it don't count: grant `/data/Archiv` or `/data/Archiv/Projekte` and everyday search finds what's in it (see [Current documents first](/guides/create-knowledge-base-agent/#current-documents-first)). Reading files is not affected.

## Verifying your mounts

Check the merged configuration before starting anything:

```bash
docker compose config
```

Then confirm both containers see your directories:

```bash
docker compose exec openclaw ls /data/
```

```bash
docker compose exec pinchy ls /data/
```

Both should list your mounted directories.

## Moving mounts out of `docker-compose.yml`

If you added your mounts to `docker-compose.yml` directly, move them now — before the next upgrade overwrites them:

1. Copy your `- /host/path:/data/name:ro` lines into `docker-compose.override.yml`, under both services as shown above (don't forget the `- pinchy-data:/data` line on `pinchy`).
2. Delete those lines from `docker-compose.yml`, leaving the rest of the file untouched.
3. Run `docker compose config` to confirm the merged result still has every mount, then `docker compose up -d`.

Nothing is re-indexed or re-uploaded by this — the mounts point at the same host directories as before, and your knowledge base index lives in Postgres.

## Supported file types

Two different paths read the files under `/data/`, and they support different formats. The distinction matters when you plan a corpus, so it's worth knowing before you mount one.

**Knowledge Base search** (`knowledge_search`) indexes **PDFs** — text-based and scanned alike — **scanned TIFF images** (`.tif`, `.tiff`, multi-page ones included), **Excel workbooks** (`.xlsx`, `.xlsm`, `.xls`), **Word documents** (`.doc`, `.docx`, `.docm`), **slide decks** (`.ppt`, `.pptx`), **plain text files** (`.txt`) and **Outlook emails** (`.msg`). Markdown files under `/data/` are not indexed — see [Create a Knowledge Base Agent — Scope in this release](/guides/create-knowledge-base-agent/#scope-in-this-release).

Word documents and slide decks — the old formats as well as the new ones — are converted to PDF on their way into the index, and that converted copy is what the search reads and what a citation opens. It never replaces your file: the original stays exactly where it is, untouched, and is still the document a citation names.

LibreOffice converts them 20 at a time. If it is killed on a batch — the server ran short of memory — or the batch runs out of time, each file of that batch is converted once more on its own, with a time limit of its own, so a file that takes LibreOffice down doesn't keep the others from being indexed. Only a file that can't be converted even on its own counts as `failed`: whatever was indexed from an earlier version of it stays searchable, and it's converted again on the next run.

From that point on the copy is read exactly like any other PDF, and that includes the scan path below: a slide that is one exported image, or a Word page holding a scanned certificate, carries no text layer and is sent to your model provider to be read.

A page with no text layer is read the same way an agent reads one when you open it in chat: the page is rendered to an image and handed to a vision model. That is worth knowing before you mount a corpus of scans, because it is the one part of indexing that sends document content to your model provider — see [What indexing sends to your provider](#what-indexing-sends-to-your-provider) below.

A scanned TIFF is read the same way. Each of its pages becomes one page of a PDF the index makes for it — frame 3 is page 3 — and every page goes to the vision model exactly like a page of a scanned PDF, under the same limits, with the same retries and the same `PINCHY_KB_OCR=off` switch. A citation names your `.tif` and opens that PDF on the page the passage came from; the original stays where it is and can be downloaded next to it. A TIFF over 200 MB, one with a page of more than about 268 million pixels, or a file named `.tif` that isn't a TIFF inside is listed as `unsearchable` without being read. Without a vision model a TIFF can't be read at all, so it is listed as `unsearchable` too, and the first run after one is configured reads it.

A `.docm` is a Word document with macros. It is converted exactly like a `.docx`, and its macros are never run: the checked copy LibreOffice reads no longer refers to them, and the converter runs with macro execution switched off on top of that.

A `.txt` file is read in the encoding it was saved in. A file that starts with a byte-order mark is read as UTF-8 or UTF-16 as the mark says; one without is read as UTF-8 when it is valid UTF-8, and otherwise as Windows-1252 — what Windows Notepad saved as "ANSI" for decades. So umlauts in an old text file come out as umlauts, not as replacement characters. A text file over 10 MB, the same limit an agent's file tools put on one, is listed as `unsearchable`. A text file has no pages, so a citation names it without a page and doesn't open a preview.

An Outlook email saved as `.msg` is indexed with its headers on top: the subject, the sender, the `To` and `Cc` recipients, the date it arrived and the names of its attachments, then the body. So a search for the sender, the subject or an attachment's file name finds the mail, and a passage from deep inside a long mail still says which mail it came from. Three things are left out on purpose. **Bcc recipients** are never indexed: a blind copy means the other recipients weren't meant to see that name, and the index is read by people who were never on the mail. **Attachments** are listed by name, but their contents aren't read — a citation can't point inside a mail, so save an attachment next to the mail and it's indexed as a document of its own, with a citation that opens it. A body Outlook stored only as RTF, which only very old versions write, isn't read; such a mail is found by its headers. A mail has no pages, so a citation names the `.msg` without a page, like a text file. A mail is read in a separate process with a memory and time limit of its own. A `.msg` over 100 MB, one that's damaged or was cut short while being copied, or a file named `.msg` that isn't an Outlook message inside — a renamed `.eml`, for example — is listed as `unsearchable`, and read again once the file changes; a body longer than 10 MB is indexed up to that point.

A workbook is read from its cells rather than converted to a page layout, so a row that is too wide for its column keeps its full text instead of being clipped at a page edge. That is also why a workbook is never converted to PDF: pages would be invented, and an invented page is not a place anyone can point at.

An older `.xls` workbook uses a file format our reader does not open, so it takes one extra step: the `office-converter` container turns it into an `.xlsx` — a workbook again, never a PDF — and from there it is read exactly like any other workbook, under the same limits. A citation names the sheet and the rows, just as it does for an `.xlsx`. The `.xls` itself stays exactly where it is, untouched, and is still the file a citation names and the one you download.

Two things a conversion does not carry into the index, because it does not render them: **comments** in a Word document and **speaker notes** in a slide deck. What it does carry is text that a tracked change deleted but nobody has accepted yet — it is still printed, struck through, in the copy you open from the citation. That is deliberate. Search and preview read the same copy, so anything else would either hide a passage you can see or quote one you cannot find. If a document's draft history should not be searchable, accept or reject its changes before you index it.

**Office files are read as untrusted input.** Anyone who can write to a mounted folder can put a file there, and indexing opens it. So Word documents and slide decks are converted in a container of their own, `office-converter`, that has no network and none of Pinchy's secrets: it can't send a request anywhere, and none of your files are in it but the copies handed to it for converting. It runs as a user of its own, so it can read those copies but not change them, and all it can write back is the converted file. On top of that, a Word document or slide deck can point at things outside itself — a linked picture, a template, a hyperlink target on another machine, a file on the server — and a converter left to its defaults goes and gets them. So we don't convert your `.docx` or `.pptx` itself. We convert a checked copy: external links are removed, and so are the parts a page isn't drawn from and the parts that are risky to hand to the converter — among them a picture that would load something from outside the file, and a part whose content isn't what the document says it is. What's left is indexed as usual. A linked picture isn't drawn, a hyperlink keeps its text but not its destination, and an embedded object, such as a spreadsheet pasted into a slide, shows as its preview picture. A picture saved as a Windows metafile (`.emf`, `.wmf`) can carry other content inside it, such as another picture, which the converter would open too, so everything a metafile carries inside it is removed and only its own plain drawing is kept. Word, PowerPoint and LibreOffice save every metafile with that plain drawing, so the picture is still drawn — words in it, such as a chart's labels, included. A metafile drawn only in the newer EMF+ format comes out blank, and its words aren't indexed. One whose structure we can't read unambiguously isn't drawn at all. SVG pictures and icons, as Word, PowerPoint and LibreOffice save them, convert as usual.

These checks are a layer, not a guarantee. They remove the ways we know of for a file to reach outside itself; they don't make the converter safe to point at anything at all. That is what the `office-converter` container is for: if a file ever gets past them, there is no network to send a request over and nothing of yours to read.

One thing is removed that does cost text: a chunk of another format — an HTML page, another Word document — embedded for the converter to import on the way through. The rest of the document is indexed; the chunk's own content isn't, and the server log names the file. A `.doc`, `.docx`, `.ppt` or `.pptx` whose content isn't one — an HTML page renamed `.doc`, for example — is listed as `unsearchable` instead of converted, and so is one with a part that claims to belong to the document but is something else, or one put together in a way no Office application writes: a part whose name has `.` or `..` in its path, or a link whose attributes carry a namespace prefix. The converter and our checks could read such a file two different ways, so we don't guess which.

The older `.doc` and `.ppt` formats can't be rewritten like that. An RTF file saved under a `.doc` name, as Word sometimes does, has its pictures, embedded objects and field codes removed before conversion. If we can't be sure where one of those ends — a binary block whose length is out of range or sits outside a picture, or a broken character escape — the file is listed as `unsearchable` instead. Otherwise it is in the same position: these files rely on the settings LibreOffice runs with, which switch off fetching links. Those settings stopped every linked picture we tried, but they don't stop every way a picture embedded in such a file can read a file. Inside the `office-converter` container that file can only be part of the converter itself — not your configuration, your secrets or another agent's documents. Who can write to the folders you mount is still the protection you control.

An `.xls` goes the same way: it is converted inside the `office-converter` container, with no network and none of your secrets, and the `.xlsx` that comes out is read by the same separate reader process as any workbook, under the workbook limits below. Only a real legacy Excel file is taken. Export tools often save an HTML or XML table under an `.xls` name; such a file is listed as `unsearchable` instead of converted, because it isn't the format its name says. An `.xls` over 200 MB is listed as `unsearchable` too, and never reaches the converter.

Files that would be too big to open safely are listed as `unsearchable` as well, and no reader ever gets them. That covers a Word document or slide deck over 200 MB, a workbook over 100 MB, any Office file that unpacks to far more than it weighs — over 500 MB for Word and PowerPoint, over 256 MB for a workbook, or more than 200 times its own size once it passes 16 MB — or to more than it says it will, a Word document or slide deck with a single part of text (the document body, a slide, its list of links) over 64 MB, and a workbook with a single sheet — or any other part our reader reads as text — over 16 MB, or a single picture over 32 MB. Most of these are far beyond anything a person writes; a compressed file built to be small on disk and huge in memory is exactly what they are for. The sheet limit is the exception, and a large export can reach it: 16 MB is roughly 40,000 rows of ten columns on one sheet. It is there because reading a sheet takes about twenty times its own size in memory. A picture costs only about its own size, which is why a price list with a large product photo in it is read as usual.

Workbooks are also read in a separate process with its own memory and time limit (384 MB, two minutes), so a workbook that needs more memory than that — several large sheets, say — is listed as `unsearchable` too, instead of taking Pinchy down with it. Split a workbook like that into smaller ones and the parts are indexed. A workbook that declares a number format no spreadsheet application writes — Excel's own limit is 255 characters, counted after character codes such as `&#91;` are spelled out — is listed as `unsearchable` without being read, since reading one can stall the spreadsheet reader, and so is an `.xlsx` that isn't a workbook archive at all. Neither is read again until the file changes. Running out of time is different, and so is the process being stopped by the system because the server as a whole ran short of memory: neither says anything certain about the workbook, so it counts as `failed` for that run, whatever was indexed from an earlier version of it stays searchable, and it is read again on the next run. The server log says which it was.

Word documents and slide decks are checked and copied for the converter in that same kind of separate process, so a 200 MB deck never sits in Pinchy's own memory. If the process is stopped because the server as a whole ran short of memory, the file counts as `failed` for that run and is read again on the next, exactly like a workbook; one whose check needs more memory than the process may use is listed as `unsearchable`. The checked copy is written to the `pinchy-office-spool` volume, the folder Pinchy hands to the converter, and so are the scratch space LibreOffice needs while opening it — about what the file unpacks to — and the PDF it makes, before the PDF is stored on `pinchy-kb-artifacts`. If that volume is full or can't be written to — for the copy, the scratch space or the PDF — the same applies as for a memory squeeze: `failed` for that run, an earlier version stays searchable, and the file is read again on the next run. It says nothing about the document, so it doesn't land on the unsearchable list — with one exception, below. Whether that happened is a question for the volume, not the converter, which reports a document it ran out of room for just as it reports one it can't read: it counts when the volume no longer takes a write, has fewer than 1,024 free inodes, or has less space left than what the file unpacks to (nothing for one that isn't an archive, such as a classic `.doc` or `.ppt`) plus room for its PDF twice over, since LibreOffice writes the PDF to its scratch space before copying it out: 32 MiB, or four times the file's size for a large one. A deck whose every slide is hidden also leaves LibreOffice without a PDF, on a volume with plenty of room, and is listed as unsearchable. The room for the PDF is an estimate — the PDF was never written — and a file full of pictures can outgrow it, because LibreOffice re-encodes pictures: an 8.5 MB Word file of 200 screenshots made an 82 MB PDF. If a PDF like that doesn't fit on a volume that still had the estimated room, LibreOffice reports it exactly as it reports that deck, and the file is treated the same way: listed as unsearchable, whatever was indexed from an earlier version of it dropped, and tried again on the next runs, five tries in all. [Customizing your deployment](/guides/customizing-deployment/#memory-when-the-knowledge-base-indexes-office-documents) says how much headroom rules it out.

After converting a Word document or a classic `.ppt` deck we count its words a second time, with an independent reader, to catch text the converter dropped. For a `.docx` or `.docm` that count reads the document as it was saved, with its links to web pages and linked pictures still in it (nothing is fetched), not the copy the converter gets with those removed, and it runs in the same kind of separate process, under the same memory limit. A `.doc` is counted with `catdoc` and a `.ppt` with `catppt`, which come with Pinchy's image. A document too big for the count, or one the reader can't count, is still converted and indexed, just without that check, and the server log says so: `word count skipped` or `word count failed`, with the file's name. A `.pptx` has no such check. If the converted PDF holds clearly fewer words than that count — more than a tenth short — we don't index the PDF, because it may be missing whole passages. A `.docx` or `.docm` is then indexed from the text that same reader found in it instead, so it stays searchable, but without a preview: its citations name the document and no heading, and the viewer offers the original (**Original (.docx)** or **Original (.docm)**) for download. The server log names the file and both word counts. A legacy `.doc` or a `.ppt` whose PDF comes out short has no such fallback — the readers that count their words also miss some of them and garble the accented letters of Central and Eastern European languages — so it is listed as `unsearchable`, with the counts in the server log.

**Reading a file directly** (the agent's file tools) handles a different set: PDFs of either kind, **Word documents** (`.docx` only, and up to about 8 MB of text and formatting once unpacked — some 500 pages the way Word writes them, more from LibreOffice; pictures don't count. A longer one is answered with an error rather than read. Every Word document is read in a separate process with its own memory and time limit — 384 MB, two minutes — so one that needs more than that, however it got past the size check, is answered with an error too, and the agent runtime keeps running. A document with unusually dense formatting can reach that memory limit below 500 pages. A `.docx` put together in a way no Office application writes, as described above, is refused), plain text and Markdown. Scanned PDFs are analyzed using the configured model's vision capabilities. So a legacy `.doc` is searchable but cannot be opened directly, and a `.md` runbook is the other way round.

A workbook whose every sheet is hidden is counted `unsearchable`: it was read without error and holds nothing to search. A scan lands there too when no vision model is configured to read it or reading scans is [switched off](#what-indexing-sends-to-your-provider), and so does a Word document or slide deck that could not be converted, or an Office file that was refused for its size or its content (see above) — the document is listed, by name, rather than dropped. A file whose type the index doesn't take at all — a `.md` runbook, say — never enters the run, so no count mentions it: mount a corpus of those and the report comes back the way it would for an empty folder.

## What indexing sends to your provider

Everything about indexing is local — reading the file, splitting it, computing embeddings — with exactly one exception: **a page with no text layer is sent to your configured model provider**, as an image, so a vision model can read it.

Three consequences worth stating plainly:

- It happens at index time, for **every** scanned page in the corpus, whether or not anyone ever asks about that document. Every page of a scanned TIFF counts, since a TIFF is nothing but images. A Word document or slide deck counts here too: it is indexed through its converted PDF, so a page of it that holds only an image is read the same way a scan is.
- It uses the same vision model Pinchy already picks for reading PDFs in chat, so a scan reads the same way whether the index read it or an agent did. On Anthropic, Google and OpenAI that's the provider's balanced model — see [Which model Pinchy picks](/guides/llm-providers/#which-model-pinchy-picks).
- It happens once per document, not once per question. With the [nightly reindex](/guides/create-knowledge-base-agent/#keeping-the-index-current) that means the night a scan first lands in a granted folder; an unchanged scan is skipped before anything is extracted. That includes a scan the vision model found no text in: it stays `unsearchable`, and the same model would find the same nothing, so it isn't sent again. It's sent again only when the answer could change: a different vision model has been configured since, or the vision call on it failed — which is how a provider outage heals by itself on the next run. A failed scan is retried for at most five runs in a row, so a page your provider rejects every time doesn't go out every night.

If that is not acceptable for your instance, add `PINCHY_KB_OCR=off` to your `.env` and run `docker compose up -d`. Indexing — manual and nightly alike — then skips scanned pages and TIFF scans entirely, nothing leaves the building, and those documents are reported as `unsearchable` instead — visible, not silent. Turn it back on and the next run reads them. A scan read before you set it keeps its text in the index.

Two limits to know:

- **A local-only stack has no vision model.** Pinchy picks the vision model from your configured cloud providers; a model you pulled into a local Ollama is not considered, because whether it can read images depends on which model you pulled. An air-gapped instance therefore indexes scans as unsearchable today.
- **At most 200 pages per document** are read this way. A document with more reports what was left behind rather than dropping it quietly.

The reindex entry in the [audit trail](/concepts/audit-trail/) records how many documents and pages were sent, and to which model. It does not record which files — audit rows are immutable and deliberately carry no filesystem paths.

## Links inside a mounted folder

Indexing never follows a symbolic link. A link inside a mounted folder is not indexed — not even one pointing at a file in the same folder — and a link to a folder is not walked into. If a document should be searchable from two places, copy it, or mount the folder it lives in. The folder you grant an agent may itself be a link; only links **below** it are left out.

What is listed is also what is read. Every file is opened without following a link, and only if it is still a regular file at the place the run found it. So a file that is swapped for a link while a run is in progress — or reached through a folder that was swapped for one — is refused rather than read:

- It counts as `failed` for that run, and a version indexed earlier stays searchable.
- The run's entry in the [audit trail](/concepts/audit-trail/) counts it as `refusedFiles`. The server log names the file.
- The next run reads it again, and indexes it if it is an ordinary file by then.

This matters because a mounted folder is often writable by more people than may read every folder next to it. Without the check, anyone who can write to one folder could point a file there at a document from another team's folder, and an agent granted the first folder would quote it. The same holds for opening a cited document and for an agent reading a file directly: the path is resolved to where it really points and checked against the agent's folders, and the file is then read without following any link that appeared after that check.

A document saved while the run is in progress is read as it is when the run gets to it. Most editors save by writing a new file and renaming it over the old one; that is still a regular file in the same place, so it is not refused.

## Knowledge Base vs. workspace files

Directories mounted under `/data/` are **admin-curated and read-only for agents** — they hold your organization's reference documents and are not writable by agents under any configuration.

This is intentional: it keeps your authoritative documents separate from anything an agent might generate or derive. An agent that has the **Create files** permission saves results to its own `workbench/` workspace, never to `/data/` and never to the `uploads/` folder holding your chat attachments. See [Agent Permissions](/concepts/agent-permissions/) for details on the workspace write capability.
