Some agent actions are worth a second look before they happen — sending an email, writing to Odoo, deleting a record. Tool confirmation lets you mark those actions so the agent **pauses and asks the person in the chat** before it runs them. The agent still does the work; a human just says "go" first.

This is a human-in-the-loop checkpoint, not a bottleneck: the person driving the agent approves their own action, in seconds, right where they're working.

## Turn it on for an agent

Confirmation is set per agent, by an admin:

1. Open the agent's **Settings → Permissions**.
2. Find **Require confirmation before**.
3. Check the tools that should pause for a confirmation — or click **Use recommended** to select the agent's powerful (write and side-effecting) tools in one go.
4. Save.

<Aside type="tip">
  "Use recommended" picks the tools that change things — the ones most worth a
  glance. Read-only tools stay un-gated so the agent keeps feeling fast. You can
  always adjust the list later.
</Aside>

## Per record type, for Odoo

"Ask before deleting" is often too broad. Deleting an invoice deserves a second look; deleting a note does not, and an agent that stops for both trains people to click through without reading.

So for Odoo the setting also lives in the **model table** on the same page, where each cell has three states:

|                 |                                                |
| --------------- | ---------------------------------------------- |
| **Not allowed** | The agent cannot do this at all.               |
| **Ask first**   | The agent pauses and waits for a confirmation. |
| **Allowed**     | The agent goes ahead on its own.               |

A cell you have never touched shows what it **inherits** from the tool setting above. That is deliberate, and it is what keeps the table honest: if you gate deletion for the agent, every model is gated — including ones you add next month. Setting a single cell to **Allowed** is how you make an exception, and it stays an exception.

The confirmation card names the record type, so the person deciding sees "Delete a record in Odoo — account.move" rather than a question they cannot answer.

<Aside type="caution">
  The check sees the call, not everything it sets off. Approving a write to an
  invoice also writes that invoice's lines, and confirming a stock transfer
  moves every line on it. Gate the operation you care about, and read the card's
  details rather than assuming the scope is one record.
</Aside>

Where a single action touches two record types — reconciling a bill against a payment, for instance — the **stricter** of the two settings wins.

## What the person sees

When the agent reaches a gated tool, it doesn't run it — it **waits**, mid-turn, holding the call open. A card appears **at the end of the conversation**, where the agent stopped, naming the agent and the tool — _"Smithers needs your confirmation: run `email_send`"_ — with a **Review** button. **Review** opens the card on the action's details — for example, `to`: ada@example.com, `subject`: Q3 numbers — and two buttons:

- **Approve** — the agent picks the turn straight back up and runs the tool. You don't have to prompt it again.
- **Deny** — the action is blocked, the agent is told so, and it carries on with the rest of the turn.

### The card shows what will run

You approve what the card shows, so the card shows everything the tool will receive — not a summary of it:

- **Every value is spelled out, or the action isn't offered.** A list shows each entry on its own line, and an object shows each field with its value — nested up to ten levels, enough for a full Odoo invoice with its line and tax commands. You see the actual ids and field values of an Odoo write, not "1 item" or "2 fields". A card holds up to 100 fields per object, 200 entries per list, 200,000 characters per text — counted as the agent sent them, so a no-break space is one character even though the card spells it out as a marker — and 512,000 characters in all as shown on the card, markers, numbers and field names included. That covers ordinary work with room to spare, a report of a few dozen pages written to a file included. A card is also bounded by what it costs your browser to draw: up to 16,384, counting what the card shows before you click **Show full text**, a long text by its preview — one for every field, value and note, one for each of their characters, and 128 for an emoji or any other character outside Unicode's Basic Multilingual Plane, because for those the browser looks up a font, which can cost a hundred times as much. The one exception is the bold and italic letters of Unicode's mathematical alphabets — 𝐁𝐢𝐠 𝐧𝐞𝐰𝐬, the way a LinkedIn post sets its headings: the browser draws them like any other letter, so they count one. Without that bound, a card of 500 short emoji previews within every other limit took two seconds to appear, and one of a hundred thousand Hebrew words between digits about a second. An email with a long body, an Odoo write with dozens of fields, an invoice with dozens of lines or one long address drawn whole stays far below it; a card with more than about 120 emoji does not. **Show full text** is bounded the same way: it reveals a long text a part at a time, each part ending where its characters would cost more than 8,192 by the same count — what one long address drawn whole may cost — and only one part is on the card at once. A body of 200,000 Hebrew letters between digits, drawn whole, held the browser for up to half a minute; in parts, each click takes a fraction of a second. An action whose arguments don't fit is **refused instead of shown in part**: no card appears, the agent is told which limit the call crossed and where, and the audit trail records an `approval.refused` entry. Where the call can be split — too many fields, entries or recipients, too much in all, or too costly to draw — the agent is told to split it into smaller calls; a single text that is too long, or arguments nested too deeply, can't be split, so the agent is told it is too long to show for approval and to stop. You never approve a card with something left out.
- **A value reads as its type.** Numbers, `true`/`false` and `null` appear as they are; a text that would look like one of them is shown in quotes. So `active: "false"` (text, which Odoo reads as _true_) can't pass for `active: false`, and `"1"` can't pass for `1`, and an empty list `[]` can't pass for an empty object `{}` — or for the text `"[]"`. A screen reader hears "empty list" or "empty object". The approval request text Pinchy hands to the agent runtime puts every text in quotes, whatever it holds, so a name `Acme, active: false` reads `name: "Acme, active: false"` there and can't pass for a second field — the card needs no quotes for that, because it draws every field and every list entry on a line of its own. Whatever Pinchy adds about a value — the record a reference names, the server an address reaches, a display name, a hidden secret — is printed outside the quotes there, so no text can imitate it: `partner_id: (record reference: res.partner #7 "Acme GmbH")` is a record, `partner_id: "(record reference: res.partner #7 \"Acme GmbH\")"` is text the agent typed.
- **The request text names every server the call reaches.** The approval request text Pinchy hands to the agent runtime is cut at 256 characters, and a cut can land anywhere — inside a long text, or inside a web address before the domain at its end. So when it has to be cut, it names every server and mail domain the call reaches first, each by its end, where the domain is: `reaches "evil.com", "…mail.firma.at" — url: …`. A call that reaches more than fit there is **refused**, the same way as one too large for the card, rather than offered with one left out — whatever order the agent sent its fields in. A domain that isn't a valid domain name — one with a label such as `xn--a` that doesn't decode — has no resolved form, so it is named as written, ending in the domain it spells.
- **Every field name is shown as it is.** A field name that isn't a plain identifier is shown in quotes, with anything unusual spelled out: `"to "` (with a trailing space) appears as its own row next to `to`, and a look-alike name with a Cyrillic letter or a hidden character reads `"t⟨U+043E⟩"`. Two fields never merge into one row.
- **What Pinchy adds is a label, never part of the value.** Where the card says something about a value — the server an address reaches, a display name, the record a reference names, that a secret is being set — it draws that as a small label with a dashed border beside the value, never as text inside it. So a value can't imitate one: an address the agent sent with `(xn--frma-l9d.at)` or `(firma.at)` typed after it shows those characters as part of the address, with no label, and text that reads `(record reference: …)` is just text. The same holds for a screen reader, which can't see the border: it reads every text value in quotes, with any `"` inside it escaped as `\"`, and every label as a note that starts with "Pinchy note:" — `"boss@fіrma.at"`, then `Pinchy note: host xn--frma-l9d.at`. So a text the agent typed to sound like a label is still read inside its quotes. A screen reader set to skip punctuation won't say the quotes; the "Pinchy note" before each label is said in words either way.
- **Every recipient is listed, address first.** For `to`, `cc` and `bcc`, the card splits the field into one line per address. An extra address tucked behind a comma, a semicolon or a long run of spaces becomes its own visible line. Each line starts with the address and puts the display name after it, in a label — `attacker@evil.com` `name "Raimund Korber"` — so a long, familiar name can't push the real address out of view. A domain with non-Latin letters also gets a label with its ASCII form, so `boss@fіrma.at` with a Cyrillic "і" reads `boss@fіrma.at` `host xn--frma-l9d.at` and can't pass for the real domain. A domain that isn't a valid domain name gets a label that names it as written and says so instead, plain ASCII or not: `boss@xn--a.evil.com` reads like an ordinary domain, but its `xn--a` label doesn't decode, so it reads `boss@xn--a.evil.com` `host "xn--a.evil.com", not a valid domain name`. The same goes for any value that is an email address or a web address, wherever it sits — an Odoo contact's `email` or `website` gets the label too. What counts as a web address is decided by the same URL parser the web tools use, not by its look — and that parser takes more than `https://server`: `https:fіrma.at`, `https:/fіrma.at` and `https:\\fіrma.at` all reach a server, and so does an address with a control character in front of it. So the card names the server a web address actually reaches whenever its text doesn't show exactly that server right after `https://`: in `https://fіrma.at\@evil.com/x` the backslash ends the server name, so the label reads `host xn--frma-l9d.at`; `https://fir%6Da.at` gets `host firma.at`; and `https://firma.at@evil.com` gets `host evil.com`, because everything before an `@` is a user name, not the server. An email address is read the way the mail tools read one, so `Boss <boss@fіrma.at>` and an address with a space in front get the label too. A web address the parser refuses because its server name isn't a valid domain name — `https://xn--a.evil.com/x`, which a browser still opens — gets that label too, naming the server, whatever follows the server name: a space or a tab in the path, or words after it, still leave a browser opening `xn--a.evil.com`. The label sits beside the preview, so a long web address that ends in `@xn--a.evil.com/…` and one that ends in `@xn--a.evil.org/…` never look alike before you click **Show full text**. Text that merely starts with a web address or holds an email address — "https://firma.at, see above" — is text: it gets no label and is previewed like any other text. An email address or web address is shown whole, at any field, so the domain at its end is always in view — up to 8,192 characters, far more than any real address. Whenever the card does start one as a preview instead — one longer than that, one with words after it, one that holds a long run of invisible characters (shown as a count such as `⟨4 × U+200B⟩`) — it always gets a `host` label naming where it goes, even a plain ASCII domain, beside the preview rather than behind **Show full text**. The card's decision to shorten a value and the label that names its server come from the same rule, so there's no shape that gets one without the other.
- **Where the action lands is shown whole.** Recipients, and the fields that name a target — `path`, `filename`, `url`, `target`, an Odoo `model` and its `ids`, and the like — are never collapsed behind a preview up to 8,192 characters as shown, they're filled in before anything else, so a long message body can't push them off the card, and they're listed first on the card. That holds every real path: the file tools refuse one longer than 1,024 characters, and even one made entirely of marked characters fits. A longer value — a web address can be, since the web tools set no length limit, and so can an Odoo field — starts as a preview, so it can't freeze the card while it is drawn; the labels beside it, such as the server it reaches, stay in view.
- **Text is shown as sent, and nothing in it can hide.** Spaces, tabs and line breaks are kept as the agent sent them; a Windows line break (CR LF) is shown as a line break, while a lone carriage return is spelled out as a marker. A run of four or more is shown as a count, such as `⟨180 spaces⟩`, so padding can't push text out of view. Every character that is invisible or renders as blank space — zero-width and text-direction controls, Unicode tag characters, variation selectors, no-break and other unusual spaces, Hangul fillers, the braille blank (U+2800) — is shown as a `⟨U+2800⟩`-style marker instead. A run of more than three of the same character becomes one marker that says how many there are, such as `⟨180 × U+2800⟩`, so padding is obvious without flooding the card; a run of different ones names every character in order, so two runs never look alike. A `⟨` or `⟩` in the text itself is marked as well (`⟨U+27E8⟩`, `⟨U+27E9⟩`), so every `⟨` on the card starts a marker Pinchy wrote: a file the agent named `a⟨U+200D⟩b.md` in plain characters reads `a⟨U+27E8⟩U+200D⟨U+27E9⟩b.md`, never like `a⟨U+200D⟩b.md` with a real joiner. The zero-width non-joiner and joiner (U+200C, U+200D) and the text/emoji presentation selectors (U+FE0E, U+FE0F) are marked too, everywhere and in every script: a company name `Noack⟨U+200D⟩ GmbH` is a different name from `Noack GmbH`, an invoice reference `RE-1001⟨U+FE0F⟩` is a different reference from `RE-1001`, and a file `க்⟨U+200C⟩ம.md` is a different file from `க்ம.md`, even though each pair can look identical. That includes Persian and Indic text, where a joiner can change how the letters are drawn (گزارش⟨U+200C⟩ها, ශ්⟨U+200D⟩රී), and emoji built from several pieces, such as `👨⟨U+200D⟩👩⟨U+200D⟩👧` or `❤⟨U+FE0F⟩⟨U+200D⟩🔥`: whether those pieces are drawn as one depends on the script and on the fonts of the device you approve on — an older system draws `❤️‍🔥` exactly like `❤️🔥` — and we would rather show you a marker than have two names look alike. A combining mark — an accent, a Hebrew point, an Arabic vowel sign, an Indic vowel sign — is shown as it is only on a letter of its own script, such as `é`, `בּ`, `مَ` or `कि`. Anywhere else — at the start of a text, after a space, a digit, a `/`, punctuation or a marker, or on a letter of another script — it is marked, such as `⟨U+05BC⟩בא`: with nothing of its own to sit on, a mark is drawn onto its neighbour, and `⟨U+05BC⟩בא` would otherwise look exactly like `באּ`.
- **Text reads in the order it was sent.** Left to itself, a browser reorders text that mixes right-to-left words with digits and punctuation: `/data/חוזים/2024.md` and `/data/2024/חוזים.md` are two different files that would look exactly alike. The card holds every value in the order the agent sent it, and lets each Hebrew or Arabic word — or run of words separated by spaces — read right to left on its own. A word keeps the punctuation that is itself written right to left, such as the Hebrew maqaf, geresh and gershayim or the Arabic question mark, and a `"` or `'` typed between two right-to-left characters in place of a gershayim or geresh: `חברה בע״מ`, `חברה בע"מ` and `ג'ירפה.md` read as they are written. So the folders of a path, the parts of an address and the words of a name always appear in the order they will be used, and the two paths above read apart. Digits and all other punctuation between right-to-left words keep their sent position, so a sentence with commas reads clause by clause from left to right. The approval request text Pinchy hands to the agent runtime carries the same order, written with Unicode's direction controls; a chat app that ignores them shows that text as it always did, so decide on the card.
- **Where the action lands reads as exactly one target.** In a field that names a target — a path, a file name, a record — two spellings that look alike are two different targets, so the card marks even what ordinary text keeps: a space, tab or line break at the start or end (`/data/out/report.md⟨U+0020⟩`).
- **Long text starts as a preview.** Any other text longer than 200 characters — and a target or address longer than 8,192 — shows a preview that says how many characters are hidden, with **Show full text** to read all of it. A text that costs more to draw than one long address — about 8,192 characters, or 64 emoji — is shown in parts: the card says which characters you're looking at and how many there are in all (`characters 8,193–16,384 of 200,000`), and **Show next part** and **Show previous part** step through them. A part ends after a space or line break where one fits, and otherwise between two characters as you read them — never inside an emoji flag, a letter and its accent, a Korean syllable or a `⟨U+200B⟩` marker — so each part draws the characters the whole text has there, and the flags after the cut pair up as they do in the whole text. Where a part ends after a space, no word changes shape at the cut. Only a word longer than a part is cut between two of its letters, and letters that join across that cut, as Arabic ones do, take the shapes they have where a word ends and begins — the same letters, with the `…` beside them saying the word goes on. The preview ends between two characters too, but it doesn't look for a space, so a word at its end can take those shapes the same way. Only a single character longer than the preview or a part — a letter under hundreds of accents, an emoji under hundreds of skin tones — is split inside, and the card says so beside it: the two pieces of a split character don't look like the whole one. Pinchy decides all of this — what is previewed, where the preview and each part end — when the agent makes the call, and stores it with the confirmation; your browser draws exactly those cuts and decides none of its own. So the card shows the same in every browser, and what it draws is exactly what was counted in the 16,384. A screen reader reads the same stretch of text, in quotes, that is drawn. The whole text is on the card — nothing is cut off behind the button.
- **Record references name their record.** An opaque Odoo reference shows the record it points at, in a label — model, id and name, for example `record reference account.move #42 "INV/2026/0042"` — so two invoices never look alike. The name comes from Odoo, where anyone who can name a record writes it, so a `"` in it is escaped: a partner named `x" — res.partner #12 "Acme GmbH` reads `record reference res.partner #666 "x\" — res.partner #12 \"Acme GmbH"`, never as a reference to #12. The agent can't fake that label: text it sends that reads `(record reference: account.move #42 "INV/2026/0042")` is shown as plain text, without one — and the Odoo tools look such text up as a record **name**, so a plain text where you expect a record is worth a second look. Anything that isn't a reference Pinchy can read is shown as the text it is: an email body that happens to start like a reference, or that starts with a real one and carries more text after it, is still shown in full — and the Odoo tools refuse such a string as a reference, too.
- **Secrets stay hidden, but setting one doesn't.** Text under field names that look like secrets (tokens, passwords, API keys) is never shown, at any depth. The card still says that such a field is being set and how long the value is, in a label — `access_token: [secret-like field is being set — value hidden, 19 characters]` — because an agent writing a token of its choosing into a record is something to notice. Only text is hidden: a number, `true`/`false` or `null` can't hold a secret and is shown, a field ending in `_id` or `_ids` holds record ids and is shown in full (`payment_token_id: 7`), and a list or object under a secret-like name is shown field by field, with the text in it hidden.

On top of that, the tools themselves refuse what the card would have to explain:

- `email_send` and `email_draft` accept **exactly one recipient per call**. A string that holds a list ("a@x.at, b@y.at") is refused with an error telling the agent to send one mail per recipient, so no second address can ride along on the one you approved. So is an address that imitates a separator, such as a fullwidth `＠` in the display name. So is an address whose domain isn't a valid domain name, such as one with a label `xn--a` that doesn't decode: it has no resolved form, so the card could only name it as written, and no real address needs one. A display name may be up to 64 characters, with single spaces and no invisible or blank-rendering characters — a single no-break or ideographic space counts as a space, as in `"山田　太郎" <yamada@example.jp>`, and the card marks it as `⟨U+3000⟩`; a run of them is refused like a run of spaces; emoji are fine, and so are the zero-width non-joiner and joiner that Persian and Indic names carry, such as علی‌رضا — the card marks each one, as `علی⟨U+200C⟩رضا`. A name with a comma or parentheses goes in double quotes, the way a mail program writes it — `"Müller, Hans" <hans@example.com>` is one recipient. Without the quotes, the comma would start a second recipient, so the tool refuses it and tells the agent to add them.
- `pinchy_write`, `pinchy_delete` and `pinchy_generate_file` refuse a path or file name that doesn't read as the file it reaches: one longer than 1,024 characters, one with a `..` segment, one not in its plain form (a `.` segment, an empty segment such as `//`, or a trailing `/`), one with an invisible or blank-rendering character, or one not in composed Unicode form (NFC). Visible-width spaces such as the no-break space are allowed — real file names carry them, and the card marks each one as `⟨U+00A0⟩`. So are emoji, ⚠️ and 👨‍👩‍👧 included, the zero-width non-joiner and joiner that Persian and Indic names carry (گزارش‌ها, ශ්‍රී, க்‌ம), and the presentation selectors: the card marks each of them, so `a⟨U+200D⟩b.md` never reads as `ab.md`, nor `Vertrag ✅⟨U+FE0F⟩.pdf` as `Vertrag ✅.pdf`. `pinchy_write` and `pinchy_delete` also refuse a file or folder name that starts or ends with a space, since `report.md ` would be a different file from `report.md`; `pinchy_generate_file` trims the name it is given, so either spelling writes the same file, and the card marks the spaces. The file you see on the card is the file that changes.
- **Every Pinchy tool refuses a parameter it doesn't declare** — the file, email, Odoo, web search and fetch, knowledge base, documentation and context tools alike, since any of them can be gated. A call carrying an extra field fails before the tool does anything, and the audit trail records the failed call: a look-alike `"to "` beside `to`, or web addresses under `target` and `destination` beside the one `url` that `pinchy_web_fetch` reads, which would otherwise sit on the card next to the address that is actually fetched. On most model providers the agent runtime checks the call against the tool's declared parameters and refuses it before any card opens, telling the agent the call has fields the tool doesn't take. On providers whose tool-schema handling drops that check, such as Gemini, the tool refuses the call itself and lists the fields it takes. For a gated tool that comes after the card, which shows the extra field as a row of its own — a reason to deny it there.

Approve clears exactly that one action. If the agent later tries something different — a different recipient, a different record — it asks again. One confirmation, one action.

If you've moved on to another chat in the meantime, the card follows you into the corner of the screen rather than disappearing — an agent waiting in a conversation you've left still needs an answer.

A card opens only when you click its **Review**, and only one is open at a time: opening another closes the one that was open. Nothing else opens a card or switches which one is open — not a newer confirmation arriving, not deciding the open one, not one answered in another tab — so the **Approve** under your pointer is always the one on the card you are reading. Once you decide, the next card stays closed until you review it. For keyboard and screen reader users, focus follows along: **Review** moves it to the details it opened, and deciding moves it to the next card's **Review**. Drawing one card at a time also keeps the screen fast: twenty of the largest cards drawn together held the browser for up to three and a half seconds.

A card can still move under your pointer: in the corner the stack is anchored to the bottom, so a card that opens grows upward and its **Approve** lands where **Review** was, and when a card below the open one leaves — it expired, or was answered in another tab — the open card drops into its place, **Approve** onto that card's **Review**; in the conversation, a card arriving above pushes the open one down. So **Approve** and **Deny** respond only once they have stayed in the same place for one second — after the card opens, and again after anything moves them, a scroll included. A press with the mouse or a finger counts only if it also started once they had stayed put, so a double click on **Review**, or a click aimed at a card that just left, approves nothing — even when you keep the button held down until a second has passed. While they wait, the card says they're _available in a moment_, and they stay in the tab order, so the keyboard reaches them as soon as the details open.

Because the agent is genuinely waiting, a confirmation doesn't stay open forever: **you have 10 minutes to answer**. Past that the agent stops waiting and the action stays blocked. If you answer after the agent has already given up — or if Pinchy can't reach the agent runtime at that moment — Pinchy tells you so instead of confirming, because your decision recorded but never delivered means the tool did **not** run.

## What gets recorded

Every step lands in the [audit trail](/concepts/audit-trail): the request, the decision (who approved or denied, and when), and the moment the action finally ran. The audit entries reference the action by a content hash, never its raw arguments, so sensitive details stay out of the log.

## Good to know

- **The check is enforced on the server**, inside the agent runtime — not in the browser. A gated tool can't run without a matching, approved, single-use confirmation, so the control holds even if someone pokes at the UI.
- **It's per person.** A confirmation you approve is yours; it never clears the same action for a teammate on a shared agent.
- **It fails safe.** If a confirmation isn't approved within 10 minutes, it expires and the action stays blocked. The same goes for anything the agent does outside a conversation with a person — a scheduled run has nobody to ask, so a gated tool simply doesn't run there.
- **You won't be buried in cards.** One agent can have at most 20 confirmations waiting for you at once. If an agent keeps asking, it's told to stop and to let you catch up first.
- **There is no "always allow".** The card offers approve-once and deny, and nothing else. A member tapping "always" would permanently overturn a policy an admin set, invisibly — so a more specific decision here may be equal or stricter than the one above it, never looser. The agent runtime enforces that, not the button.
- **Confirmations live in the Pinchy app.** On other channels (say, Telegram) there's no way to approve yet, so a gated tool stays blocked there — the safe default. If you want an agent to act freely on a channel, leave its tools un-gated; channel-side approval is on our list.
