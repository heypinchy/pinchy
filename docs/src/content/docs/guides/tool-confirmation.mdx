Some agent actions are worth a second look before they happen — sending an email, writing to Odoo, deleting a record. Tool confirmation lets you mark those actions so the agent **pauses and asks the person in the chat** before it runs them. The agent still does the work; a human just says "go" first.

This is a human-in-the-loop checkpoint, not a bottleneck: the person driving the agent approves their own action, in seconds, right where they're working.

## Turn it on for an agent

Confirmation is set per agent, by an admin:

1. Open the agent's **Settings → Permissions**.
2. Find **Require confirmation before**.
3. Check the tools that should pause for a confirmation — or click **Use recommended** to select the agent's powerful (write and side-effecting) tools in one go.
4. Save.

<Aside type="tip">
  "Use recommended" picks the tools that change things — the ones most worth a
  glance. Read-only tools stay un-gated so the agent keeps feeling fast. You can
  always adjust the list later.
</Aside>

## Per record type, for Odoo

"Ask before deleting" is often too broad. Deleting an invoice deserves a second look; deleting a note does not, and an agent that stops for both trains people to click through without reading.

So for Odoo the setting also lives in the **model table** on the same page, where each cell has three states:

|                 |                                                |
| --------------- | ---------------------------------------------- |
| **Not allowed** | The agent cannot do this at all.               |
| **Ask first**   | The agent pauses and waits for a confirmation. |
| **Allowed**     | The agent goes ahead on its own.               |

A cell you have never touched shows what it **inherits** from the tool setting above. That is deliberate, and it is what keeps the table honest: if you gate deletion for the agent, every model is gated — including ones you add next month. Setting a single cell to **Allowed** is how you make an exception, and it stays an exception.

The confirmation card names the record type, so the person deciding sees "Delete a record in Odoo — account.move" rather than a question they cannot answer.

<Aside type="caution">
  The check sees the call, not everything it sets off. Approving a write to an
  invoice also writes that invoice's lines, and confirming a stock transfer
  moves every line on it. Gate the operation you care about, and read the card's
  details rather than assuming the scope is one record.
</Aside>

Where a single action touches two record types — reconciling a bill against a payment, for instance — the **stricter** of the two settings wins.

## What the person sees

When the agent reaches a gated tool, it doesn't run it — it **waits**, mid-turn, holding the call open. A card appears **at the end of the conversation**, where the agent stopped, with the action and its details — for example, _"Smithers needs your confirmation: run `email_send` with `to`: ada@example.com, `subject`: Q3 numbers"_ — and two buttons:

- **Approve** — the agent picks the turn straight back up and runs the tool. You don't have to prompt it again.
- **Deny** — the action is blocked, the agent is told so, and it carries on with the rest of the turn.

### The card shows what will run

You approve what the card shows, so the card shows everything the tool will receive — not a summary of it:

- **Every value is spelled out, or the action isn't offered.** A list shows each entry on its own line, and an object shows each field with its value — nested up to ten levels, enough for a full Odoo invoice with its line and tax commands. You see the actual ids and field values of an Odoo write, not "1 item" or "2 fields". A card holds up to 100 fields per object, 200 entries per list, 200,000 characters per text — counted as the agent sent them, so a no-break space is one character even though the card spells it out as a marker — and 512,000 characters in all as shown on the card, markers, numbers and field names included. That covers ordinary work with room to spare, a report of a few dozen pages written to a file included. An action whose arguments don't fit is **refused instead of shown in part**: no card appears, the agent is told which limit the call crossed and where, and the audit trail records an `approval.refused` entry. Where the call can be split — too many fields, entries or recipients, or too much in all — the agent is told to split it into smaller calls; a single text that is too long, or arguments nested too deeply, can't be split, so the agent is told it is too long to show for approval and to stop. You never approve a card with something left out.
- **A value reads as its type.** Numbers, `true`/`false` and `null` appear as they are; a text that would look like one of them is shown in quotes. So `active: "false"` (text, which Odoo reads as _true_) can't pass for `active: false`, and `"1"` can't pass for `1`.
- **Every field name is shown as it is.** A field name that isn't a plain identifier is shown in quotes, with anything unusual spelled out: `"to "` (with a trailing space) appears as its own row next to `to`, and a look-alike name with a Cyrillic letter or a hidden character reads `"t⟨U+043E⟩"`. Two fields never merge into one row.
- **Every recipient is listed, address first.** For `to`, `cc` and `bcc`, the card splits the field into one line per address. An extra address tucked behind a comma, a semicolon or a long run of spaces becomes its own visible line. Each line starts with the address and puts the display name after it — `attacker@evil.com (name: "Raimund Korber")` — so a long, familiar name can't push the real address out of view. A domain with non-Latin letters is also shown in its ASCII form, so `boss@fіrma.at` with a Cyrillic "і" reads `boss@fіrma.at (xn--frma-l9d.at)` and can't pass for the real domain. The same goes for any value that is an email address or a web address, wherever it sits — an Odoo contact's `email` or `website` reads `https://fіrma.at (xn--frma-l9d.at)` too. For a web address, the card names the server the address actually reaches whenever that differs from the one it reads as: in `https://fіrma.at\@evil.com/x` the backslash ends the server name, so the card adds `(xn--frma-l9d.at)`, and `https://fir%6Da.at` reads `(firma.at)`. An email address or web address is never shortened to a preview, at any field, so the domain at its end is always in view.
- **Where the action lands is never shortened.** Recipients, and the fields that name a target — `path`, `filename`, `url`, `target`, an Odoo `model` and its `ids`, and the like — are never collapsed behind a preview, they're filled in before anything else, so a long message body can't push them off the card, and they're listed first on the card. Together with the refusal above, that means they are always on the card whole.
- **Text is shown as sent, and nothing in it can hide.** Spaces, tabs and line breaks are kept as the agent sent them; a Windows line break (CR LF) is shown as a line break, while a lone carriage return is spelled out as a marker. A run of four or more is shown as a count, such as `⟨180 spaces⟩`, so padding can't push text out of view. Every character that is invisible or renders as blank space — zero-width and text-direction controls, Unicode tag characters, variation selectors, no-break and other unusual spaces, Hangul fillers, the braille blank (U+2800) — is shown as a `⟨U+2800⟩`-style marker instead. A long run of them becomes one marker that says how many there are, such as `⟨180 invisible characters: U+2800 U+2800 U+2800 …⟩`, so text hidden in invisible characters is obvious without flooding the card. The emoji joiner (U+200D) and the text/emoji presentation selectors (U+FE0E, U+FE0F) are left alone inside an emoji, where they're part of what you see — 👨‍👩‍👧, ❤️. So are the zero-width non-joiner and joiner (U+200C, U+200D) where they shape Arabic-script or Indic text — the Persian گزارش‌ها, the Sinhala ශ්‍රී: right after a virama between letters of its own script (a joiner may also end a word, as in the Malayalam അവന്‍), or a non-joiner between two letters that would otherwise join. This follows the rule internationalized domain names use, approximately: it is exact for Persian, Urdu and Arabic letters, and generous for rarer joining scripts such as Syriac, where a non-joiner that changes nothing may still be shown as it is. A non-joiner after a virama with nothing after it to keep apart, as in `जगत्⟨U+200C⟩.md`, is marked. Anywhere else they render as nothing, so they're marked too: a company name `Noack⟨U+200D⟩ GmbH` is a different name from `Noack GmbH`, and an invoice reference `RE-1001⟨U+FE0F⟩` is a different reference from `RE-1001`, even though each would look identical.
- **Where the action lands reads as exactly one target.** In a field that names a target — a path, a file name, a record — two spellings that look alike are two different targets, so the card marks even what ordinary text keeps: a space, tab or line break at the start or end (`/data/out/report.md⟨U+0020⟩`), and a presentation selector that changes nothing because the character is an emoji anyway (`Vertrag ✅⟨U+FE0F⟩.pdf`).
- **Long text starts as a preview.** Any other text longer than 200 characters shows a preview that says how many characters are hidden, with **Show full text** to read all of it. The whole text is on the card — nothing is cut off behind the button.
- **Record references name their record.** An opaque Odoo reference shows the record it points at — model, id and name, for example `(record reference: account.move #42 "INV/2026/0042")` — so two invoices never look alike. Anything that isn't a reference Pinchy can read is shown as the text it is: an email body that happens to start like a reference, or that starts with a real one and carries more text after it, is still shown in full — and the Odoo tools refuse such a string as a reference, too.
- **Secrets stay hidden, but setting one doesn't.** Text under field names that look like secrets (tokens, passwords, API keys) is never shown, at any depth. The card still says that such a field is being set and how long the value is — `access_token: [secret-like field is being set — value hidden, 19 characters]` — because an agent writing a token of its choosing into a record is something to notice. Only text is hidden: a number, `true`/`false` or `null` can't hold a secret and is shown, a field ending in `_id` or `_ids` holds record ids and is shown in full (`payment_token_id: 7`), and a list or object under a secret-like name is shown field by field, with the text in it hidden.

On top of that, the tools themselves refuse what the card would have to explain:

- `email_send` and `email_draft` accept **exactly one recipient per call**. A string that holds a list ("a@x.at, b@y.at") is refused with an error telling the agent to send one mail per recipient, so no second address can ride along on the one you approved. So is an address that imitates a separator, such as a fullwidth `＠` in the display name. A display name may be up to 64 characters, with single spaces and no invisible or blank-rendering characters; emoji are fine, and so is a zero-width non-joiner where it shapes a Persian name such as علی‌رضا. A name with a comma or parentheses goes in double quotes, the way a mail program writes it — `"Müller, Hans" <hans@example.com>` is one recipient. Without the quotes, the comma would start a second recipient, so the tool refuses it and tells the agent to add them.
- `pinchy_write`, `pinchy_delete` and `pinchy_generate_file` refuse a path or file name that doesn't read as the file it reaches: one longer than 1,024 characters, one with a `..` segment, one not in its plain form (a `.` segment, an empty segment such as `//`, or a trailing `/`), one with an invisible or blank-rendering character, or one not in composed Unicode form (NFC). Visible-width spaces such as the no-break space are allowed — real file names carry them, and the card marks each one as `⟨U+00A0⟩`. So are emoji, ⚠️ and 👨‍👩‍👧 included: the emoji joiner and presentation selectors are accepted inside an emoji, where they are part of what you see, the zero-width non-joiner and joiner where they shape Arabic-script or Indic text (گزارش‌ها, ශ්‍රී — by the same rule the card uses), and both are refused anywhere else, where they would render as nothing, such as a non-joiner between `जगत्` and `.md` — and so is a presentation selector that changes nothing, such as U+FE0F after ✅, which is an emoji on its own. `pinchy_write` and `pinchy_delete` also refuse a file or folder name that starts or ends with a space, since `report.md ` would be a different file from `report.md`; `pinchy_generate_file` trims the name it is given, so either spelling writes the same file, and the card marks the spaces. The file you see on the card is the file that changes.
- `email_send`, `email_draft`, `pinchy_write`, `pinchy_delete` and `pinchy_generate_file` refuse any parameter they don't declare. A call carrying an extra, look-alike field like `"to "` fails before it does anything, and the audit trail records the refusal.

Approve clears exactly that one action. If the agent later tries something different — a different recipient, a different record — it asks again. One confirmation, one action.

If you've moved on to another chat in the meantime, the card follows you into the corner of the screen rather than disappearing — an agent waiting in a conversation you've left still needs an answer.

Because the agent is genuinely waiting, a confirmation doesn't stay open forever: **you have 10 minutes to answer**. Past that the agent stops waiting and the action stays blocked. If you answer after the agent has already given up — or if Pinchy can't reach the agent runtime at that moment — Pinchy tells you so instead of confirming, because your decision recorded but never delivered means the tool did **not** run.

## What gets recorded

Every step lands in the [audit trail](/concepts/audit-trail): the request, the decision (who approved or denied, and when), and the moment the action finally ran. The audit entries reference the action by a content hash, never its raw arguments, so sensitive details stay out of the log.

## Good to know

- **The check is enforced on the server**, inside the agent runtime — not in the browser. A gated tool can't run without a matching, approved, single-use confirmation, so the control holds even if someone pokes at the UI.
- **It's per person.** A confirmation you approve is yours; it never clears the same action for a teammate on a shared agent.
- **It fails safe.** If a confirmation isn't approved within 10 minutes, it expires and the action stays blocked. The same goes for anything the agent does outside a conversation with a person — a scheduled run has nobody to ask, so a gated tool simply doesn't run there.
- **You won't be buried in cards.** One agent can have at most 20 confirmations waiting for you at once. If an agent keeps asking, it's told to stop and to let you catch up first.
- **There is no "always allow".** The card offers approve-once and deny, and nothing else. A member tapping "always" would permanently overturn a policy an admin set, invisibly — so a more specific decision here may be equal or stricter than the one above it, never looser. The agent runtime enforces that, not the button.
- **Confirmations live in the Pinchy app.** On other channels (say, Telegram) there's no way to approve yet, so a gated tool stays blocked there — the safe default. If you want an agent to act freely on a channel, leave its tools un-gated; channel-side approval is on our list.
