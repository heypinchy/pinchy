title: Create a Knowledge Base Agent
description: Step-by-step guide to creating an agent that answers questions from your documents with cited sources.
---

This guide walks you through creating a Knowledge Base agent — an agent that searches an indexed set of your documents and answers with numbered citations back to the source document and page, instead of guessing.

## Prerequisites

- Pinchy is running (see [Quick Start](/getting-started/))
- You have mounted at least one data directory (see [Mount Data Directories](/guides/mount-data-directories/))
- A chat model is configured for the agent under **Settings → AI Provider**
- You are logged in as an admin

The knowledge base embeds your documents with a local model (`embeddinggemma`) that ships inside the Pinchy image, so there is nothing to pull or configure and no Ollama endpoint is involved — indexing and search work offline, independent of whichever chat model the agent uses.

## 1. Mount your data directories

Before creating a Knowledge Base agent, make sure the documents you want the agent to access are mounted under `/data/` — on **both** the `openclaw` and the `pinchy` service, since indexing reads them in the `pinchy` container. See the [Mount Data Directories](/guides/mount-data-directories/) guide for detailed instructions.

## 2. Navigate to "New Agent"

In the Pinchy sidebar, click the **+** button next to "Agents" to open the agent creation form.

## 3. Select the "Knowledge Base" template

Choose **Knowledge Base** from the template options. It's in the first group, **Knowledge & Compliance**, because it needs no integration — only a folder and a model that can read images and call tools. If your provider has no such model, the card is greyed out, as is every template except Custom Agent; see [Ollama setup](/guides/ollama-setup/#vision-templates). This template gives the agent the `knowledge_search` tool — a search over your indexed documents that returns citable passages, not raw file access.

## 4. Enter a name and create

Give your agent a descriptive name, for example "HR Policy Assistant" or "Engineering Docs". You can also add an optional tagline like "Answers questions about company HR policies". Select the directories under `/data/` that hold the documents this agent should search, then click **Create**.

The agent is created with an auto-generated avatar and you are taken to its chat page. The Knowledge Base template pre-fills operating instructions (AGENTS.md) with the agent's role, and attaches the [`knowledge-search` skill](/explanation/skills-and-templates/), which carries the cite-then-answer workflow. Pinchy starts indexing the directories you selected straight away, and the chat tells you how far it has got (see [step 6](#6-index-the-documents)).

Citing isn't left to the skill alone either. `knowledge_search` states the contract in its own results — cite the passages you used, list them with path and position (where the document has one) so a reader can check them, and say so when they don't answer the question — so an agent cites its sources even if you rewrite the instructions or build an agent without this template.

:::caution[Agents you created earlier]
Operating instructions are written once, when the agent is created, and are yours to edit from then on — Pinchy never rewrites them behind your back, which also means an upgrade cannot fix them for you. Open an existing agent's settings and check the **Instructions** tab: if they end in a `## File Access` block with a numbered **"Tool use workflow"** list, that agent still carries older guidance telling it to walk the folder tree instead of searching.

Delete that list and keep the paths above it, or create the agent fresh. Tool descriptions and search results steer the agent the right way regardless, so this is not a broken agent — but the two instructions pull against each other, and on a large corpus the older one has won.
:::

## 5. Configure directory access

The directories you picked when creating the agent live in its settings, where you can change them later. Open the agent's settings by clicking the gear icon, then select the **Permissions** tab.

![Permissions tab with safe tools and directory picker](/screenshots/agent-settings-permissions.png)

Under **Knowledge Base**, the **Allowed Directories** picker shows all directories found under `/data/`, each with its name and the path it's mounted at. Select the directories that contain the documents this agent should be able to search — or open one with the arrow beside it and select a folder inside it, so that one share serves one agent per department (see [Granting a subfolder](/guides/mount-data-directories/#granting-a-subfolder)). This is the same folder scope that governs everything the agent can retrieve and cite — an agent can never search or cite a document outside its granted directories. If no directory is listed, nothing is mounted under `/data/` yet; [Mount Data Directories](/guides/mount-data-directories/) shows how. A granted folder that no longer exists — a mount that was renamed, say — is marked "Folder not found" with a **Remove** button, so the agent doesn't keep a grant for nothing.

Click **Save** to apply the permissions. Until you do, a note under the picker says what saving will change — which directories the agent starts and stops reading — and **Reindex now** waits, because it works on the saved directories. A change takes effect the moment you save: the agent searches its saved directories on every question. Taking a directory away doesn't delete anything from the index; its documents just stop showing up in this agent's answers.

## 6. Index the documents

You don't have to start the first index. Creating the agent queues it for the directories you selected, and saving the **Permissions** tab queues it for any directory you add there — only for directories nothing has indexed yet, so saving the tab again, or granting a folder another agent already uses, queues nothing. One run happens at a time across your whole Pinchy (see below), so if another run is going, the first index waits for it and starts once the slot is free. Nobody has to come back and press anything. Like every reindex it's in the [audit trail](/concepts/audit-trail/), with `trigger: "initial"` and the admin whose grant started it — or `kb-index-worker` when Pinchy queued it itself, for instance after another run was in the way, or for an agent created over the API.

Until the first index has finished, the agent can't find anything in its documents. So its chat says so, right above the message box: "Reading this agent's documents for the first time — 120 of 505 done", or, while another run holds the slot, that indexing waits for it. When you add a folder to an agent that already has indexed ones, the notice talks about the newly added folders only: the agent keeps answering from the others meanwhile. If another agent's first index is already reading the same folder, the chat shows that run's progress — the documents arrive with it. Everyone who can open the chat sees it, not just admins, and it goes away once the run is done. Only the first index shows up there: a later run leaves the agent answering from the index it already has, so the chat stays quiet.

The run itself shows in the agent's **Permissions** tab, where the **Knowledge Base** section has an **Index** block. Its first line tells you where the index stands at a glance:

| Status              | What it means                                                                                                                                                                                                                                            |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **No directories**  | The agent has no saved directory to index yet.                                                                                                                                                                                                           |
| **No runs yet**     | Directories are granted, but this agent hasn't been indexed yet. Another agent's run may already have indexed the same directories.                                                                                                                      |
| **Indexing**        | A run is in progress. It keeps going if you leave the page.                                                                                                                                                                                              |
| **Indexed**         | The last run finished, and every document in this agent's folders has readable text.                                                                                                                                                                     |
| **Needs attention** | Something in this agent's folders can't answer questions: the last run couldn't read a document or a folder, or documents have no readable text. Documents without text are listed below the status; a document that failed to read is in the run's log. |
| **Failed**          | The last run stopped early. The reason is shown below it.                                                                                                                                                                                                |
| **Checking**        | Pinchy is loading the status.                                                                                                                                                                                                                            |
| **Unknown**         | Pinchy couldn't load the status. **Try again** asks once more.                                                                                                                                                                                           |

Beside it, the status says when the last run finished, in your own time, and what it found — say, "13 files checked, 2 new or changed". When a run you're watching completes, a short confirmation pops up too; a run that fails says so in the block itself. **Reindex now** starts a run yourself — to pick up documents added today rather than tonight, say — and the block shows any run inline — discovery, a live progress bar, how long the run has been going, an estimate of how much longer, and the last run's outcome — so you never have to leave the page or read a log. The estimate is deliberately shy: it appears only once the run has produced enough readings to support one, and it disappears again if progress stalls. On a real corpus a single large document can dominate the work, so a countdown that always shows a number would mislead more than it helps.

Reindex now is available over the API too:

```bash
curl -X POST -b session_cookie "https://pinchy.example.com/api/agents/<agentId>/knowledge/reindex"
```

This reads the agent's granted folders, extracts text from each PDF and reads the cells of each Excel workbook, splits the result into overlapping chunks, embeds every chunk with a bundled local model (`embeddinggemma`), and stores the result in Pinchy's own Postgres database (using `pgvector`) so it can be searched later.

Indexing is idempotent — unchanged files are skipped on the next run, changed files are re-indexed, and files removed from disk are dropped from the index. After the first run you don't have to come back: Pinchy reindexes the agent [every night](#keeping-the-index-current), so new files, edits and deletions are picked up on their own.

The request comes back immediately with a job to watch:

```json
{
  "jobId": "6f1c2b64-6c3e-4a2f-9c19-5c1d3a1f2e77",
  "status": "pending",
  "pathCount": 2
}
```

Indexing itself runs in the background. It has to: every page has to be read, split, and turned into a vector, and on a few thousand documents that's hours of work on a CPU. Nothing about that fits inside an HTTP request, so the request queues the run and hands you its id.

One index run happens at a time, across your whole Pinchy — the index is shared, and embedding is CPU-hungry enough that two runs would only slow each other down. Trigger a second while one is going and you get a `409` naming the run that's in your way, including which agent it belongs to. That may not be the agent you asked about; watch that one instead of retrying.

A first index of a large share takes a while, so we read your current documents before your old ones. Every file in an [archived folder](#current-documents-first) waits until everything else is in the index, and the rest is read one folder after another: everything in `Certificates/` that everyday search shows is in the index before we start on `Datasheets/`. You can let people try the agent on the first folders while the run keeps going. To make the run itself faster, give Pinchy more CPU: the embedding model gets one thread with the default `PINCHY_CPUS=1.5`, and up to six on a bigger box. A box that gives it six threads embeds about two and a half times as fast as one that gives it two. [CPU when the knowledge base embeds](/guides/customizing-deployment/#cpu-when-the-knowledge-base-embeds) explains how to set it. Scanned PDFs are sent to your vision model three pages at a time, so you wait less on the vision model too.

## 7. Watch the run

If you triggered the reindex from the **Permissions** tab, the **Index** control already does this for you — it polls in the background and renders the progress bar and the counts below the button until the run finishes. The rest of this section explains those same numbers, whether you read them there or over the API.

Over the API, ask the same endpoint how it's going:

```bash
curl -b session_cookie "https://pinchy.example.com/api/agents/<agentId>/knowledge/reindex"
```

```json
{
  "job": {
    "status": "running",
    "processed": 340,
    "total": 1893,
    "processedBytes": 806531072,
    "totalBytes": 4183396352,
    "counts": null
  }
}
```

`total` is every document we found across the granted folders, counted before the first one is read — so it doesn't move once the run starts. `counts` fills in as the run goes, so you don't have to wait until the end to see how it's going:

`processed` counts whole documents, so a long one holds the number still while we work through it — a 300-page PDF can sit there for minutes. That's the run being slow, not stuck. `processedBytes` keeps moving through it, though: it's weighed by file size and credited as each document's pages are embedded, which is why the progress bar and the estimate are built on those two rather than on the document counters.

| Field          | What it means                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `indexed`      | Added or updated, and searchable afterwards. The **Index** section shows this count as **new or changed**.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `skipped`      | Unchanged since the last run, left alone. The **Index** section shows this count as **unchanged**.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `removed`      | Gone from disk, dropped from the index.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `unsearchable` | Read without error, but the file holds no text to search — a scan no vision model was available to read or that wasn't read because reading scans is switched off, a workbook whose sheets are all hidden, or an Office file refused for its size or content (see [Scope in this release](#scope-in-this-release)). The **Index** section shows this count as **without readable text**.                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `failed`       | Couldn't be read or parsed at all, was refused because it had been [swapped for a link](/guides/mount-data-directories/#links-inside-a-mounted-folder) during the run, or the reader stopped before it had an answer — a workbook that ran out of time, say, or a disk too full for the private copy a file is read from, or for an Office file's checked copy or converted PDF (one exception, a PDF far larger than its file, counts as `unsearchable` instead: see [Customizing your deployment](/guides/customizing-deployment/#memory-when-the-knowledge-base-indexes-office-documents)), or the database or the embedding model refused what was read from it — or anything else went wrong with that one file. The run continues; if an earlier version of the file was indexed, that version stays searchable, and the file is read again on the next run. |
| `unsupported`  | Documents in the granted folders we can't index yet — an `.rtf` note, a binary `.xlsb` workbook, a photo or a scan saved as `.jpg`. They're not in the index at all, so they aren't part of the counts above; [Files Pinchy can't read](#files-pinchy-cant-read) names them.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `ignored`      | Files in the granted folders that aren't documents at all — programs, drivers, data exports, firmware images, video. We skip them on purpose and don't warn about them, but they're on the same list, so nothing goes missing without a trace.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |

`indexed` counts documents the agent can actually reach, not documents we processed — that's why a document we read but found nothing searchable in lands under `unsearchable` instead. If `unsearchable`, `failed` or `unsupported` is above zero, part of your corpus can't answer questions yet, and it's worth knowing which part before someone asks it something. For `unsearchable` you don't have to go looking: the **Index** section names those documents, folder by folder, and has them all as a download (see [Documents that can't be searched](#documents-that-cant-be-searched)). A `failed` file can't be named there — it never got far enough to have an entry in the index — so that one you find in the run's log. And `unsupported` has a list of its own: **Download the list**, below the counts (see [Files Pinchy can't read](#files-pinchy-cant-read)). `ignored` isn't on that worry list: those files were never documents, so nobody can ask about them.

A `status` of `failed` is a different thing from a `failed` file: it means something systemic stopped the whole run — the embedding model couldn't be loaded or reached, or the connection to the database was lost or the database shut down — and `error` says what. A broken file never gets that far, even one the database refuses to store or the embedding model refuses to take; it's counted and stepped over, and the run's log names it. A passage too long for the embedding model isn't even refused: it's split into pieces the model takes, each keeping the page or sheet it came from.

If Pinchy restarts mid-run, the run resumes on the next start. Nothing is lost and nothing is done twice: everything already indexed is skipped on the way back through.

## Keeping the index current

Once a night — at **02:00 in your [organization timezone](/reference/organization-timezone/)** unless you change it — Pinchy reindexes every knowledge-base agent on its own. A document someone drops into the folder during the day is searchable the next morning, an edited one answers with its new content, and a deleted one stops being cited. Nobody has to press anything.

A night is cheap after the first run. Every file is read once to check whether it changed, and only what changed is extracted and embedded again. The rest is `skipped` — including a document that came out `unsearchable`, unless something has changed that could read it differently (see the scans below). On a large share the reading is most of the work, so the run takes about as long as copying the folder once — on a slow network share that can be an hour or more, which is why it runs at night. That's per agent: two agents granted the same share each read it. An agent granted a subfolder reads only that subfolder, at night and on **Reindex now** alike, so one agent per department costs no more than one agent for the whole share. That holds with `PINCHY_KB_OCR=off` too: a scan the text layer can't read is parsed once, not every night.

What's covered: every agent that has the `knowledge_search` permission and at least one granted folder. Those are the agents that search the index, and between them their folders are everything a search can reach. An agent that only reads files isn't swept. The **Index** section in each agent's **Permissions** tab says which applies, and when the next run is — in your own time, the way it shows when the agent was last indexed. If you're in a different time zone from the organization, the time it's set to is shown beside yours.

How it runs:

- **One agent at a time.** The nightly run queues the agents one after another, behind the same one-run-at-a-time rule as **Reindex now**. If a run is already going at 02:00 — say you started a big one at half past one — the night waits for it rather than cancelling it. If that run lasts into the morning, the agents behind it run when it finishes, which can be during the working day. The agent whose run it was is left for the next night: that run has only just read its folders — as long as it finished successfully and covered all of them. A run long enough to outlast the following night's start too (a first index of a very large share can) counts for that night as well, so the next run is the night after, not the moment it finishes.
- **A share that isn't there doesn't empty the index.** A network share that failed to mount looks, from inside Pinchy, like a folder that is missing or suddenly empty. So a folder that can't be read is skipped, and a folder that comes up completely empty while the index still holds documents from it is skipped too — nothing under it is removed. That holds for a granted folder and for any folder inside one (a share mounted at `/data/contracts` under a granted `/data`), and for every run, including one you start with **Reindex now** — retrying a failed night while the share is still down must not delete its index. When a run had to leave folders out, the **Index** section says how many; if it could read none of an agent's folders, the run is marked failed and names them, each with what to check: a folder that's gone — renamed or deleted — belongs out of the agent's **Allowed Directories** (the picker marks it "Folder not found"), one Pinchy can't open needs its permissions fixed on the server, and one that came up empty is most likely a share that didn't mount. To drop the documents of a folder you emptied on purpose, delete the folder itself, or take it out of the agent's granted folders.
- **A missed night is caught up.** If Pinchy wasn't running at 02:00, the night runs when it starts again. Once, not once per missed night.
- **A restart doesn't lose it.** An interrupted run resumes on the next start, and agents still waiting for their turn keep their place.
- **It's on the record.** Each run is audited like any other reindex, with `trigger: "scheduled"` and a `sweepId` shared by every agent reindexed that night — see [Audit trail](/concepts/audit-trail/).
- **Scans are read like any other run's.** A new scanned PDF or TIFF is sent to your vision model the night it first appears. Once its text is in the index it's `skipped` like any unchanged file, so it isn't sent again. A scan the model found no text in at all stays `unsearchable`, and it isn't sent again either: the same model would find the same nothing. It's read again only when that could change: when OCR has been switched on since the scan was last read, when a different vision model has been configured, or when an update to Pinchy reads documents differently. A scan whose vision call **failed** is read again on the next run — including the failed pages of a scan whose other pages are already searchable — which is how a provider outage heals by itself. That retry stops after five runs in a row, so a page the provider rejects every time isn't sent again every night. The same five tries apply to a Word or PowerPoint file that couldn't be converted. The **Index** section lists those documents by name. `PINCHY_KB_OCR=off` stops all of it exactly as it stops a manual run; see [What indexing sends to your provider](/guides/mount-data-directories/#what-indexing-sends-to-your-provider).

To change the time or switch it off, go to **Settings → Organization → Knowledge Base Indexing**. A new setting applies from its next occurrence: switching it back on in the afternoon doesn't start a run then and there. With it switched off, new documents show up only when someone clicks **Reindex now**.

One kind of run doesn't wait for the schedule, and runs with it switched off too. When an update to Pinchy changes how Word and PowerPoint files are converted, every such file already in the index has to be converted again, and until it has been, search leaves it out, its preview doesn't open, and the Index section lists it under [Documents that can't be searched](#documents-that-cant-be-searched), marked as waiting to be converted again. So Pinchy queues that run itself when it starts, and looks again every hour after: one reindex for each knowledge-base agent whose folders hold such files, one after another, behind whatever run is already going — except an agent whose such files all lie in folders a successful reindex under the new rules started going through less than 24 hours ago, whatever started it: one of these runs, the nightly one, or **Reindex now**. That run converted what it could, so a second one over the same folder would change nothing. A run that finished before the update doesn't count, even within the day: it converted nothing under the new rules. A run that failed holds its folders back for six hours from when it started rather than a day: it's no evidence they were converted, so Pinchy tries again then — and a failure that doesn't go away, like a share that didn't mount, costs four failed runs a day rather than one every hour. A run that succeeded but couldn't read one of its folders — the **Index** section says so under the run — counts like a failed one: it never read that folder. A restart resets neither. While the bundled embedding model is missing, no such run is queued at all: it could only fail, and the nightly run and **Reindex now** already say so. The server log says the conversion is waiting for the model instead. Like the nightly reindex, it leaves out agents that only read files and don't search the index: running their folders would index everything they can read for nobody. A file no knowledge-base agent's folders hold anymore stays left out until one is: once an agent that searches the index is granted its folder, or an agent granted its folder is given `knowledge_search`, Pinchy's next hourly look queues the run that converts it. The **Index** section shows it as indexed automatically, and the audit trail records it with `trigger: "upgrade"`. A file whose conversion can't finish on that run stays left out, and listed: Pinchy runs its folder again 24 hours after the last run over it started, and a nightly run or **Reindex now** in between counts as that run, so the folder isn't read twice in a day on its account.

Pinchy doesn't watch the folder for changes. File-change notifications don't arrive from network shares (SMB/CIFS), which is where knowledge bases usually live, and polling a large share every few minutes would mean reading it all day. A nightly run is the mechanism, not a stopgap. If a document needs to be searchable before tomorrow, click **Reindex now** — it takes the same route through the index and costs the same.

## See what the agent can search

The counts tell you how a run went. They don't tell you which part of your share an answer can come from. The **Folders** list does. You'll find it in the **Index** section, below the counts. Each granted folder and the folders directly inside it show one state:

| State               | What it means                                                                                                                                                                               |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Indexing now**    | The run is working through this folder right now. The count says how far it has got.                                                                                                        |
| **Queued**          | The run will get to this folder later. Until then, the agent answers from what was indexed before.                                                                                          |
| **Searchable**      | Every file the last run found here is in the index. While a run is still reading this folder's archive, every current one is (see below).                                                   |
| **Needs attention** | Some files here can't be searched: they hold no readable text, they're waiting to be converted again, or fewer files made it into the index than the run found. **Files** shows which ones. |
| **Not indexed yet** | No run has read this folder. A folder you granted today is in this state until the [nightly reindex](#keeping-the-index-current) or **Reindex now** gets to it.                             |
| **No files**        | The last run found nothing to index here.                                                                                                                                                   |

The count beside each folder is measured against what the last run found there, not against what made it into the index. So `40 of 100 files searchable` means 60 files aren't searchable yet, not that the folder holds 40.

Every run reads [archived folders](#current-documents-first) last, so on a large share a folder's current files can be in the index hours before its `OLD/` subfolder is. The folder doesn't wait for its archive: once every current file in it is in, it says **Searchable**, and the count tells you what's left of the archive — `677 of 677 files searchable · 428 archived files queued`, or `indexing archived files, 425 left` while the run is reading them. While its current files are still being read, the count is against them alone, with the archive beside it: `675 of 677 files done · 428 archived files queued`. A folder that holds nothing but archived files has no current files to be searchable for, so it stays **Queued** and then **Indexing now** until the run is through all of it: `1 of 5 archived files done`.

**Files** lists a folder's files, 50 at a time, each with its own state. On a granted folder it lists only the files directly in it; each subfolder has its own row and its own list. **Not yet searchable** shows only the files an answer can't come from, and the search box filters by name. Some states need a word of explanation. **No searchable text** is a scan or file with nothing to read (see [Documents that can't be searched](#documents-that-cant-be-searched)). **Not indexed** means the last successful run saw the file and it still isn't in the index; the run's log says why. **Added since the last run** is a new file that the next run picks up. **Changed since it was indexed** is still searchable, but in its old version until the next run. **File type not supported yet** is a document the index can't read, and **Not a document — skipped** is a program, a data file or anything else that was never a document (see [Files Pinchy can't read](#files-pinchy-cant-read)). Both are counted apart from the rest, so `12 of 40 files searchable, plus 3 files the index can't read yet and 5 files skipped because they aren't documents` means 40 files the index reads. A folder with 20,000 files or more is listed only in part, and the list says so.

Everyone who can chat with the agent can see this, not only admins. "Why doesn't it know about the new price list?" is usually a member's question. In the chat, the folder button in the header opens **What can this agent search?**, which shows the same list, read-only. It only appears for an agent that searches the knowledge base. It names the granted folders and every file in them except hidden files and operating-system clutter, including files search can't return, such as scans and file types the index can't read. Nothing outside the granted folders appears.

## 8. Chat with the agent

Go back to the agent's chat and start asking questions. The agent calls `knowledge_search` behind the scenes, which runs a hybrid search — semantic (vector) and full-text — over the passages you indexed, then answers using only what it found.

### Cite-then-answer

Every grounded answer cites its sources inline, like `[1]` and `[2]`, and ends with a **Sources** list mapping each number to its document path and the spot inside it:

```
**Sources:**

- [1] handbook/policies/Employee Handbook.pdf — p. 12
- [2] handbook/policies/Employee Handbook.pdf — p. 14
```

The spot is a page, slide, section heading or row range. Some passages have none — a Word file without headings, for example — and then the entry is the path alone; the agent doesn't announce a missing position.

That makes every claim in the answer traceable back to a specific document and a specific spot in it, even though the underlying search results aren't shown in the chat.

Sources are named by their path, not just the filename. In a real document tree a bare filename is often impossible to act on — you can't tell which of several folders it lives in, and two folders may hold files with the same name. The path is what lets you open the document and check the claim for yourself.

The path you see is the one you'd recognise: it starts at the folder you mounted, not at the container path underneath. If you mounted a share as `quality`, a citation reads `quality/QM/Handbook.pdf` — the same tree you see in Explorer, minus the plumbing.

Not every document has pages, which is why a citation says "the spot" rather than "the page". A PDF is cited by page and a slide deck by slide number, because both are properties of the file itself. A Word document is cited by its heading path instead: where a Word page break falls depends on fonts and printer settings, so a page number would describe our rendering of the document rather than yours, and a citation should never state something you can't verify in the file you open. A spreadsheet is cited by sheet and row range — `Suppliers, rows 5-12` — which is what you scroll to in Excel, and what a page number could never be for a sheet forty columns wide.

### Open a source and check it

Each source path in an answer is a link. Click it and the PDF opens in a viewer over the chat, at the cited page, with the answer still visible behind it — the same viewer a PDF you attach to a message opens into. Checking a claim takes a click instead of a hunt through folders.

A PDF cited by page, a slide deck cited by slide and a Word document cited by heading open with **the passage the answer came from highlighted**, scrolled into view, so on a dense page you don't have to hunt for the sentence. Pinchy draws that page itself — the browser's own PDF viewer can jump to a page but can't mark text on it — and asks the index which of the page's passages the answer drew on, using the answer's own words. That works even when the answer is in English and the document in German, because the match is by meaning, not by wording. The arrows below the page take you to the pages around it, and **Open in new tab** still gives you the browser's full viewer, for searching the whole document, selecting text or printing.

If Pinchy can't tell which passage it was, it shows the page without a highlight rather than guess, because a highlight is a statement that the answer came from that text. That happens when the page holds several passages and Pinchy can't tell which of the answer's sentences the source backs — for example when the Sources list is numbered `1.` instead of `[1]`, so no sentence in the answer refers to it — and on a scanned page whose text was read by a vision model rather than taken from the PDF — there is no text on the page itself to mark. A file Pinchy can't draw opens in the browser's viewer as before, and so does a PDF cited without a page.

Word documents and slide decks are shown as the PDF Pinchy converted them to. A slide is the same page of that PDF, so a slide citation opens like a page citation. A Word citation names a heading instead, so Pinchy looks the heading up in the PDF's table of contents and then searches only that section's pages for the passage — on a 400-page manual that's a few pages, not the whole file. It opens at the start of the section right away and moves to the page holding the passage as soon as Pinchy has found it — unless you've already paged on. When the passage isn't within the section's first 25 pages, it stays at the start of the section. If the heading isn't in the document any more — renamed since the last index run, say, or written differently in the answer — the document opens in the browser's viewer at its first page, as Word citations did before. So does a Word or slide citation that names no heading or slide at all.

A spreadsheet opens differently, because a sheet has no pages to open at. Clicking one shows you **exactly the cited rows** as a table, with the sheet's own column headers above them and its own row numbers beside them — so the row you are looking at is the row you would scroll to in Excel. A workbook mentioned without naming rows opens the same pane at the top of its first sheet. Converting the workbook to pages was the obvious alternative and is the wrong one: pagination cuts a column that is too wide, which is precisely the text the index went out of its way to keep. The workbook itself is one click away in the same pane, for everything a preview is not for. Workbooks are read one at a time, so when several previews are already waiting, a further one asks you to try again in a moment instead of joining the queue — and a preview you close stops being read.

Word documents and slide decks open in the PDF viewer, not the sheet pane. No browser renders a `.doc`, so what you see is the PDF Pinchy converted on its way into the index — the same copy the search read, which is what lets a citation point at a spot you can actually find. The original is never modified and never replaced; it stays exactly where it is on your share. After an update that changes how these files are converted, an older citation of one opens its preview again once the file has been converted anew (see [Keeping the index current](#keeping-the-index-current)); the original downloads in the meantime.

That shared copy has one consequence worth knowing before you index a folder of drafts. A conversion prints the document as it stands, so text a tracked change deleted — but nobody has accepted yet — is still there, struck through, and is therefore searchable. It is not hidden from you: you see the same struck-through line when you open the citation. Comments and speaker notes are a different matter and are not converted at all, so they never enter the index.

Document size is not a limit. Knowledge bases routinely contain scanned compilation binders of several hundred megabytes, and because those contain the most, they tend to be cited the most. Pinchy streams the file and serves byte ranges, so the viewer fetches the pages it renders rather than the whole document — opening page 510 of a 268 MB binder transfers a fraction of it.

Reading the answer is often not the end of the job — sometimes you want the document itself, to send it on to a customer. The viewer's header carries a **Download** control beside the document's name, so the file lands in your downloads folder under its own name, umlauts and all, without a detour through a remote desktop.

For a Word document or slide deck you get two, labelled so you can tell them apart: **Original (.doc)** is the file as it sits on your share, the one to attach to a mail, and **PDF** is the converted version you were just reading. Hover over either to see the file name it saves as. Often that PDF is what you wanted to send anyway, and this saves you converting it yourself.

Opening a source is governed like every other access. The link resolves against the same allowed directories that scope the agent's search, so a path outside them is refused even if an answer names one. A converted PDF is reachable only through the document it came from, so it is governed by exactly the same grant — there is no second door into it, and a document nobody may read has no readable conversion. Each view is written to the audit trail as `knowledge.source_viewed`, and each download as `knowledge.source_downloaded` — reading a document and taking a copy of it out of the building are different acts, and only the second one can be answered with "who has this file now".

The list resolves exactly the numbers the answer cites — no more and no fewer. A number with no entry would be a dead end, and an entry the answer never cited would make a single source look like several.

### Regression-protected

Citation accuracy isn't just a goal here — it's tested. Every change to the knowledge base runs against an automated test suite that checks retrieval quality (the right passages come back for a query) and citation integrity (every `[N]` in an answer resolves to a real, correctly-formatted source, and vice versa). A change that broke either would fail before it ships. We also track groundedness — whether an answer's claims are actually backed by what it cites — against a reference set of questions, so accuracy is measured over time, not just assumed.

### Honest when it doesn't know

If the indexed documents don't contain the answer, the agent says so instead of guessing. If only part of a question is answered by the sources, it answers what's supported and flags what's missing rather than padding the rest.

### Cross-language

The agent answers in the language you asked in, even if the source documents are written in a different language. Ask in Polish about a German test report and you get a Polish answer. The quote and the document title stay in German, as they appear in the file you open. If you ask for a different language ("Bitte auf Englisch: …"), you get that one.

Every agent with `knowledge_search` gets the rule at the end of its instructions, the same on every turn. When we can tell which language your message is in, we also name it: in a short note on the first message of a conversation and whenever you switch languages, and at the end of every `knowledge_search` result, together with your question, right after the passages. The passages themselves are marked as quoted documents, so their language doesn't pass for the language of the conversation. When we can't tell, the rule still asks for the language of your message, without naming one.

Models need this most when the agent itself sounds like the documents. In our cross-lingual eval (German documents, questions in Polish, Italian and English), an agent with a German name answered a third or more of the questions in German, on Claude Haiku 5.5 and Claude Sonnet 5 alike. With the language named, Haiku 5.5 answered 47 of 48 first questions in the right language, and 43 of 48 follow-up questions in the same language. Sonnet 5 answered all of them correctly. One case is still hard for Haiku 5.5: when the agent's own instructions are written in German and the user switches languages within a chat, it answers about one question in four in German. Sonnet 5 answered every one of those correctly. If your team writes its agents' instructions in one language and asks in several, give its knowledge base agent Sonnet 5.

### Current documents first

Real document trees keep old material around — a quality binder full of expired certificates, a `Archive/` folder of superseded revisions. Answering a "what's our current certification?" question with a document that expired years ago isn't a small mistake; for a compliance question it's a dangerous one.

So we treat archived folders as archived. When we index your documents, any file sitting under a folder whose name contains one of the words `old`, `older`, `archive`, `archives`, `archived`, `expired`, `obsolete`, `Archiv`, `archiviert`, `alte`, `ältere` or `veraltet` is marked archived and left out of everyday search. Case doesn't matter, and the word can sit anywhere in the folder name, as long as it stands on its own: `OLD/`, `X_OLD/`, `Old certificates/`, `older versions/`, `OLD - don't use/`, `OLD2019/`, `Expired/` and `Alte Versionen/` all count. So does `xOLD/`, the run-together spelling of `X_OLD/`. A word that merely contains those letters doesn't: `Gold/`, `AccuScan Gold/`, `Folder/` and `Archivübersicht/` stay current. A change of case doesn't separate words, so `OldVersions/` stays current too. The other way round, a current folder that uses one of the words on its own — a supplier called `Old Mill Foods/` — is treated as archived. The document is still indexed — nothing is lost — it just doesn't compete with current material by default.

Only the folders inside the folder the agent is granted count. If the granted folder is itself called `Archiv`, or sits somewhere below one — `/data/Archiv/Projekte` — its documents are current: you granted that folder on purpose, so we don't hide what's in it. The archive status is one value per document for your whole Pinchy, so when two agents are granted nested folders, the folder granted further down decides: if one agent searches `/data/Quality` and another `/data/Quality/Archive`, the documents in `Archive/` are current for both.

Date and year folders like `2013/` or `Q3/` are **not** treated as archives: those are almost always live structure, not an archive. A file only counts as archived because of the folder it lives in, never because its own name contains one of those words. The German `alt` doesn't count either: in a folder name it means "alternative" just as often (`Logo alt/`). If your old material sits in a folder called `Alt/`, rename it to `Archiv/`.

If you genuinely need to search the archive too — "find me the 2013 certificate" — that's still possible: the agent can opt into including archived documents for a specific search. Everyday questions just won't surface stale material on their own. The **Index** section shows how many of the documents the last run read sit in archive folders, so you can check that the ones you expect are recognised as archived.

### One binder can't crowd out the datasheet

Some corpora contain large compilation documents — a single "quality file" binder that reprints dozens of individual datasheets. Left unchecked, a binder like that can fill an entire result list with its own pages and push the clean, single-topic source out of the answer, so a citation points at a 500-page binder instead of the 8-page datasheet it copied.

We cap how many passages any one document can contribute to a single answer, so a result set always spans several distinct documents. The binder still appears when it's genuinely the best match — it just can't monopolize the answer and hide the cleaner source behind it. Documents at different folder paths stay independent even when their content is identical, so this never collapses a file one team can see into one only another team can.

## Scope in this release

What the knowledge base does is deliberately narrow:

- **PDFs**, **scanned TIFF images** (`.tif`, `.tiff`), **Excel workbooks** (`.xlsx`, `.xlsm`, `.xls`), **Word documents** (`.doc`, `.docx`, `.docm`), **slide decks** (`.ppt`, `.pptx`), **plain text files** (`.txt`) and **Outlook emails** (`.msg`) are indexed and searchable via `knowledge_search`. Markdown files are not; the **Index** section counts them and offers the list as a download (see [Files Pinchy can't read](#files-pinchy-cant-read)). The two sides also do not line up in the other direction: pointed at a file directly, the agent's file tools read Markdown the index never takes, and cannot open the legacy `.doc`, a TIFF or an Outlook `.msg` the index reads fine. [Supported file types](/guides/mount-data-directories/#supported-file-types) has the full split.
- **Scanned PDFs and TIFF scans are indexed by sending their pages to a vision model**, the same one that reads a scan when you open it in chat. That is the one step of indexing that transmits document content to your model provider, and it applies to every scanned page in the corpus rather than only the ones somebody asks about. [What indexing sends to your provider](/guides/mount-data-directories/#what-indexing-sends-to-your-provider) states the data flow, how to turn it off, and why an air-gapped instance cannot use it yet.
- Indexing runs in the background and reports its progress in the app. The first run starts on its own when you grant a directory (step 6); after that the [nightly reindex](#keeping-the-index-current) keeps the index current. Nothing watches the folder in between, so a document added at 10:00 is searchable the next morning, or straight away if you click **Reindex now**.

### Documents that can't be searched

A gap you can't see is worse than one you can. If an agent answers "I found nothing" about a scanned certificate, it sounds like a statement about your company — not about the index — and nobody thinks to check.

So the **Index** section in the agent's Permissions tab lists the documents this applies to: everything that was indexed but produced no searchable text, and every Word or PowerPoint file search leaves out until it has been converted again after an update (see [Keeping the index current](#keeping-the-index-current)), marked as waiting to be converted again. It counts the two kinds separately, because they mean different things: a document with no searchable text needs something that can read it, while a file waiting to be converted has its text and only needs a run. For an agent that searches the index, Pinchy runs that conversion on its own; for an agent that only reads files, **Reindex now** does it. It's scoped to the folders that agent is granted, exactly like search itself, so the list never mentions a document the agent isn't allowed to know about. Documents in archived folders are marked as such — they're already out of everyday search.

The count of documents with no searchable text covers everything in those folders, while the `unsearchable` count above it covers only the documents the last run actually touched — a file that hasn't changed since the run before is `skipped`, not counted again. So that count is usually the larger of the two, and that's them agreeing, not disagreeing.

A large share can hold thousands of such documents, so the section starts with the count and keeps the list closed. **Show the documents** opens it grouped by folder — each folder directly inside a granted folder, with how many documents it holds — and a folder shows its files when you open it, file name first, with the path below the granted folder beside it. A folder lists its first 100 files. **Download the list** gives you every one as a CSV, with its file name, folder, reason, whether it's archived, and full path, so you can sort and filter it in a spreadsheet.

The list is how you find out which questions your agent can't answer, before somebody asks one of them. Why a document has no text depends on how the server is set up right now, so the section says which of these applies and to how many documents, and the download says it for each one:

- **Reading scans is switched off on this server** — `PINCHY_KB_OCR=off`. No vision model changes that. Once it's switched on, the next run reads those scans.
- **No vision model is available to read scans** — reading scans is on, but the instance has no model that can read them, for example because its only models are local. Make one available and the next run reads them.
- **Will be read on the next run** — a vision model can read them now, an older version of Pinchy read them, or the last attempt didn't finish. The next run, the nightly one included, reads them again. A Word or PowerPoint file the converter refuses shows up here for its first runs, while Pinchy still tries it again.
- **Couldn't be read: the vision model failed on every attempt** — five runs in a row, every call to the vision model failed, for example with an error from the provider or a timeout. Pinchy stops sending it then. Configure a different vision model, or replace the file, and the next run reads it again.
- **Couldn't be read: the file is too large, damaged, or not what its name says** — the converter or the workbook reader refused it, for good (a Word or PowerPoint file after five tries). The server log names each refused file and the reason. A file that's replaced is read again on the next run. A workbook with nothing visible in it — no cells, or every sheet hidden — lands here too, because it looks the same to the reader as one it refused; that one isn't in the log.
- **Read in full and holds no text** — a blank page, a picture without words, or a scan too faint to make out. Another run with the same vision model won't change that.

An Office file reaches it for a different reason when Pinchy declined to open it. Indexing treats Office files as untrusted: it converts a `.docx` or `.pptx` from a checked copy with its external links and risky parts removed, and it lists a file as unsearchable, without converting it, when it is too big to open safely, when its content isn't what its name says — an HTML page renamed `.doc`, or an HTML table an export tool saved as `.xls`, for example — or when it is put together in a way no Office application writes. A workbook is read in a separate process with a memory and time limit of its own, and so is a Word or PowerPoint file while it is checked; one that needs more memory than that is listed the same way. One that runs out of time, or whose process the system stops because the server ran short of memory, is not: that can be a busy server rather than the file, so it counts as `failed` and is read again on the next run. The same goes for a Word or PowerPoint file whose checked copy or converted PDF can't be written because the disk is full. A file that was refused stays on the list until it is replaced; the reason (which file, and why) is in the server log. [Supported file types](/guides/mount-data-directories/#supported-file-types) has the limits. An agent can still be pointed at such a document directly, which reads it with the model's vision capabilities.

If the list is empty after a run that finished, that's the whole message: every document in those folders came back with searchable text. After a run that failed we don't say it — the run stopped early, so there's nothing solid to say it about.

### Files Pinchy can't read

Not every file on a share is one we can index. An `.rtf` note, a workbook saved as binary `.xlsb`: the run finds them, and leaves them out of the index. Without a word, that looks like a model problem. A folder of 13 files reports 11 documents, and the agent can't answer a question the other two would have answered.

So the run counts them — `N not supported yet` in the **Index** section — and after a run that finished, **Download the list** gives you a CSV with every such file's full path and type. Sort it by type and you know what to do: save the notes as PDF, the `.xlsb` workbooks as `.xlsx`, and the next run picks them up. Or tell your users up front that the agent can't see them.

A share holds more than documents, though. Next to the price lists sit installers, driver `.dll` files, `.json` exports, firmware images and videos. Those were never documents, and calling them "not supported" would bury the two notes that matter under four hundred files nobody has to do anything about. So we count them apart, as `N ignored (not documents)`, not as files Pinchy can't read. A folder of PDFs and drivers reports its PDFs and says it skipped the rest. We skip them; we don't hide them: they're on the same list, and its `status` column says `not supported yet` or `ignored` for each file, so you can filter one way or the other. Pictures and scans (`.jpg`, `.png`), mails, office files we can't read yet, Markdown, HTML and CSV, page formats such as `.epub`, signed documents (`.p7m`), saved web pages (`.mht`), technical drawings and archives count as documents. Everything else, including a type we have no name for, is ignored. If a file you need to search lands under `ignored`, convert it to a format the index reads.

The list is scoped to the agent's granted folders, like search itself. It describes the share as the last run that finished found it, so a file you converted drops off after the next run. A folder the run couldn't read — a share that failed to mount — keeps the files it listed before: we don't know they're gone. That's also why the list can be longer than the count: the count is what this run found, and the list adds what it couldn't look at. The list follows the agent's folders as they're granted now, too, so a folder granted since the last run shows up in it before it shows up in the count. Hidden files and the clutter operating systems and Office leave behind (`Thumbs.db`, `~$Report.docx`, `*.tmp`) aren't documents, so they aren't counted or listed.

A large share can hold a hundred thousand such files, which is why the list is a download and not a panel: the file can be as long as it needs to be. The CSV is UTF-8 with a byte-order mark, so Excel shows umlauts correctly. If your Excel expects semicolons and puts everything in one column, open it through **Data → From Text/CSV** instead.

Every retrieval and every reindex is recorded in the [audit trail](/concepts/audit-trail/) — each `knowledge_search` call as `retrieval.query` with the documents it drew on (and a flag when the search reached into archived material), and every reindex as two `knowledge.reindex` entries sharing a `jobId`: who asked for it, and how it turned out, including how many documents were archived. Both are needed, because the run finishes long after the request that started it. The search query text itself is never stored in plaintext, only a one-way hash.

## Customizing the agent

Beyond permissions, you can customize your Knowledge Base agent through its settings tabs:

- **General** — Change the name, tagline, avatar, or model, and add **starter prompts**: the clickable suggestions shown in an empty chat. A Knowledge Base agent starts without any, because we can't know what your documents cover or which language your team works in. Add two or three questions your colleagues actually ask, in their language, and they'll see them the first time they open the chat.
- **Personality** — Choose a personality preset (e.g. The Professor for a formal tone) or write custom personality instructions
- **Instructions** — Edit the operating instructions that tell the agent how to cite documents and when to abstain

To add organization-specific context like team structure or terminology, go to **Settings → Context**. This context is applied to all shared agents, not configured per-agent.

## Changing permissions later

You can update an agent's permissions at any time by returning to the **Permissions** tab. Add or remove directories and click **Save**. A directory nothing has indexed yet gets its first index as soon as you save, exactly as on creation; one another agent's run has already gone through is searchable straight away, and one another agent's first index is still reading becomes searchable when that run finishes. Giving an agent that already has directories the `knowledge_search` permission counts as granting them.

## How it works

Under the hood, Pinchy uses an allow-list approach. The agent starts with no capabilities and only gets the tools an admin explicitly enables — here, `knowledge_search`, scoped by the same folder allowlist as everything else. For a full explanation, see [Agent Permissions](/concepts/agent-permissions/).
