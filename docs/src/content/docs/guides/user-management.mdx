Pinchy uses an invite-only system for user onboarding. Admins create invite links, new users claim them by setting up their account, and then they are guided through an onboarding conversation with Smithers. This guide covers the full lifecycle: inviting, onboarding, managing, and deactivating users.

Every account comes from one of two places: the setup wizard, which creates the first admin, or an invite someone claims. Self-sign-up is closed: there is no public registration endpoint. Of the underlying authentication library's endpoints, clients reach only sign-in, sign-out and the session lookup; its sign-up and user-administration endpoints (`/api/auth/sign-up/*`, `/api/auth/admin/*`) answer `404` to every client — including admins. Users are created, promoted and deactivated only through the flows described here, and each of those steps is written to the [audit trail](/concepts/audit-trail/) — account creation as `user.created`. Releases up to v0.9.1 left sign-up open; if an account from that time is still around, **Settings → Users** shows it in a banner (see [Accounts nobody invited](#accounts-nobody-invited)). See [Endpoints closed to clients](/guides/hardening/#endpoints-closed-to-clients).

## Prerequisites

- Pinchy is running (see [Quick Start](/getting-started/))
- You are logged in as an admin

## Inviting users

![User management showing active users and pending invites](/screenshots/user-management.png)

Only admins can invite new users. Here is how:

1. Go to **Settings → Users**.
2. Click the **Invite User** button in the top right.
3. Fill out the invite form:
   - **Email** — The new user's account is created with this address, and they sign in with it.
   - **Role** — Choose **Member** or **Admin**.
   - **Groups** <Badge text="Enterprise" variant="note" /> — If you have an active enterprise license and have created groups, you can assign the new user to one or more groups during invitation. See [Groups](/concepts/groups/) for details.
4. Click **Create Invite**.
5. Copy the generated invite link and send it to the user yourself — by email, chat, or however your team talks. Pinchy doesn't send emails, so the link only reaches them through you. Below the link, the dialog shows when it expires.

On devices that support it, a **Share** button appears instead of Copy, letting you send the link directly via your operating system's share sheet.

<Aside type="tip">
  Anyone who has the link can claim the invite, and the account they create gets
  the email you entered. Share the link only with the person you invited.
</Aside>

<Aside type="note">
  If your enterprise license has a seat cap and all seats are in use, the
  **Invite User** button is disabled and a banner explains how many seats are in
  use. To free up a seat, revoke a pending invitation or deactivate an existing
  user. See [Enterprise Setup — Seat cap
  enforcement](/guides/enterprise-setup/#seat-cap-enforcement) for details.
</Aside>

### Invite token details

- Each invite token is **valid for 7 days** from creation.
- Tokens are **single-use** — once claimed, the token cannot be reused.
- Tokens are stored as SHA-256 hashes in the database. The plain token only appears once, in the invite link.
- If a token expires before the user claims it, you can **resend** the invite from the user list (this creates a fresh token).
- Pending invites can be **revoked** at any time by clicking the Revoke button next to the invite entry.

## Accepting an invite

When a new user opens the invite link, they see the account creation page:

1. The heading names the admin who sent the invite — for example "Ada Lovelace invited you to Pinchy" — so a link from someone they may not expect is easy to place. Above the form, the page shows the email address the account signs in with. It comes from the invite and can't be changed here.
2. The user enters their **name** and chooses a **password**. The rule is shown under the field: at least 12 characters, with a letter and a number. Passwords on the breach-list of common passwords are rejected too. There is no second "confirm password" field — the eye icon shows the password to check it.
3. After clicking **Create account**, Pinchy signs them in straight away and opens the app. If that sign-in doesn't go through (for example, because of too many recent sign-in attempts), the page confirms the account was created, repeats the email address to sign in with, and offers **Continue to sign in**.
4. Smithers (the onboarding agent) greets them with a short interview to learn about the user and set up their personal context.

<Aside type="note">
  If the invite link is invalid or expired, the user sees an error message. Ask
  an admin to resend the invite.
</Aside>

## Managing users

The **Settings → Users** page shows all users and pending invites in a single list. Each entry displays:

- **Name** — The user's display name (or a dash for pending invites).
- **Email** — The user's email address.
- **Role** — Admin or Member.
- **Groups** <Badge text="Enterprise" variant="note" /> — Group memberships. Only visible with an active enterprise license.
- **Status** — Active, Pending (invite not yet claimed), Expired (invite token expired), or Deactivated.

### Viewing user details

Click on any active user row to open the user detail panel. From here you can:

- **Change their role** — Switch between Admin and Member using the Role dropdown. You cannot change your own role, and you cannot demote the last remaining admin.
- **Manage group memberships** <Badge text="Enterprise" variant="note" /> — Check or uncheck groups to add or remove the user from groups.
- **Reset their password** — Generate a password reset link (see below).
- **Deactivate the user** — Prevent the user from logging in (see below).

Click **Save** to apply any role or group changes.

### How groups affect agent access

Group membership determines which restricted agents a user can see. Agents configured with **Restricted** visibility in **Agent Settings → Access** list one or more groups; only members of those groups (and admins) can see the agent in the sidebar or message it via Telegram. Agents set to **All users** ignore group membership entirely.

Changes propagate immediately: removing a user from a group revokes their access to restricted agents on the next sidebar refresh, and adding them grants access without a restart. For the full group model, see [Groups](/concepts/groups/).

### Changing a user's role

1. Click on the user in the user list.
2. In the detail panel, change the **Role** dropdown from Member to Admin (or vice versa).
3. Click **Save**.

If you've turned members' personal agents off ([Member access](/guides/cost-governance/#member-access)), the role decides who keeps one: promoting a member gives them their Smithers back, demoting an admin pauses theirs.

<Aside type="caution">
  You cannot demote the last admin. Pinchy requires at least one active admin at
  all times.
</Aside>

### Resetting a user's password

If a user forgets their password, an admin can generate a reset link:

1. Click on the user in the user list.
2. In the detail panel, click **Reset Password**.
3. A reset link appears. Copy it and share it with the user.
4. The user opens the link, enters a new password, and is signed in with it.

The reset page is dedicated to recovery: it reads **"Reset your Pinchy password"**, shows the email address the account signs in with, and asks only for a new password. Unlike the invite page, it does **not** ask for a display name, so a reset can never change the user's existing name.

Reset links follow the same rules as invite tokens: valid for 7 days, single-use.

When a reset completes:

- The user's existing sessions are **revoked** in the same database transaction as the password update. Any browser or device that was logged in with the old password must sign in again with the new one; the reset page itself signs in with the new password right after the reset. This guards against the case where the password was reset because the previous one might be compromised.
- An `auth.password_reset_completed` entry is written to the audit log with `outcome: success`, the target user, and the invite id. See [Audit trail › Authentication](/concepts/audit-trail/#authentication).
- If any part of the reset fails (database error, etc.), the whole flow rolls back: the user keeps their old password and the reset link stays usable. A matching `outcome: failure` audit entry is written.

### Deactivating a user

Deactivation prevents a user from logging in without permanently deleting their data.

1. Click on the user in the user list.
2. In the detail panel, click **Deactivate**.
3. Confirm the action in the dialog.

When a user is deactivated:

- They can no longer log in, and every session they had ends at once.
- Any chat they have open stops working immediately: Pinchy closes the connection with the message "Your account has been deactivated.", sends the tab to the login page, and refuses anything it still sends. A message they sent a moment earlier that Pinchy was still preparing — looking up the agent, staging attachments — is refused too, before it reaches the agent.
- A tab whose connection was already closed at that moment — in the background for more than five minutes, or reconnecting after a network blip — gets no message. Its reconnects fail, and after the second failed reconnect in a row it checks whether it still has a session and goes to the login page. If Pinchy itself is unreachable, the tab keeps retrying as usual instead.
- A reply that is still running in one of their chats is stopped. Pinchy aborts it on OpenClaw the same way the stop button does, so the agent starts no further tool for them; a tool call that was already executing at that moment can still complete. A reply OpenClaw hasn't started yet is stopped too. If Pinchy is still waiting for OpenClaw to load the agent (right after a restart, for example), it doesn't send the message again. If OpenClaw is still preparing the reply, there is nothing to abort yet and OpenClaw answers that it stopped nothing — so Pinchy keeps asking it to abort that reply — at once, then after a quarter, a half and a whole second, then every two seconds — until OpenClaw confirms the abort, reports the reply over, or turns the message away (then nothing ran). A reply OpenClaw starts in that time is stopped by the next attempt, within about two seconds; a tool the agent starts before then can still run. Pinchy keeps asking for up to a minute; a reply OpenClaw only starts after that is not stopped. If Pinchy had to send the message twice because OpenClaw couldn't load the agent's model the first time, the abort goes to the reply OpenClaw is running now, not to the attempt that failed. Each stopped reply is recorded as `chat.run_aborted` with `reason: "account_deactivated"` and you as the actor. If that first abort failed — OpenClaw is unreachable, or answers that it stopped nothing — the row's outcome is `failure`. When the stop took effect after all, a second `chat.run_aborted` row follows with outcome `success`: `followUp: "aborted_by_run_id"` when a later attempt stopped the reply, `followUp: "stopped_before_dispatch"` when Pinchy didn't send the message again. When OpenClaw instead reports that the reply finished, it is recorded as `chat.run_completed_after_disconnect`.
- Their personal agents are soft-deleted.
- Their data remains in the database and can be restored.
- The user appears as "Deactivated" in the user list with reduced opacity.

You cannot deactivate your own account.

#### What deactivation doesn't stop

Pinchy can only stop what Pinchy started. A few things carry on:

- **A Telegram reply that's already running.** OpenClaw's Telegram channel starts those, not Pinchy, so Pinchy has no way to abort one; it finishes with the agent's permissions. New messages from their Telegram account are refused from the moment you deactivate them.
- **An automation run already handling an email on one of their personal agents.** No new run starts — those agents are removed with the account — but one in progress finishes on its own. Pinchy stops any single turn of an automation run after five minutes.
- **Automations they created on shared agents.** These belong to the agent, not to the person, and keep running with the agent's permissions. Their notifications still go to the deactivated account, where nobody reads them. Disable them in **Agent Settings → Automations**, or recreate them yourself if they should go on.
- **API keys they created.** Keys belong to your organisation and keep working. See [what to rotate when someone leaves](/reference/agent-provisioning-api/#offboarding-what-to-rotate).

### Reactivating a user

To restore a deactivated user:

1. Click on the deactivated user in the user list.
2. In the detail panel, click **Reactivate**.

The user can log in again immediately.

### Accounts nobody invited

Releases up to and including v0.9.1 left the authentication library's sign-up endpoint open, so anyone who could reach your Pinchy URL could register a member account. That is closed now, but an account created back then still signs in. Pinchy looks for them on every start. An account counts as explained if it is the setup admin (the earliest-created admin), claimed an invite, or created one (only admins can). Any other account gets one `user.unknown_origin_detected` row in the audit trail, and while it is active, a banner at the top of **Settings → Users** lists it.

Click **Review** next to an account to open it. If you don't recognise it, **Deactivate** it as described above. If you do — say you demoted the admin who ran setup and they never sent an invite — click **Mark as known** and confirm. It can't be undone — nothing puts an account back on the list. That works on your own account too, and it is recorded as `user.origin_acknowledged` with you as the actor; the account stays off the banner from then on. The banner hides when you dismiss it, but only for this visit — it comes back until every active account is explained or marked as known. [Upgrading](/guides/upgrading/) explains what such an account could reach and how to check what it did.

The check can also miss one: a self-registered account that an admin promoted reads as legitimate once it is the earliest admin left, or once it has sent an invite. Both need an admin to have promoted it first, and the `user.role_updated` row records who did.

### Managing pending invites

Pending and expired invites appear in the user list alongside active users:

- **Pending invites** show a Pending status badge and a **Revoke** button to cancel the invite.
- **Expired invites** show an Expired status badge and a **Resend** button to generate a fresh invite link. An expired invite without an email (created before v0.10) shows **Revoke** instead, since a fresh invite needs an email.

## Profile settings

Every user (not just admins) can manage their own profile at **Settings → Profile**. This page has three sections:

### Changing your name

1. Go to **Settings → Profile**.
2. Update the **Name** field.
3. Click **Save**.

### Changing your password

1. Go to **Settings → Profile**.
2. In the Change Password section, enter your **current password**, then your **new password**, and confirm it. Passwords must be at least 12 characters, contain at least one letter and one digit, and must not appear on the breach-list of common passwords.
3. Click **Change Password**.

A successful change **signs you out everywhere else** — your phone, a second browser, any machine you left logged in. The tab you changed it in stays signed in; everything else asks for the new password. That is the point: changing your password is what you do when you think someone else has your session, and it only helps if their session ends with it.

If you enter the wrong current password repeatedly, Pinchy stops accepting attempts for that account after five tries and tells you how long to wait. The limit is per account, not per browser, so it also holds against someone guessing at your password from a session they should not have.

### Logging out

Click the **Log out** button in the Session section to end your current session and return to the login page.

Logging out also clears what Pinchy kept in this browser for you: unsent message drafts, attachments you staged but didn't send, anything you shared into the installed app but didn't send, and which chat you last had open for each agent. Other Pinchy tabs in the same browser reload, so none of them keeps showing your chats. Unsaved changes in those tabs, such as agent settings you were still editing, are discarded. On a shared computer, the next person who signs in starts clean.

If your session expires instead, nothing is cleared until the next sign-in. When someone else signs in, Pinchy clears the same things first. When you sign back in yourself, your drafts are still there.

One exception: if you share a file into the installed app while nobody is signed in, Pinchy opens the login page. It keeps that file for whoever signs in there within 10 minutes. Pinchy cannot tell who shared it, so on a shared computer, sign in right away or close the login page.

## Emergency admin password reset (CLI)

If the admin has lost their password and there is no other admin who can generate a reset link through the UI, you can reset the password directly from the command line.

Run the following command on the server where Pinchy is deployed:

```bash
docker compose exec pinchy pnpm reset-admin
```

This finds the first admin user, generates a new random password, and prints it to the terminal:

```
Admin password reset for: admin@example.com
New password: aB3kLm9xPqRs7wZn
```

To reset the password for a specific user by email:

```bash
docker compose exec pinchy pnpm reset-admin --email admin@example.com
```

<Aside type="caution">
  The generated password is shown only once. Make sure to copy it immediately.
  After logging in, change the password via **Settings → Profile → Change
  Password**.
</Aside>

<Aside type="note">
  This command requires direct access to the server running Pinchy. It connects
  to the database using the `DATABASE_URL` environment variable configured in
  Docker Compose.
</Aside>

## Audit trail

All user management actions are logged in the audit trail:

| Action                       | Audit event                     |
| ---------------------------- | ------------------------------- |
| Account created              | `user.created`                  |
| Account nobody invited found | `user.unknown_origin_detected`  |
| Account marked as known      | `user.origin_acknowledged`      |
| User invited                 | `user.invited`                  |
| Invite blocked (seat cap)    | `user.invite_blocked`           |
| Role changed                 | `user.role_updated`             |
| Group memberships changed    | `user.groups_updated`           |
| User reactivated             | `user.updated`                  |
| User deactivated             | `user.deleted`                  |
| Password reset completed     | `auth.password_reset_completed` |

Each admin action records which admin took it, and `user.created` records the new account itself as the actor — via the setup wizard or an invite. A claim that fails to create the account is recorded too, with `system` as the actor. Entries record the affected user's name, and the before/after role or group diffs. We never store the affected user's email address in plaintext: deactivation events omit it entirely (GDPR Art. 17), and invite events store a keyed HMAC hash plus a short masked preview instead. Password resets also revoke the target user's active sessions in the same database transaction, so a partial failure rolls back the whole reset — the old password keeps working and the reset link stays usable. The audit row is written after that transaction commits, and a failed reset records its own `outcome: failure` entry. See [Audit Trail](/concepts/audit-trail/) for more information on viewing and exporting audit logs.
